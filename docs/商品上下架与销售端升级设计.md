## 1. 缺价国家下架 + 管理员可上下架

### 1.1 问题的真实形状

"下架"要作用的对象是 **产品线 × 国家** 这个组合，不是商品。因为社媒的荷兰、静态的俄罗斯根本没有商品行，
没有东西可以设 `is_active = false`。所以不能靠现有字段解决。

### 1.2 方案：两层控制

**第一层 · 默认规则（一次性解决 11 国）**

官网目录只输出"有报价"的组合。没价的国家不再出现在列表里，而不是出现后标"暂无报价"。

```
/ api/public/catalog  ←  只返回 offers 非空的 (产品线, 国家)
```

理由：客户看到"暂无报价"会以为系统坏了，或者以为自己选错；直接不出现，他就不会点。
代价：客户无法知道"你们支持但不卖这个国家"——按玖夜这次的口径，这正是想要的。

**第二层 · 逐条覆盖（管理员手动上下架）**

新表 `catalog_listings`：

| 字段 | 说明 |
| --- | --- |
| `line_code` | residential / social / live |
| `region_id` | 国家 |
| `status` | `listed` / `unlisted` |
| `reason` | 备注（如"上游无货，暂停"） |
| `updated_by` | 操作人 |
| 唯一约束 | `(line_code, region_id)` |

**没有记录 = 按默认规则推导**（有价即上架）。有记录 = 以记录为准。这样存量数据零迁移。

三种状态的实际效果：

| 场景 | 有价 | 记录 | 官网表现 |
| --- | --- | --- | --- |
| 正常在卖 | 有 | 无 | 出现，显示价格 |
| 缺价（11 国现状） | 无 | 无 | **不出现**（第一层规则） |
| 缺价但想展示 | 无 | `listed` | 出现，显示"暂无报价"，不可下单 |
| 有价但暂停 | 有 | `unlisted` | **不出现**（即使有价） |
| 补价后恢复 | 有 | `unlisted` | 仍不出现，需管理员手动上架 |

最后一行是刻意的：管理员下架是有意决定，不能因为后来补了价就自动复活。

### 1.3 后台界面

「商品与价格」加第三个页签 **官网可见性**，网格展示 3 条线 × 34 国 = 102 格：

```

美国      ● 有价         ● 有价        ● 有价
荷兰      ● 有价         ○ 未上架      ● 有价
```

- 点格子切换上架/下架，二次确认
- 每格显示来源：`默认` 或 `手动`
- 顶部批量：整条线下架 / 整列下架（按国家）
- 下架缺价国家可以"一键清理"：所有无价且无记录的组合不用管，本来就不可见

同时补上**商品级**上下架：现有商品表格加"上架/下架"开关，接 `is_active`。
这是另一件事（整条商品停售），与上面的组合级可见性并存：
`is_active = false` 时，该商品在所有国家都不出现。

## 3. 下拉框"一直在动"

### 3.1 现象与截图

点击"有货 / 无货"下拉时，展开的选项层位置漂移，蓝色高亮块浮在两行之间，不贴着触发它的下拉框。

### 3.2 三个可能根因（按可能性排序）

**① 原生 select 弹层 + 滚动容器**

表格外层是 `.table-scroll{overflow:auto}`（`CatalogManagementView.vue` 样式段）。
Chrome 的原生 select 弹层由浏览器绘制，**不是 DOM**，在滚动容器内滚动或布局变化时会重新定位。
表格行高 58px、输入框 32px，输入框 focus 时 `box-shadow` 虽不引起 reflow，但 `:focus-visible`
的 `outline-offset` 会让浏览器重算可见区域，触发弹层重定位。

**② 数据刷新导致行重排**

`productDrafts` 在每次 `loadProducts()` 时整体重建（`CatalogManagementView.vue:67`）。
若下拉展开期间发生重新加载（筛选、保存某行、分页），`v-for` 的行会被重建，弹层跟着跳。

**③ 内嵌预览环境（iframe）**

当前预览面板是内嵌浏览器。原生弹层在 iframe 内定位依赖宿主窗口坐标，视口高度变化
（移动端键盘、面板拖拽）会让它漂移。

### 3.3 修法：统一自绘下拉，不用原生 select

新增 `components/AppSelect.vue`：

- 触发按钮是普通 `<button>`，选项层是 `position: fixed` 的 DOM 节点
- 位置在打开时用 `getBoundingClientRect()` 计算，并监听 `scroll`（捕获阶段）、`resize`、
  `ResizeObserver` 重算；一旦触发元素离开视口就关闭
- 键盘可用（上下/Enter/Esc）、点击外部关闭、支持禁用项与分组
- 不依赖任何父级 `overflow`，从根上消除三种根因

**为什么不只改样式**：定位问题出在"浏览器自己画的弹层"，CSS 管不到。
留着原生 select 就永远有这个风险，只是换个页面复现。

### 3.4 替换范围（分三批）

| 批次 | 文件 | 数量 | 理由 |
| --- | --- | --- | --- |
| P0 | `CatalogManagementView` | 6 | 截图处，先修 |
| P1 | `OrderCenterView`、`CustomerManagerView`、`SupplierPoolView` | 32 | 管理端高频操作 |
| P2 | `WorkspaceView`、`InboxView`、`OrderOnBehalfDialog` 等 | 32 | 其余表单 |

同时把弹窗统一到 `AppDialog`（滚动锁定 + 焦点陷阱 + Esc 关闭），解决"窗口"这一类问题的另一半。

### 3.5 工作量

`AppSelect` + `AppDialog`：**1 天**
P0 替换 + 验证：**0.3 天**
P1、P2 替换：**1.2 天**
合计 **2.5 天**（P0 可单独先上，0.3 天见效）。

### 3.6 实施记录（2026-11-10）：只做了 P0，其余经过核查不需要

落地：

- `components/AppSelect.vue`：Teleport 到 body + `position:fixed`，打开时按
  `getBoundingClientRect` 算坐标，面板渲染后按真实高度校正（下方不够就向上翻），
  `scroll`（捕获阶段）/`resize` 重算，`pointerdown` 外部关闭，键盘 Enter/Space/上下/Esc/Tab 可用。

**P1/P2 复核结论**：核查了全部 70 个 select 的位置——

## 4. 双击价格直接编辑

### 4.1 现状

每行已有价格 `<input>` + 独立「保存」按钮（`CatalogManagementView.vue` 商品表格）。
问题是：改一个价要"点输入框 → 输入 → 找保存按钮 → 点"，一行两次以上点击，批量改时很烦。

### 4.2 方案：双击进入编辑，点一下确认

```
默认（只读）
  ¥ 79                        ← 纯文本，不可编辑

双击
  ¥ [ 79        ]  ✓  ✕      ← 自动全选，光标就位

输入 85 后
  ¥ [ 85        ]  ✓  ✕      点 ✓ 或按 Enter 保存
                              Esc 或点 ✕ 取消
```

交互细节：

| 操作 | 行为 |
| --- | --- |
| 双击价格文字 | 进入编辑，全选当前值，光标就位 |
| 输入后点 ✓ / 按 Enter | **保存**，按钮变 spinner，成功后回到只读并显示新值 |
| 按 Esc / 点 ✕ | 取消，恢复原值，不发请求 |
| 输入非法（≤0、非数字、超上限） | 就地红字提示，不允许提交，不退出编辑态 |
| `price_locked = true` 的行 | 不可编辑，显示"随月价联动"，双击给出提示"请在零售价页修改" |
| 提交后价格未变 | 不请求，直接退出编辑 |

### 4.3 "二次确认"的两种理解，我选哪种

玖夜原话："需要二次确认只需要再点一下确认就行了"。

- **理解 A**：点 ✓ 就是二次确认（编辑一次 + 确认一次），不再弹窗。→ **采用**
- **理解 B**：点 ✓ 后再弹一个"确认改成 85 吗"的对话框。→ 不做，批量改价时会变成点击地狱

所以二次确认 = ✓ 按钮本身。为防止误触，✓ 只在值发生变化且合法时可用。

### 4.4 顺带解决的批量改价

现有"统一设置售价"批量编辑器保留，但它的问题是一次改一批、无法逐行微调。
双击编辑 + 批量编辑器并存：批量做粗调，双击做细调。

### 4.5 工作量

`PriceCell` 组件（只读/编辑两态 + 校验 + 保存）：**0.5 天**
接入商品表与零售价表两处：**0.2 天**
测试（双击进入、Enter 保存、Esc 取消、非法值、锁定行、未变更不请求）：**0.3 天**
合计 **1 天**。

### 4.6 实施记录（2026-11-10）

`components/PriceCell.vue` 已落地，两个易错点都处理了：

1. **失焦 = 取消**，不是保存。价格直接给客户看，误触不能生效。
2. **✓ 用 `mousedown.prevent` 保持焦点**。否则点它的瞬间先触发 blur，单元格自我取消，
   click 落空——这是行内编辑最常见的 bug。

同时删掉了两处「保存」按钮列：现在价格和售卖状态都是确认即生效，少一次点击。

## 5. 现状说明：映射的供应商商品、API、两条下单流程

这一节不设计新东西，只把现有机制讲清楚——因为界面上的"选择已映射的供应商商品"没有解释，容易误用。

### 5.1 "映射的供应商商品"是什么

一句话：**本地卖的东西和上游买的东西不是同一个东西，映射就是这两者的对照表。**

| 层 | 表 | 例子 |
| --- | --- | --- |
| 本地零售 | `products` | 中国香港 静态住宅IP 30天，¥79 |
| 上游供货商品 | `supplier_products` | 「独享静态住宅（普通）」，供应商侧 ID `2` |
| 上游国家 | `supplier_regions` | 香港（`HK`，无城市细分） |
| **映射关系** | `product_supply_rules` | 上面三者 + 资源池 + 模式 |

`product_supply_rules` 的字段含义：

| 字段 | 作用 |
| --- | --- |
| `product_id` | 本地的哪个商品 |
| `region_id` | 本地哪个国家 |
| `supplier_product_id` | 上游哪个商品 |
| `supplier_region_id` | 上游哪个国家（必须是该商品下的） |
| `pool_id` | 属于哪个资源池（当前只有一个 `global_proxy_pool`） |
| `mode` | `manual`（人工采购）/ `auto`（自动采购，**当前被配置强制关闭**） |
| `is_enabled` | 是否启用 |

**为什么必须映射**：客户买的"香港静态住宅 30 天"是零售概念；上游卖的是"这个商品在这个国家、
这个网段、这个时长"的 SKU。没有映射，系统不知道客户这笔单该去上游买哪一个。

界面上"选择已映射的供应商商品"= 选一条 `product_supply_rules`（或旧的 `supplier_products.local_product_id` 兼容路径）。

### 5.2 上游 API 怎么用

上游是"全球代理"（`SUPPLIER_CODE = quanqiudaili`），6 个端点，全部在 `supplier_service.py` 顶部：

| 端点 | 用途 | 落到本地的表 |
| --- | --- | --- |
| `/externalapi/conpons/getProductList` | 商品目录 | `supplier_products` |
| `/externalapi/inventory/countryList` | 国家清单 | `supplier_regions` |
| `/externalapi/inventory/cityList` | 城市细分 | 同上（`city_name` 非空） |
| `/externalapi/inventory/getBuyProductSku` | 可买 SKU + 库存 | `supplier_ip_segment_snapshots` |
| `/externalapi/product_order/checkInventory` | 网段库存检测 | 同上 |
| `/externalapi/product_price/getProductUnitPrice` | 报价（成本） | `supplier_quotes` |

调用方式：同步任务定时拉取（`supplier_sync`）→ 存**快照**，不是实时透传。
下单时校验快照新鲜度：

- 库存快照超过 `SUPPLIER_INVENTORY_TTL_MINUTES` → 409「网段快照已过期」
- 报价快照超过 `SUPPLIER_QUOTE_TTL_MINUTES` → 409「报价快照已过期」

**关键事实**：拉取的是**成本**，不是售价。售价来自本地零售价目表（`retail_price_rules`），
两者独立——成本涨了不会自动改售价，需要人工调价。这是刻意的，避免上游涨价直接穿透到客户。

### 5.3 客户购买线路的完整流程

```
① 浏览   官网 → 产品线 → 国家 → 规格/周期
         GET /api/public/catalog（未登录：无价格）
         GET /api/catalog（登录：含价格）

② 算价   POST /api/public/orders/preview（需登录）
         校验：商品在售、地区匹配、周期合法
         返回：单价、合计（零售价目表月价 × 周期，线性无折扣）

③ 建单   POST /api/customer/orders
         校验：产品启用/有货、地区匹配、金额由后端算（前端传价无效）
         落库：status = pending_payment / pending_confirm
               assigned_sales_id = 客户的 sales_id（业绩自动归属）
               created_via = self_service

④ 支付   ├ 余额：POST /api/wallet/orders/{id}/pay-balance（余额不足 422，不允许负余额）
         ├ 在线：POST /api/wallet/orders/{id}/pay-online（生成支付单，等回调）
         └ 联系经理：不走支付，等管理员线下收款后确认

⑤ 确认   管理员 POST /api/admin/orders/{id}/confirm
         闸门：未付款不能确认交付（已修）

⑥ 交付   管理员 POST /api/admin/orders/{id}/deliver
         指定节点 + 到期日 → 生成 CustomerLine → 客户中心可见

⑦ 到期   定时任务 expire_lines 把过期线路置 expired
         line_expiry_reminders 提前提醒（站内信 + 可选企微推送）

⑧ 续费   POST /api/customer/lines/{id}/renew → 生成续费订单 → 回到 ④
```

三个闸门（都已实现，这里列出是为了避免误以为可以绕过）：

1. 已付款订单不能直接取消，必须走退款登记
2. 未付款订单不能确认
3. 在线支付进行中不能取消

**注意**：客户自助下单这条链路**全程不碰上游供应商**。商品是本地零售商品，
交付由人工指定节点。上游采购是下面这条独立链路。

### 5.4 管理员创建订单的完整流程

界面：后台「订单中心 → 新建资源池订单」。这是**采购单**，不是给客户开销售单。

```
① 选客户   GET /api/admin/order-center/options
           只列已注册且未删除的客户（user_id 非空）
           —— 没有登录账号的客户不能走这条链路，因为他付不了款

② 选商品   本地 Product（必须在售）

③ 选供应商  "选择已映射的供应商商品"
           → 选中 ProductSupplyRule
           → 带出 supplier_product_id + supplier_region_id
           校验：分类一致、映射存在、供应商商品可用、国家属于该商品

④ 选网段   supplier_segment_snapshot_id（库存快照）
           校验：未过期、请求数量足够、网段充足

⑤ 选报价   supplier_quote_id（成本快照）
           校验：未过期、周期匹配

⑥ 定价     零售价目表（不是上游报价）× 周期
           写入：amount / total_amount（售价）
                supplier_cost（成本快照，用于算毛利）

⑦ 建单     POST /api/admin/order-center/orders
           status = pending_payment
           order_type = purchase，source_type = resource_pool
           created_via = admin

⑧ 后续     支付 → 人工采购审核 → 上游下单（人工/沙箱）→ 补偿
           —— 系统不会自动向上游下单（`SUPPLIER_AUTO_PROCUREMENT_ENABLED` 强制关闭）
```

### 5.5 管理员现在开不了"客户销售单"，这是缺口

| 想做的事 | 现在怎么做 |
| --- | --- |
| 客户要买一条香港静态住宅，管理员代开 | **做不到**。资源池订单是采购单，走的是上游链路，不是销售单 |
| 绕路方案 | 让客户自己登录下单，或用销售的代客下单（`POST /api/orders/on-behalf`） |

建议：把代客下单的入口也给管理员（**已经有**，在客户详情页），并明确界面上"资源池订单 ≠ 销售订单"。
或者把资源池订单页的标题改成「采购单（对接上游）」，避免误解。这条属于文案修正，不做功能。

### 6.2 需要玖夜拍板

1. **缺价国家是"不显示"还是"显示但标暂不可售"？**

2. **销售能不能改客户资料？**

4. **管理员"以销售视角预览"要不要做？**
   原型有。我建议做只读版，排查问题不用借账号。

5. **下拉组件要不要全量替换 70 处？**
   全量 2.5 天，只做 P0 是 0.3 天。全量的收益是"以后不再出现同类问题"，代价是改动面大、要回归所有表单。
