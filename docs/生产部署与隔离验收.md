# 生产部署与隔离验收

## 能力边界

本文只描述构建和隔离验收，不代表已经部署生产环境。在线支付、余额扣款、退款、真实线路采购和真实订阅交付均不在当前系统能力内。

## 生产必需变量

生产后端必须显式提供以下变量，任一缺失都会在 Compose 解析或应用启动阶段失败：

| 变量 | 要求 |
| --- | --- |
| `ENVIRONMENT` | 固定为 `production` |
| `DATABASE_URL` | `postgresql+psycopg://` 地址；禁止 SQLite、localhost 和回环地址 |
| `JWT_SECRET_KEY` | 至少 32 字节的高熵随机值；不得使用示例值 |
| `SESSION_TOKEN_HASH_KEY` | 独立于 JWT 密钥的至少 32 字节会话令牌哈希密钥 |
| `FRONTEND_ORIGIN` | 单一 HTTPS 来源；禁止通配符、localhost、凭据、路径和查询参数 |
| `JWT_EXPIRE_MINUTES` | 固定为 10 分钟 |
| `REFRESH_SESSION_DAYS` | 固定为 7 天，不滑动延长 |
| `RATE_LIMIT_BACKEND` | 生产固定为 `redis`，禁止回退到进程内存 |
| `REDIS_URL` | 共享 Redis 地址；禁止 localhost 和回环地址，密码由密钥管理服务注入 |
| `TRUSTED_PROXY_CIDRS` | 逗号分隔的可信反向代理 IP/CIDR；禁止空值、无效网段及 `/0` |
| `LOGIN_RATE_LIMIT` | 单一客户端在窗口内的登录请求上限，默认 10 |
| `REGISTRATION_RATE_LIMIT` | 单一客户端在窗口内的注册请求上限，默认 5 |
| `RATE_LIMIT_WINDOW_SECONDS` | 限流固定窗口秒数，默认 60 |

不要把真实密钥写入 `.env.production.example`、Compose 文件、镜像构建参数或版本库。应由部署平台的密钥管理功能注入。

## TLS、代理与客户端地址

生产 Uvicorn 使用 `--no-proxy-headers`，不会直接采信客户端传入的 `X-Forwarded-For`、`X-Forwarded-Proto` 或 `Forwarded`。应用只在 TCP 直连地址属于 `TRUSTED_PROXY_CIDRS` 时解析 `X-Forwarded-For`，并从右向左剥离可信代理，得到第一个不可信地址作为客户端来源。TLS 代理必须覆盖而不是原样透传外部请求的转发头，并只从受控网络访问 API。

应用负责设置：

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Referrer-Policy: no-referrer`
- `Permissions-Policy`
- `Cross-Origin-Opener-Policy` 和 `Cross-Origin-Resource-Policy`
- API 的限制性 `Content-Security-Policy`
- 登录和注册响应的 `Cache-Control: no-store`

TLS 终止反向代理负责：TLS 1.2/1.3、证书自动续期、HTTP 到 HTTPS 跳转、`Strict-Transport-Security`、请求体大小和连接超时。应用不设置 HSTS，因为应用本身无法可靠判断外部连接是否已经由可信代理完成 TLS 终止。

## Redis 限流故障策略

登录和注册使用 Redis 原子计数，在所有 API 实例间共享。应用启动时会执行 Redis `PING`；生产 Redis 不可用时启动失败。运行期间 Redis 连接失败时，登录和注册返回 503 并拒绝请求，不会静默回退到单进程内存限流。账号不存在、密码错误、停用和锁定统一返回相同 401 文案；账号锁定计数仍在数据库中维护。

## 生产镜像构建

在配置好上述环境变量且 Docker daemon 可用后执行：

```shell
docker compose -f docker-compose.prod.yml config --quiet
docker compose -f docker-compose.prod.yml build --pull
```

生产后端镜像只安装 `requirements.txt`，以 `app` 非 root 用户运行。生产前端使用多阶段构建，最终由非特权 Nginx 提供静态文件，不运行 Vite、不挂载源码，也不会在启动时执行 `npm install`。生产 Compose 不执行种子脚本。

## 隔离 PostgreSQL 验收

`docker-compose.acceptance.yml` 使用 PostgreSQL 17 和 `tmpfs` 数据目录。该数据库随容器删除，不连接开发或生产数据库。

```shell
docker compose -f docker-compose.acceptance.yml build --pull
docker compose -f docker-compose.acceptance.yml run --rm postgres-acceptance
```

`postgres-acceptance` 会顺序执行：

1. `alembic downgrade base`
2. `alembic upgrade head`
3. `alembic check`
4. PostgreSQL 并发交付与事务回滚测试
5. 两个独立 Redis 客户端共享限流状态的实测

只有上述命令退出码为 0，才可记录 PostgreSQL 迁移和事务验收通过。SQLite 结果不得替代该结论。

## 生产镜像运行验收

PostgreSQL 验收通过后，在同一临时环境启动实际生产镜像并运行检查脚本：

```shell
docker compose -f docker-compose.acceptance.yml up --build -d api web
python scripts/verify_production_images.py
docker compose -f docker-compose.acceptance.yml down --remove-orphans
```

脚本检查以下项目：

- API 与 Web 镜像声明非 root 用户；
- API 与 Web 容器健康检查进入 `healthy`；
- 容器不存在 bind 类型的源码挂载；
- API 最终文件系统不包含测试、开发数据库、`.env` 和 pytest 缓存；
- Web 最终文件系统不包含前端源码、`node_modules` 和 `.env`。

无论验收成功或失败，都应执行 `down --remove-orphans`。验收 Compose 不得复用生产数据库地址。
