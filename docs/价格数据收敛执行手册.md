# 价格数据收敛执行手册（生产库回填 + 长周期归一）

> 适用版本：定价改为「月价 × 周期数」之后（`Product.resource_category` 已上线）。
> 关联：`docs/定价收敛实施方案.md` §7、`backend/scripts/backfill_product_pricing.py`。
> 现状：**生产库已于 2026-11-12 执行完毕**（分类 0 待回填、展示价 0 不一致、长周期 369 条归一，复核全 0）。
> 本手册保留为下次换库/灾备恢复后的执行依据。

---

## 0. 这件事到底是什么

两步，互相独立：

| 步骤 | 改什么 | 影响客户吗 | 能回滚吗 |
| --- | --- | --- | --- |
| A. 回填分类与展示价 | `products.resource_category`、`products.price` | 会。展示价从旧折扣价变成线性价（涨价） | 改数据即可（置 `resource_category = NULL`） |
| B. 长周期行归一 | `retail_price_rules` 的 90/180/360 天行 | **不会**。这些行已不参与报价，只是休眠数据 | 需从备份恢复，或用旧值反算 |

**为什么分两步**：A 是业务口径切换，必须挑窗口、提前通知；B 是清洁数据，不影响任何人，可以随时跑。
不要把 B 和 A 绑在一次发布里——A 出问题时，B 的写入会让「回滚到备份」多丢一天数据。

## 1. 执行前检查（只读）

在服务器项目目录执行。以下命令都不写库。

```bash
cd /opt/99ipxin

# 1) 当前迁移版本必须是 0034 或更高（resource_category 已加）
docker compose --env-file .env.production -f docker-compose.prod.yml \
  run --rm migrate alembic current

# 2) 备份必须新鲜（退出码 0；不新鲜就先跑一次备份）
python3 scripts/backup_postgres.py --check-only
python3 scripts/backup_postgres.py            # 需要时立即补一份

# 3) 预演：只读，输出“哪些商品会归入哪个分类、展示价从多少变多少”
docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T api python scripts/backfill_product_pricing.py --dry-run
```

预演输出必须人工确认三件事：

1. **跳过清单里只有固定价商品**（例如「直播线路」）。如果出现静态住宅/社媒/直播专线（手机/电脑）被跳过，说明 `product_type` 文案与分类标签不一致，先停下来核对，不要 `--apply`。
2. **展示价变化方向合理**：只应上涨（旧表在打折），不应出现降价。出现降价说明月价配错。
3. **命中商品数**与后台「商品与价格」在售商品数量大致相符。差异过大先查是不是有重复商品。

## 2. 执行 A：回填分类与展示价

挑低峰窗口，先公告长周期涨价（180 天约 +9%，360 天约 +20%，以预演输出为准）。

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T api python scripts/backfill_product_pricing.py --apply --verify
```

- `--apply` 写库；`--verify` 写完立刻复核，输出 `{'uncategorized': 0, 'display_price': 0, 'period_rows': N}`。
- 只要 `uncategorized` 或 `display_price` 不为 0，命令退出码就是 1，按第 5 节排查。
- 这一步**不动**长周期行，`period_rows` 此时仍为 N（正常）。

随后跑一次全站价格巡检：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T api python scripts/audit_price_consistency.py
```

退出码必须是 0。若报「展示价不一致」，先看是不是执行后有运营在后台改了月价——重跑一次 `--apply --verify` 即可收敛。

---

## 3. 执行 B：长周期休眠行归一（可延后）

确认 A 已稳定运行至少一个工作日后再做。先预演：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T api python scripts/backfill_product_pricing.py --normalize-periods --dry-run
```

输出应为「N 条价目行与线性值不一致」，并抽样列出 `90天: 150 → 180` 这类变化。确认后执行：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T api python scripts/backfill_product_pricing.py \
  --apply --normalize-periods --verify
```

复核输出三个 0 才算完成。

> 归一前后客户看到的价格完全一样（报价只读 30 天档）。如果这一步之后有客户说价格变了，
> 问题不在这一步，去查 30 天档是否被改过（审计 `retail_price_rule` / `update_retail_price`）。

## 5. 出问题怎么退

| 现象 | 处理 |
| --- | --- |
| 展示价出现降价 | 立刻停止，记录预演输出；查该国家 30 天档是否被误改。**不要**继续 `--apply` |
| 分类回填命中 0，但商品明显是静态住宅 | 检查 `product_type` 是否被改过文案。脚本只认 `RESOURCE_CATEGORY_CODES` 的四个标签，不猜 |
| 复核 `display_price` 不为 0 | 有并发改价。重跑 `--apply --verify`；仍不收敛则查 `retail_price_rules` 是否有重复 `(分类,国家,30天)` 行 |
| 需要整体回滚 A | `UPDATE products SET resource_category = NULL;` 立即退回旧固定价逻辑（秒级生效，不用发版）。之后从备份恢复 `price` 与 `resource_category` |
| 需要回滚 B | 只能从执行前备份恢复 `retail_price_rules`；因为 B 不影响报价，通常不值得为它恢复整库 |

回滚只影响**后续报价**，不会改已成交订单的金额（订单存的是快照）。
