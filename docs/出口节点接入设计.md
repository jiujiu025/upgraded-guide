# 出口节点 API 接入设计

> 状态：探测脚本已落地，业务代码**未接入**
> 日期：2026-11-26
> 上游文档：出口节点 API v1（2026-10-28 上线），接口地址 `https://chukou.154769.xyz/api/integration/v1`
> 相关代码：`backend/scripts/chukou_probe.py`（新增）、`backend/app/services/transit_service.py`、
> `backend/app/services/xui_client.py`、`backend/alembic/versions/0036_transit.py`
> 相关文档：[3xui 中转自动化设计](3xui中转自动化设计.md)

## 1. 结论先行

**这不是 3x-ui 的替代品，它是 3x-ui 的外包版。两者做同一件事，结构上几乎一一对应。**

工作区里 3x-ui 方案已经写完了模型（`transit_vps` / `transit_routes` / `transit_provisions`）、
迁移 `0036`、面板客户端 `xui_client.py`（登录 / 入站 / 模板 / 重启全齐），差最后一步
`provision_transit` 接线。

出口节点 API 提供的是同一套东西的托管版本：

| 自建 3x-ui 里的概念 | 出口节点 API 的对应物 |
| --- | --- |
| `transit_vps`（一台机器，按 `group_code` 分 us / hk） | 供应商的 node（`hkt1:19` / `us1:13`），按 `link_type` 分订阅 / vless |
| `transit_routes`（国家 → 区域组） | `link_type` 决定香港还是美国，颗粒度更粗 |
| `inbounds/add` 建入站 + 分配端口 | `POST /provisions` 分配节点 |
| Xray 模板追加 socks5 出站指向住宅 IP | `outbound` 字段填住宅代理 |
| 路由规则绑定入站与出站 | 供应商内部完成，不可见 |
| 本地拼 `vless://` 链接 | `GET /bindings/{id}/link` 返回订阅地址或 vless |
| `TransitProvision (order_id, line_index)` 幂等 | `business_id` = `{order_no}-{index}` 幂等 |
| 删 inbound 回收端口 | **没有对应接口** |

差别只在谁承担运维：

| 维度 | 自建 3x-ui | 出口节点 API |
| --- | --- | --- |
| 上线时间 | 买 VPS、装面板、配 reality | 拿到 Key 当天可用 |
| 区域覆盖 | 想加哪台加哪台，`transit_routes` 随便配 | **只有香港、美国两地，且绑死 link_type** |
| 传输层 | reality / ws / grpc / tls 自由 | 只有普通 TCP（客户侧仍是 reality vless，不影响体验） |
| 故障排查 | 面板日志、Xray 日志全在手 | 只有一句 `message` |
| 回收/释放 | 删 inbound，端口立刻复用 | **无接口，占用不可主动归还** |
| 重启影响 | 改模板重启，**自己客户瞬断 1-3 秒** | 保存会让节点重载，**该节点客户也瞬断几秒** |
| 单机容量 | 自己定（文档建议 100-200） | 按上游节点库存 |
| 面板可达性 | 后端要能直连海外 VPS，可能超时 | 供应商帮你扛这一层 |
| 长期成本 | VPS 固定成本，量越大越便宜 | 按上游计费（未知，见第 7 节） |

**推荐做法是「双通道」，不是「二选一」：**

保留 3x-ui 作为主执行层（区域自由、可回收、可控），把出口节点 API 接成同一层的
**第二个 provider**，补三种缺口：

1. 某国的 `transit_routes` 指向的区域组**没有可用自建机** → 走 API，订单当天能卖；
2. 自建机达到 `max_inbounds` → 溢出到 API，不用急着扩机器；
3. 自建机或面板故障 → API 兜底，客户不至于卡在 `pending_transit`。

反过来不成立：现在就把 3x-ui 换掉，会丢掉 23 个可售国家的区域覆盖——出口节点
API 只有两地；而且没有释放接口，线路到期后的占用成本无法控制。

## 2. 三个必须先验证的未知

文档写得清楚，但有三件事只能靠实跑确认，**在跑通之前不写业务代码**。

| 未知 | 为什么重要 | 怎么验 |
| --- | --- | --- |
| 真实出口能不能通过连通性检测 | 文档示例地址是假的（`203.0.113.10`）；上游住宅代理是否允许被第三方节点回连、是否有 IP 白名单，只有试了才知道 | `chukou_probe.py provision --socks5 <真实住宅>` |
| 订阅地址里到底是什么 | 决定香港那条线路的交付形态（见 3.3）。可能是 base64 节点列表、Clash YAML，或别的东西 | `chukou_probe.py sub --business <id>` |
| vless 链接的字段是否完整 | 文档示例带 `security=reality`，需要 `pbk/sid` 才能生成可用配置；`proxy_link.parse_link` 能解析，但字段齐不齐要看真实返回 | `chukou_probe.py sub` 会打印全部 query 参数 |

探针脚本已经把这些串成一条命令链，不需要手工拼请求。

## 3. 数据映射

### 3.1 编号

| 上游字段 | 我们的来源 | 规则 |
| --- | --- | --- |
| `business_id` | `orders.order_no` + 线路序号 | `{order_no}-{index}`，一单多线时每条线路一个节点（上游是 1:1 绑定） |
| `request_id` | 由 `(order_id, line_index, 操作类型)` 稳定重建 | `prov-{order_id}-{line_index}` / `chg-{order_id}-{line_index}-{n}`。**必须是可重建的固定值**，程序重启后原样重发才能拿回原任务 |
| `node_id` | 上游返回，存进 `CustomerLine`/采购台账 | 当不透明字符串存，不解析不拼接 |

`business_id` 里的字符限制是 1-64 位、字母数字加 `_ . : -`，`order_no` 符合。

### 3.2 出口

从 `PurchaseResult.accounts` 的 `ProxyAccount` 直接构造：

```python
# 优先用链接写法，URL 编码交给 quote；上游账密一般是字母数字，但别赌
from urllib.parse import quote
outbound = (
    f"socks5://{quote(account.username, safe='')}:{quote(account.password, safe='')}"
    f"@{account.ip}:{account.port}"
)
```

用户名或密码里含 `:@/?#%` 时，编码后才是安全写法。文档明确：非 Base64 的认证写法里
`@` 和 `/` 不编码会被直接拒绝。

**不要**用 `地址:端口:用户名:密码` 那种写法省事——它虽然对密码宽容，但用户名含冒号就废，
而且和链接写法的错误文案不一样，排查时容易绕。

### 3.3 链接交付：两种形态

| 形态 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 直传 | 把上游 `link` 原样写进 `CustomerLine.node_link` | 零解析成本，一条线路一个地址 | 暴露上游域名（`*.154769.xyz`）；客户 3 条线路就有 3 个订阅地址，和「一个客户一个订阅」的体验冲突；上游失效即客户失效 |
| B. 转接 | `parse_link(上游链接)` → 建 `Node` → 走自己的客户级订阅 | 体验与现有线路一致；客户换线路不用换地址；上游域名不外露 | 需要能解析；订阅形态还要多拉一次内容，多一个失败点 |

**建议：vless 走 B，订阅按探针结果定。**

- vless 是单条 `vless://`，`proxy_link.parse_link` 已支持，直接构造 `ParsedNode` 即可。
  注意 `security=reality` 时必须带 `pbk`，否则生成的 Clash 条目连不上（探针会打印全部参数）。
- 订阅如果是 base64 节点列表，可以解码后逐行 `parse_link`，同样走 B。
- 订阅如果是 Clash YAML 或无法解析的自定义格式，只能走 A，或只取其中的节点字段落库。

### 3.4 状态与到期

| 上游状态 | 我们的处理 |
| --- | --- |
| job `pending` | 订单保持 `pending_transit`，继续轮询 |
| job `succeeded` | 写 `CustomerLine`（`node_link` / `node_qr_data`），订单推进到已交付 |
| job `failed` | **仍保持 `pending_transit`**，不标 `failed`。IP 已经买了（钱已花），标失败会诱导人工重试，重试就是再买一次 IP |
| `needs_review` | 保持 `pending_transit`，记 `TRANSIT_NEEDS_REVIEW`，通知管理员，禁止自动重试 |
| 5 分钟仍 `pending` | 停止轮询，保持 `pending_transit`，交给定时任务隔一段再查（文档允许） |

**`expires_at` 不要抄上游的。** 上游从「节点首次实际使用」才开始计时；
我们的 `CustomerLine.expires_at` 按订单 `billing_days` 从交付时间算。两者口径不同，
混用会让到期提醒提前或延后。上游的 `expires_at` 只用来判断节点是否被上游回收。

## 4. 接入位置：作为可切换的第二 provider

### 4.1 适配器

新增 `app/suppliers/chukou.py`，不实现 `ReadOnlySupplierAdapter`（它没有商品/报价概念），
单独一个类：

```python
class ChukouAdapter:
    def list_nodes(self) -> list[EntryNode]: ...
    def provision(self, *, request_id, business_id, outbound, node_id="auto", link_type=None) -> JobRef: ...
    def get_job(self, job_id) -> JobResult: ...
    def get_binding(self, business_id) -> Binding: ...
    def change_outbound(self, *, request_id, business_id, outbound) -> JobRef: ...
    def get_link(self, business_id) -> LinkResult: ...
```

约束沿用现有适配器惯例：

- 密钥从 `resolve_api_key` / 环境变量读，不进数据库明文、不进日志、不进异常正文；
- `base_url` 走配置白名单，不允许请求参数覆盖；
- 错误归一化成 `SupplierRateLimitError` / `SupplierTimeoutError` / `SupplierBusinessError`，
  不要用上游中文消息驱动状态机；
- `outbound` 和 `link` 属于凭据，`repr`、审计、通知里都要脱敏。

探针脚本里的 `ChukouClient` 已经实现了这六个方法、轮询、重试和错误映射，
适配器可以直接复用它，只补错误类型翻译和密钥注入。

### 4.2 路由：先自建，再外包

`provision_transit` 保持现有签名，内部按顺序选执行层：

```python
def provision_transit(db, *, order, accounts, country_code, city_name=None) -> list[TransitEndpoint]:
    for index, account in enumerate(accounts, start=1):
        vps = pick_transit_vps(db, country_code)      # 现有逻辑：匹配 group_code、未满
        if vps is not None:
            yield _provision_via_xui(db, vps, order, index, account)   # 3x-ui 路径
        elif chukou_enabled():
            yield _provision_via_chukou(db, order, index, account)     # 出口节点 API 路径
        else:
            raise TransitNotConfigured("该地区没有可用中转机，且未启用外包通道")
```

判断顺序的原因：自建机成本固定、可回收、区域可控，能自己扛就自己扛；
外包只在「没机器 / 机器满 / 机器坏」这三种情况下兜底。

### 4.3 数据模型改动（最小）

`transit_provisions` 加两个字段即可，**不动 `transit_vps`**：

| 字段 | 用途 |
| --- | --- |
| `provider` | `xui`（默认，兼容存量）/ `chukou` |
| `external_ref` | chukou 的 `business_id`，即 `{order_no}-{index}` |
| `job_id` | chukou 的任务号，轮询和排障用 |

`transit_vps_id` 对 chukou 记录留空（节点是上游分配的，本地不维护机器）。
迁移编号接 `0036`，走 `0037_transit_provider`。

`POST /provisions` 的 `business_id` 直接用 `{order_no}-{index}`，
和 `transit_provisions` 的幂等键 `(order_id, line_index)` 天然对齐——
重试时用同一个 `request_id`（`prov-{order_id}-{index}`）重发即可，不会重复开通。

### 4.4 `link_type` 由 `transit_routes` 决定

不需要业务侧单独拍板。现有 `transit_routes.group_code` 已经表达了「这个国家走哪台机器」，
直接映射到上游的两种节点：

| `group_code` | `link_type` | 节点 | 说明 |
| --- | --- | --- | --- |
| `us` | `vless` | 美国 | 北美/欧洲落地 |
| `hk` | `subscription` | 香港 | 东南亚/南非落地 |

这样新增国家只改 `transit_routes` 一行，不用改代码，和 3x-ui 路径的行为一致。

### 4.5 实现要点

1. **同步阻塞**。`wait_job` 最长 5 分钟，而 `provision_transit` 现在跑在采购的同一个后台线程里。
   要么把 `pending_transit` 做成真正的状态机（提交后立刻返回，定时任务推进），
   要么接受后台线程最长卡 5 分钟。**推荐前者**，顺带解决「进程重启丢轮询」。
   3x-ui 路径有同样问题（改模板要等重启），可以一起改。
2. **多线路要串行**。全站并发有上限，超了返回 `429 busy`；一个业务 5 分钟内只能保存一次
   （开通也算）。`quantity > 1` 时逐条提交、逐条等结果。
3. **失败回滚不了**。开通失败时上游会把节点释放回可分配列表（文档明确），
   但**开通成功后我们无法主动释放**。见第 6 节。
4. **失败不标 `failed`**。和现有 `TransitNotConfigured` 分支一致：IP 已经买了，
   标 failed 会诱导人工重试，重试就是再买一次 IP。只能停在 `pending_transit`。

## 5. 配置

```dotenv
CHUKOU_API_KEY=
CHUKOU_BASE_URL=https://chukou.154769.xyz/api/integration/v1
CHUKOU_ENABLED=false
CHUKOU_HTTP_TIMEOUT_SECONDS=30
CHUKOU_JOB_WAIT_SECONDS=300

```

- `CHUKOU_ENABLED=false` 时 `provision_transit` 继续抛 `TransitNotConfigured`，行为和现在一致；
  打开才走新路径。这样上线前不影响现有订单流程。
- 密钥能放后台加密就放后台（复用 `SUPPLIER_SECRET_ENCRYPTION_KEY` 那套），环境变量作为回退。

## 6. 已知缺口

| 缺口 | 影响 | 应对 |
| --- | --- | --- |
| **没有释放/退订接口** | 客户到期或退单后，节点仍被占用，我们无法主动归还 | 必须向对方书面确认：未使用/已过期节点是否计费、回收策略是什么、能否人工回收。这直接决定成本模型 |
| 没有回调，只能轮询 | 开通量大时轮询压力在我们这侧 | 定时任务批量查，不按订单起线程 |
| 无批量接口 | 批量开通只能串行，叠加 429 | 排队 + 退避，控制并发 |
| 每业务 5 分钟一次保存 | 「开完发现出口填错」要等 5 分钟才能改 | 开通前本地预校验出口（探针已有 `validate_outbound`） |
| 一业务一节点 | 做不了多节点冗余/多地区 | 需要冗余就在我们这层用多个 `business_id` 拼 |
| 换密钥即失联 | 新旧密钥业务互不可见，旧节点不释放 | 密钥轮换要当迁移项目做，不能随手换 |
| 订阅是节点级的 | 与「客户级聚合订阅」体验冲突 | 见 3.3，优先走形态 B |
| 连香港节点的是订阅地址，不是节点 | 上游可能随时改节点内容，客户被动接受 | 交付时快照一次，监测变化并告警 |

## 7. 待拍板

1. **交付形态走 A 还是 B？** 取决于第 2 节探针里订阅内容的实际格式。
   建议 vless 走 B（`parse_link` 已支持），订阅按实跑结果定。
2. **`pending_transit` 要不要改成真正的异步状态机？** 两条执行层都有同一个问题
   （xui 等重启、chukou 等 15-60 秒），一起改更划算。
3. **要先向对方确认计费和回收**（没有释放接口这件事的直接后果）：
   - 未使用的节点是否计费？
   - 客户到期后节点由谁回收、多久回收？
   - 能否人工按 `business_id` 释放？
   - 密钥轮换时旧业务怎么迁移？
   这四个答案决定外包通道能不能当长期方案，还是只能当应急。
4. **要不要先只开一个国家的外包通道做灰度？** 比如只给东南亚某国开，
   观察一周的成功率和耗时，再决定要不要扩大。
