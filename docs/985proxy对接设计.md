# 985Proxy 上游对接设计：付款后自动用余额采购

> 状态：设计方案（未实施）。2026-11-10 玖夜给的文档：<https://docs.985proxy.com/>
> 目标流程：客户下单美区住宅 IP（可选指定 IP 段）→ 付款 → 后台调 985 API 用**上游余额**下单 → 把 IP 交付给客户。
> 结论先行：**能实现**，而且比现有「全球代理」通道更完整（有预下单锁库存、有订单状态轮询、有钱包余额查询）。
> 但有 5 个硬约束必须先拍板，否则做出来会返工（见第 7 节）；另外它支持**指定 IP 段**，
> 这是个可做可不做的加分项，做了要接受一类新的失败场景（段被占完）。

---

## 1. 上游接口地图（已逐页读过文档）

网关：正式 `https://open-api.985proxy.com`，沙箱 `https://sandbox-open-api.985proxy.com`（实测可达，200 / 480ms）。
鉴权：请求头 `apikey`（账户级；通道级 ApiKey 文档标注已废弃）。状态码：`code=0` 成功，其他失败。
前置条件：**企业实名认证**，否则开放 API 用不了。

静态住宅这条线一共 13 个接口，与本项目相关的 9 个：

| 用途 | 路径 | 关键入参 | 返回要点 |
| --- | --- | --- | --- |
| 业务列表 | `POST /res_static/business_list` | — | 用途分类（Airdrop / AliExpress / Alibris…） |
| 库存查询 | `POST /res_static/inventory` | `static_proxy_type`、`purpose_web` | 按国家/城市列出 `stock`、`price`、`can_spec` |
| 计算价格 | `POST /res_static/price` | 同类参数 | 单价与总价 |
| **购买下单** | `POST /res_static/buy` | `zone`、`pay_type`、`static_proxy_type`、`time_period`、`buy_data[]` | `order_no` + `cost.pay_price`，**不直接返回 IP** |
| **预购买下单** | `POST /res_static/pre_buy` | 同上 | 预订单号（锁库存，**不扣钱**） |
| **预订单支付** | `POST /res_static/order_pay` | `order_no`、`order_type`(buy/renew) | 真正扣余额 |
| 订单结果 | `POST /res_static/order_result` | `order_no` | `status` 1未开始/2进行中/3已完成；`nodes[]` 含 `proxy_id`、`username`、`password`、`expire_time`、部署状态 |
| IP 列表 | `POST /res_static/ip_list` | `page`、`limit`、`status`、`order_nos[]` | IP:PORT + 账密 |
| 续费下单 | `POST /res_static/renew` | 同购买 | 续费单号 |
| 钱包余额 | `GET /wallet/balance` | — | `balance` / `wallet_balance` / `gift_balance` |

产品类型只有两档：`premium` = **原生**、`shared` = 广播。
—— 我们卖的「静态住宅原生 IP」对应 `premium`，这条线两边口径能对上。

## 2. 上游的六条规则（五条是硬约束，第六条是可选的加分项）

### 2.1 `city` 是必填，但我们不必让客户看到它

`buy_data[].city` 是 `required`。而本项目的目录、订单、线路全部只到国家（美国/日本/香港）。
库存接口会返回城市列表（如 `Buenos Aires`），所以**城市数据是有的，只是我们没建模**。

**2026-11-10 补充：客户可以选 IP 段（`spec_ip_segment`），这改变了城市问题的性质。**

上游有专门的号段接口 `POST /res_static/spec_ip_segment_list`：

| 项 | 值 |
| --- | --- |
| 入参 | `static_proxy_type`（必填）、`country`（必填）、`city`（必填）、`purpose_web` |
| 返回 | `data: string[]`，IP 段列表（如 `1.1.1`，是 /24 的前三段） |
| 下单传参 | `buy_data[].spec_ip_segment`，格式同上 |
| 是否支持 | 库存接口的 `can_spec` 字段：true / false |

关键发现：**号段接口本身要求传 `city`**。所以「可以选号段」不等于「不用管城市」——
城市是号段的父级参数，选段之前必须先定位城市。

于是城市从"产品概念"降级成"内部参数"：

- 客户看到的是「美国」；如果他选了号段，城市由号段反查确定；
- 如果他没选段，就按「该国有库存的城市里库存最多的那个」自动填；
- 两种情况下，`city` 都只是我们传给上游的隐藏参数，不进订单、不上官网。

这样官网的产品结构不用动，城市和号段都收在「可选高级选项」里。

### 2.2 周期只支持 30 / 60 / 90 / 180 天

文档原文：「时长 单位天 仅支持 30、60、90、180」。
本项目卖 **30 / 90 / 180 / 360**（`SELLABLE_PERIODS`）。

**360 天上游没有**。三条路：
- 官网下架 360（最简单，但少一档）
- 360 拆成 2×180 两单（成本可能变化，交付时要合并成一条线路，复杂）
- 360 打上「人工开通」，不走自动采购

### 2.3 `zone`（通道标识）必填

要先在上游后台建「静态住宅代理通道」，拿到 `zone` 标识才能下单。
通道不是账号级的，是**按通道走的**：一个 zone 对应一套通道配置。

本项目需要新增一个配置项存放 zone（可能一个，也可能 shared/premium 各一个）。

### 2.4 下单不返回 IP，必须轮询

`/res_static/buy` 只返回 `order_no` 和费用明细。IP、账号密码、到期时间要再查
`/res_static/order_result`（`status=3` 已完成才拿到 `proxy_id/username/password/expire_time`），
或 `/res_static/ip_list`。

也就是说**采购天然是异步的**，不可能在客户点击付款的同一个 HTTP 请求里完成。

### 2.5 下单直接扣上游余额

`pay_type=balance` 意味着采购成功即扣钱，**没有二次确认**。
这是资金风险最高的一点：一旦程序重复下单，就是真金白银。

### 2.6 可选号段是加分项，但会引入新的失败场景

支持选号段的产品力很实在——做 TikTok、支付、电商的客户经常指定「要 ISP 段，不要机房段」，
这正好是你之前强调的「原生 / 住宅 / 静态 / 独享是四个不同属性」的落地方式。

但要注意三件事：

1. **号段是消耗品**。某个 /24 段放完就没了。今天查到的列表，客户明天付款时可能已经没位置。
2. **不能自动改选**。如果客户指定 `1.1.1` 而它被占完，自动给他换个段，等于交付了客户没要的东西。
   正确处理是：采购失败 → 退款 → 提示改选，不做静默替换。
3. **同步成本**。号段要按 (类型, 国家, 城市) 逐个查，34 国 × 多城市会打爆接口。
   只同步「在售且 `can_spec=true`」的国家，且每国只取库存 Top 3 的城市。

## 3. 设计：三段式状态机

核心思路：**客户订单和上游采购单解耦**。客户只看到自己的订单，采购是内部另一条流水，
失败可以重试、可以退款，不影响客户订单的状态语义。

```
客户订单（orders）                    采购单（procurements，新增）
─────────────────                    ──────────────────────────
pending_payment                       —
     │ 支付成功（回调/余额扣款）
     ▼
paid                                 pending ──► 调 /res_static/buy
     │                                            │
     │                               success ◄────┤ code=0，拿到 order_no
     │（等交付）                        │         │
     ▼                                 │      failed ──► 重试（≤3 次）
delivered ◄── 写回 IP/账密/到期日 ─────┘                │
     ▲                                              └──► 最终失败 → 退款
     └─ 轮询 /res_static/order_result（status=3）
```

关键设计点：

**① 触发点放在「支付成功」，不是「下单」**

客户没付钱就去上游买，等于白送。所以：
- 客户下单 → 只落本地单，不碰上游
- 支付成功（余额扣款成功 / 在线支付回调 / 管理员确认收款）→ 触发采购

**② 采购在后台任务里跑，不在请求里**

新增 `procurement_dispatch` 任务（每分钟），扫 `paid` 且无采购单的订单 → 建采购单 → 调上游。
另一个 `procurement_poll`（每分钟）轮询进行中的采购单，`status=3` 就把 IP 写回客户线路。

理由：上游下单 + 交付可能要几十秒甚至几分钟，卡在 HTTP 里会超时、也会因为用户关页面而丢单。

**③ 幂等靠唯一约束**

`procurements.order_id` 唯一。同一笔客户订单永远只会有一条采购单。
上游 `order_no` 也存下来，重试用它查状态而不是重新下单（避免重复扣款）。

**④ 失败必须有出口**

上游失败（库存被抢、余额不足、通道异常）→ 采购单 `failed` → 客户订单**自动退款** + 通知客户和销售。
不允许「付款了但没线路，只在日志里报错」。

## 4. 两种下单时机，这是我的核心建议

### 方案 A：先付款 → 再采购（推荐）

```
客户付款成功 → 采购（余额直扣）→ 拿到 IP → 交付
```

优点：不占用上游库存；实现简单；客户没付款就不会烧钱。
缺点：付款后可能没货 → 要退款。

**为什么推荐**：静态住宅不是抢购型资源，库存通常几十到几百；
而「先锁库存」会让下单不付款的人占坑，反而更容易没货。退款虽然体验差，但概率低，
且本项目已经有退款登记和支付对账任务（`payment_reconcile`），兜底链路是现成的。

### 方案 B：先锁库存 → 再付款（更安全，但更重）

```
客户下单 → /res_static/pre_buy（锁库存，不扣钱）
客户付款 → /res_static/order_pay（扣余额）
客户超时不付 → 预订单过期释放
```

优点：付款前就确定有货，几乎不会出现「付了钱没线路」。
缺点：预订单会占用库存；文档**没写预订单的有效期**，需要问上游或实测；
       「下单不付」的人会拖住库存。

**建议**：主力用 A；如果某个国家库存常年个位数（可以在库存同步时标出来），
对这个国家自动切 B。这个「按国家切换策略」是配置项，不用改代码。

## 6. 资金安全护栏（必须有，不是可选）

自动采购直接花上游余额，一旦跑飞就是真金白银。以下五条建议全部上：

1. **幂等**：`procurements.order_id` 唯一约束 + 上游 `order_no` 复用查询，绝不重复下单。
2. **单笔上限**：单笔采购成本超过阈值（比如 ¥500）自动转人工，不自动买。
3. **每日总额**：当日累计采购金额超过上限（比如 ¥3000）自动停摆并发告警。
4. **余额水位**：定时查 `/wallet/balance`，低于阈值（比如 ¥500）告警；低于成本线自动关闭采购开关。
5. **失败自动退款**：采购失败 → 客户订单退款 + 通知，不允许静默失败。

再补一条运营习惯：**前 20 笔全部人工复核**（采购单建好但不自动支付，管理员点一下才真扣钱），
跑顺了再全自动。这比任何代码护栏都有效。

## 7. 需要玖夜拍板的五件事

### 7.1 城市与号段怎么处理？

城市本身不用客户选（它是内部参数）。真正要定的是**要不要让客户选 IP 段**：

- **A（推荐）**：客户可选号段，不选则自动分配
  - 选购页在「国家」之后加一个可折叠的「指定 IP 段（可选）」
  - 只有 `can_spec=true` 的国家才显示
  - 选了段就传 `spec_ip_segment`，没选就按库存最多的城市随机分配
  - 段被占完 → 退款 + 提示改选（不自动替换）
- B：不开放选段，全部自动分配（最简单，但丢掉一个卖点）
- C：开放选段 + 后台可锁定某些段不对外（防止好段被低价卖掉）

### 7.2 360 天怎么办？

- **A（推荐）**：官网下架 360，只卖 30/90/180
- B：360 拆 2×180（要合并交付，复杂）
- C：360 只走人工

### 7.3 下单时机用 A 还是 B？

- **A（推荐）**：付款后再采购，失败退款
- B：付款前预下单锁库存
- 或「按国家库存自动切换」

### 7.4 采购失败怎么赔？

- 原路退回余额（如果是余额支付的）
- 还是转人工处理（销售跟进）
- 我建议：**余额支付原路退回 + 在线支付登记退款 + 都通知销售**

### 7.5 是否现在就接？

需要你提供三样东西，缺一样都联调不了：
1. **企业实名认证后的账户 API Key**
2. **静态住宅通道标识 `zone`**（上游后台建通道时生成）
3. **沙箱账号**（先在沙箱跑通，再上正式环境）

## 9. 明确的判断

**能实现，且技术上不难**——985 的接口比现有「全球代理」更规范（有预下单、有订单状态、有钱包余额），
本项目的供应商抽象、快照、映射、定时任务都能复用。

**难点不在接口，在四个业务决策**：城市怎么选、360 天怎么办、失败怎么赔、要不要自动扣钱。
这四个定了，剩下是照图施工。

**不建议现在就开自动采购开关**。先同步库存和成本、把 985 作为一个「能看不能买」的通道接进来，
让运营对比两家的价格和库存，再决定哪条线走哪家。这一步没有资金风险，但能验证接口和鉴权的稳定性。
