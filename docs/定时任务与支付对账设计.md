# 定时任务与支付对账设计

> 状态：已实现（迁移 `0023_scheduled_task_runs`）
> 目标：把"必须有人点按钮"的事变成自动执行，并让执行结果可追溯

---

## 1. 为什么要有这一层

在此之前，系统里**没有任何定时器**：超时未付的订单一直挂在"待支付"，线路到期要等客户自己打开续费页才提醒，支付单过期后没有终态，人工核查队列也没有人盯。这些都不是 bug，是缺了一层"按时间做事"的机制。

设计上刻意做了两个取舍：

- **不引入新组件**。没有上 Celery / arq / APScheduler，而是复用同一个镜像多起一个进程，用 Redis 抢锁保证多副本不重复执行。少一个中间件，就少一处生产事故来源。
- **不猜外部接口**。支付平台虽有 `act=order` 查单能力，但响应字段未经沙箱验证，因此本层只做**本地对账**，不凭推测自动入账。

## 2. 任务清单

| 任务 | 周期 | 做什么 | 不做什么 |
|---|---|---|---|
| `payment_reconcile` | 15 分钟 | 过期支付单置 `expired`；统计"已付但没入账"的差异；把积压超 24h 的 `manual_review` 报给管理员 | 不改账、不自动退款、不调外部接口 |
| `wallet_audit` | 24 小时 | 只读巡检钱包账本（余额 / 流水 / 浮点副本三者是否自洽），有阻断项才发通知，按自然日去重 | 不改任何数据、不修脏账 |
| `close_expired_orders` | 30 分钟 | 关闭超时未支付的 `pending_payment` 订单并通知客户与归属销售 | 不动 `pending_confirm`（等人工确认的线下单） |
| `line_expiry_reminders` | 6 小时 | 按 7/3/1 天档位给客户发到期提醒 | 不改线路状态、不自动续费 |
| `supplier_catalog_refresh` | 6 小时 | 产品 / 国家 / 城市，各自按 TTL 判断是否需要重拉 | 不改映射、不动发布状态 |
| `supplier_quotes_refresh` | 6 小时 | 拉完整单价表 | 不下单、不自动采购 |
| `supplier_inventory_refresh` | 30 分钟 | 按国家轮转，每轮拉一批库存 | 不做全量扫描，不写 `SupplierSyncRun` |

周期在 `app/tasks/registry.py` 里集中定义，改一行即可。

## 3. 各任务的具体口径

### 3.1 关闭超时未支付订单

- 只处理 `status = pending_payment` 且 `payment_status = unpaid`、且 `created_at < now - ORDER_PAYMENT_TIMEOUT_MINUTES`（默认 1440 分钟）。
- **跳过**存在 `pending` / `manual_review` 支付单的订单——客户可能正在支付页上，关掉会造成"钱付了单没了"。
- `pending_confirm`（`contact_manager` 渠道，等销售/客服确认）**不自动关闭**，因为对公转账可能要几天。
- 关闭只改 `status = cancelled` + `cancelled_at`，不涉及资金与交付。

### 3.2 线路到期提醒

- 按"档位"去重而不是按天：剩余 5 天的线路归入 7 天档，同一档只发一次 → 任务每天跑也不会变成每天一条。
- 通知内容以 `线路 {id} 即将到期（剩余 N 天提醒）` 作为去重标记，**并且与 `GET /api/customer/renewals` 里原有的惰性提醒共用前缀**：客户先打开过续费页、或任务先跑过，都不会重复发。
- 档位由 `LINE_REMINDER_DAYS` 控制（默认 `7,3,1`）。

### 3.3 支付对账（本地）

三件事：

1. `status = pending` 且 `expires_at < now - PAYMENT_RECONCILE_GRACE_MINUTES` → 置 `expired`，让挂单有终态。
2. 差异检测：`paid` 的充值单没有对应 `wallet_transactions`；`paid` 的订单支付单没有把订单推进到 `paid/processing/completed`。
3. 积压检测：`manual_review` 超过 24 小时的笔数。

有差异时给所有启用中的管理员发一条站内通知，按自然日去重（同一天只发一条）。

> **注意**：把支付单置 `expired` 之后，如果客户真的在那之后付款，异步通知里会命中
> "订单已过期"分支转成 `manual_review`，不会丢钱，但需要人工核对。这是有意的：
> 宁可让人看一眼，也不在状态不确定时自动入账。

### 3.4 供应商数据自动刷新

`SUPPLIER_CATALOG_TTL_MINUTES` 这几项配置此前只被**读取**（判断快照是否新鲜、发布前校验），
但没有任何东西在刷新上游数据。结果是：只要运维不点"同步"按钮，数据就永久过期，
而发布目录会因为"快照已过期"被直接拒绝。三个任务补上这一环。

**目录（`supplier_catalog_refresh`）**：产品 / 国家 / 城市三步各自判断 `last_synced_at`
是否超过 TTL，只有过期的步骤才发请求。正常情况下一天只拉一次（`TTL=1440`，任务 6 小时一轮，
新鲜就跳过）。某一步失败不影响其他步骤，摘要里给出 `errors` 与 `failed_steps`；
只有**三步全失败**才把任务标成 failed。

**报价（`supplier_quotes_refresh`）**：按 `quoted_at` 判断 TTL，过期才拉完整单价表。

**库存（`supplier_inventory_refresh`）**：库存接口是**按国家**查询的，78 个国家就是 78 次请求，
不可能每 30 分钟全量扫一遍（会被上游限流，也没必要）。所以做**轮转**：

- 候选国家来自已同步的 `supplier_regions`；
- 按上次查询时间升序排序，**从没查过的排最前**，每轮只取 `SUPPLIER_INVENTORY_BATCH_SIZE`（默认 10）个；
- 摘要里的 `pending` 是还没轮到的国家数，可以用来估算多久能转完一圈；
- 单个国家失败只记 `failed_countries`，不影响同批其他国家；全批失败才标 failed。

> 这意味着**大部分国家在任何时刻都不是 `fresh`**。这是刻意的：库存是"下单前先查一下"的
> 信号，真正下单走的是 `POST /admin/suppliers/check-inventory`（实时、单国家）。
> 批量扫描只用于资源池概览，不必追到分钟级。

#### 为什么自动刷新不写 `SupplierSyncRun`

`SupplierSyncRun.status` 是**发布闸门**：`catalog_publication_service._require_fresh`
看到某个 `sync_type` 最近一次不是 `success` 就禁止发布。自动任务一轮要拉十来个国家，
只要其中一个国家报错，就会把整个人工发布流程卡死，而运维根本不知道该修哪个国家。

所以自动刷新**只更新快照时间**（`last_synced_at` / `checked_at` / `quoted_at`），
让数据重新变"新鲜"，执行结果记在 `scheduled_task_runs`（后台 `/admin/tasks` 可见）。
人工同步仍然照旧写 `SupplierSyncRun`，两个通道互不覆盖。

#### 快照保留

库存快照每轮**追加**而不覆盖，一轮 10 个国家 × 若干城市就是几十行。因此任务里带一步清理：
删除超过 `SUPPLIER_SNAPSHOT_RETENTION_DAYS`（默认 7 天）的快照，但**已被
`catalog_publications` 引用的快照永不删除**（否则破坏外键，也会让历史发布记录失去依据）。

#### 未配置 API Key 时

`has_configured_api_key` 为假时任务直接返回 `{"skipped": "未配置供应商 API Key"}`，
状态仍为 success——这不是故障，是供应商接入还没开。开发环境和测试库不会有噪音失败。

代价是"跳过"不报警，所以生产环境必须保证 worker 容器拿得到凭据：后台录入的密文优先，
环境变量回退值 `GLOBAL_PROXY_API_KEY` 由 `docker-compose.prod.yml` 同时注入 api 与 worker；
只注入 api 的话，定时刷新会每轮安静跳过，`/admin/tasks` 里只看得到成功。

### 3.5 `wallet_audit`：把账本巡检变成日常动作

巡检本身在 `app/services/wallet_audit_service.py`（只读，见
[金额一致性现状与迁移方案](金额一致性现状与迁移方案.md)），任务是它的调度壳：

- **只在有阻断项时发通知**。提示项（浮点副本分叉、孤儿余额）在迁移过渡期是常态，
  天天推只会训练管理员忽略通知；
- 通知按自然日去重（marker `巡检日期 YYYY-MM-DD`），账没修好第二天继续提醒；
- 通知内容列前 5 条明细，其余归"另有 N 项"，避免一条通知刷满屏；
- 每轮计数写进 `scheduled_task_runs`，后台 `/admin/tasks` 能看到 `blocking` 是否长期非 0。

它不修账：脏账怎么修是人的判断，自动"修平"只会把证据一起抹掉。

## 4. 幂等、并发与可观测

| 关注点 | 做法 |
|---|---|
| 多副本重复执行 | Redis `SET lock:sched:{task} <token> NX EX`；释放时用 Lua 比对 token，避免误删他人的锁 |
| Redis 不可用 | **跳过本轮**，不降级为无锁执行（宁可少跑一轮，也不要重复入账） |
| 单实例重复执行 | 每个任务自身按业务键去重（订单状态、通知标记、支付单状态） |
| 执行记录 | 每次运行写一行 `scheduled_task_runs`（任务、状态、耗时、摘要 JSON、错误） |
| 失败可见 | 调度进程记 `logger.exception` 全栈；流水 `status = failed` + `error`；管理后台可查 |
| 轮询 | `SCHEDULER_POLL_SECONDS`（默认 60）决定检查间隔，任务的 `interval_minutes` 决定实际频率 |

任务流水用**独立会话**落库，避免任务事务回滚时把日志一起回滚掉。

## 5. 部署

`docker-compose.prod.yml` 新增 `worker` 服务：同一个镜像，命令 `python -m app.scheduler`，`read_only` + `tmpfs /tmp`，依赖 `postgres` / `redis` 健康。

```bash
docker compose -f docker-compose.prod.yml up -d worker
docker compose -f docker-compose.prod.yml logs -f worker
```

环境变量（都已在 `Settings` 里校验）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `SCHEDULER_ENABLED` | `true` | 置 `false` 时调度进程启动后立即退出 |
| `SCHEDULER_POLL_SECONDS` | `60` | 轮询间隔，不得小于 10 |
| `TASK_LOCK_TTL_SECONDS` | `900` | 任务锁有效期，不得小于 60 |
| `ORDER_PAYMENT_TIMEOUT_MINUTES` | `1440` | 订单支付超时时长 |
| `LINE_REMINDER_DAYS` | `7,3,1` | 到期提醒档位，1–90 天 |
| `PAYMENT_RECONCILE_GRACE_MINUTES` | `5` | 支付单过期后的宽限，避免与回调抢同一个订单 |
| `SUPPLIER_INVENTORY_BATCH_SIZE` | `10` | 每轮刷新多少个国家的库存，1–50 |
| `SUPPLIER_SNAPSHOT_RETENTION_DAYS` | `7` | 库存/报价快照保留天数，被发布记录引用的不受影响 |

命令行（不依赖容器，直接跑在当前环境）：

```bash
cd backend
python -m app.scheduler --once                                # 跑一轮
python -m app.scheduler --once --task payment_reconcile        # 只跑一个
python -m app.scheduler                                       # 常驻
```

`--once` 有任务失败时退出码为 1，可以直接接进 CI 或运维巡检脚本。

## 6. 管理后台

`/admin/tasks`（`AdminTasksView.vue`，导航项"定时任务"）：

- 展示任务清单、周期、上次执行时间与状态；
- 「立即运行」触发一次（`POST /api/admin/task-runs/{name}/run`），同步返回摘要；
- 执行流水表格：时间、任务、状态、耗时、触发来源、摘要（JSON 拆成标签）、错误。

接口只读流水，唯一的写操作是手动触发；三个端点都要求 `admin` / `super_admin`。

## 7. 明确未做

- **远程查单对账**（`act=order`）：需要先拿服务商沙箱确认响应字段、金额单位与状态取值，验证后再接入，并且只允许"金额一致 + `TRADE_SUCCESS`"才入账。
- **自动退款 / 自动补单**：涉及资金，保持人工。
- **供应商全量库存扫描**：库存接口按国家查询，全量扫会被限流，因此只做轮转（见 §3.4）。
- **任务失败的外部告警**（邮件/webhook）：目前只有站内通知与日志。
- **管理员页面之外的 UI**：销售端不需要看这些。

## 8. 测试

`backend/tests/test_scheduled_tasks.py`（8 个用例）：

- 关单：超时关闭、未超时不关、付款中的跳过、`pending_confirm` 不动、通知到客户；
- 提醒：按档位只发一次、二次运行零发送、与旧惰性提醒去重；
- 对账：过期支付单置 `expired`、三类差异计数、同日只通知一次、已推进订单不计差异；
- 执行器：成功写流水、未知任务失败、处理器抛异常时仍写 `failed` 流水；
- 鉴权：三个端点未登录均 401。

`backend/tests/test_supplier_tasks.py`（13 个用例，用假适配器，不打真实上游）：

- 目录：首轮三步全拉、5 分钟后全部跳过、超过 TTL 重拉、`force` 绕过 TTL；
- 目录容错：城市失败不影响产品与国家落库、三步全失败才 raise；
- 库存轮转：一次只拉一批、下一轮只补剩余国家、全部新鲜后零请求、同时过期时取最早的那个；
- 库存容错：单国失败隔离、全批失败才 raise、目录未同步时优雅跳过；
- 清理：过期快照被删，但被发布记录引用的那条保留；
- 报价：新鲜跳过、过期重拉；
- 接线：注册表处理器正确把 `SUPPLIER_INVENTORY_BATCH_SIZE` 注入任务，且目录排在库存之前。
