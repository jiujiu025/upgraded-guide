# 金额一致性：现状核查与迁移方案

> 状态：**读口径已切到钱包（Step 1）+ 副本写入加校验（Step 2）已落地**
> （`app/services/wallet_audit_service.py`、`app/services/wallet_migration_service.py`、
> `app/services/customer_view.py` + 两个 CLI）
> 停写副本、改列名、删列（Step 3-4）尚未执行。
>
> **上线顺序**：生产先跑 `audit_wallet_ledger.py`（阻断项必须 0）→ 再跑
> `migrate_customer_balance_to_wallet.py --apply`（把孤儿余额补进钱包）→ 最后才发布本版代码。
> 顺序反了会让那批客户的余额在界面上直接变 0。

## 1. 一句话结论

余额在系统里有**三个表示**，其中两个是可写的，长期必然分叉。但**分叉不等于现在就已经错了**——所以第一步不是改类型，而是先能**证明**账是平的。这一步已经做完了。

---

## 2. 现状：三处表示，两个可写

| 表示 | 类型 | 位置 | 谁在写 | 谁在读 |
|---|---|---|---|---|
| `wallet_accounts.balance_cents` | `BigInteger`（整数分） | 钱包表 | `apply_wallet_delta` | `/wallet`、财务页、客户 360 |
| `wallet_transactions` | 明细账（整数分） | 流水表 | `apply_wallet_delta` | 客户 360 流水、财务页 |
| `customers.balance` | `Float`（浮点元） | 客户表 | **仅** `wallet_service.py`（`after / 100`） | 仅巡检（业务路径已不再读，见 Step 1） |

关键事实（都是读代码确认的，不是推测）：

1. **`customers.balance` 只有一个写入点**，就是 `wallet_service.apply_wallet_delta` 末尾。没有第二处代码会改它。
2. **它曾在两处被当作"兜底"读**（`customer_admin_routes.py` 客户列表 / 客户详情，均发生在钱包账户不存在时）。
   Step 1 已把这两处改为按 0 处理，并把 6 个 `CustomerOut` 端点的余额取值统一到 `customer_view`。
3. **它现在唯一的读者是巡检**（`wallet_audit_service` 的 `customer_float_drift`），用来在过渡期观察副本是否还在被写坏。
   Step 3 停写之后，这一项会持续报警，届时用 `--ignore customer_float_drift` 关掉。

## 3. 两个我先前判断错的点，这里更正

写方案前我原本准备了两条"金额 float 必然出问题"的论据，核查后发现**都不成立**，如实记下来，避免后面按错的理由动刀。

### 3.1 「float 会累积漂移」——不成立

`customers.balance` 不是累加出来的，而是**每次从整数分重新赋值**（`after / 100`）。既然是"赋值"不是"累加"，就不存在误差随笔数增长的问题；单次 `分/100 → float → round(*100)` 的往返在 2^53 范围内是精确的。

真实风险不是漂移，而是**双真相源**：两个字段可以各自被改，谁对说不清。

### 3.2 「代码里 `int(balance*100)` 会少 1 分」——不成立

我实测过：对 1~200000 分逐值验证，用 `int(v*100)` 取整会有 **9174 个值（4.6%）少 1 分**（例：`1.15*100 = 114.999…` → 114）。但现有代码**两处都用 `round()`**，没有一处用 `int()`，所以这个 bug 实际不存在。

结论：**不要为了"修精度"去迁移**。迁移的理由只有一条——**同一笔钱有两个可写的家**。

## 4. 真实风险（这三条才是要解决的）

### 4.1 兜底路径会"凭空造钱"（**已修，Step 1**）

钱包账户不存在时，客户列表/详情会拿 `customers.balance` 顶上。这条路径意味着：**一个没有钱包的客户，在财务页能显示出余额，但在钱包页是 0**。两个页面各说各话。现在两边都按钱包取值，缺失即 0。

### 4.2 缺钱包账户的余额无法核销（**已提供补建脚本，需在生产执行**）

`orphan_customer_balance` 这类客户（有非零 `balance`、没有 `wallet_accounts` 行）一旦要消费，`apply_wallet_delta` 会**新建一个余额为 0 的钱包**，然后判定"余额不足"。也就是说：**显示的余额花不出去。**

### 4.3 收付款与钱包之间没有对账

`PaymentOrder` 标了 `paid`，理论上钱包一定有一条对应流水（充值 +、余额支付 −、退款 +）。但代码里没有任何地方校验这件事。一旦某次事务部分失败、或有人手工改状态，就会变成"钱收了但没入账"，而**没有任何机制会发现**。

## 5. 巡检工具（已落地）

不修数据，只出报告。这是迁移的**验收基线**：迁移前后各跑一次，阻断项必须都是 0。

```bash
cd backend
python scripts/audit_wallet_ledger.py                    # 人看
python scripts/audit_wallet_ledger.py --csv wallet.csv   # 导给运营
python scripts/audit_wallet_ledger.py --limit 200        # 每类最多列 200 条
```

| 级别 | 检查项 | 含义 |
|---|---|---|
| **阻断** | `balance_vs_ledger` | 账户余额 ≠ 该账户流水累计 |
| **阻断** | `ledger_chain` | 相邻流水首尾不接，或单条 `期初+金额≠期末` |
| **阻断** | `missing_wallet_transaction` | 已付款支付单在钱包里找不到对应流水 |
| **阻断** | `missing_refund_transaction` | 余额渠道退款登记没有对应退回流水 |
| **阻断** | `negative_balance` | 余额为负（说明绕过应用改过库） |
| 提示 | `customer_float_drift` | 浮点副本与钱包余额不一致 |
| 提示 | `orphan_customer_balance` | 客户有余额但没有钱包账户 |
| 提示 | `ledger_opening` | 最早一条流水期初不为 0（余额没有来源） |

**退出码**：`0` = 无阻断项；`1` = 有阻断项。可直接接到上线前检查。

已用 11 个用例覆盖：健康账本零误报、每种故障都能被单一识别、在线支付与已退款单不误报。实测在一个构造了三类问题的库上输出：

```
[阻断] 支付单在钱包里找不到对应流水：1 项
    payment#2  BAL-LOST-1（order_payment/balance，paid）金额 50.00，余额支付应在钱包扣款：期望 -50.00，实际 无流水
[提示] 客户浮点副本与钱包余额不一致：1 项
    customer#3  分叉客户 浮点副本 99.99 ≠ 钱包权威余额 100.00，差 -0.01
[提示] 客户有余额但没有钱包账户：1 项
    customer#2  历史客户 冗余余额 88.88，但没有钱包账户（user_id=None），需在迁移时补建钱包
```

## 6. 迁移路径（5 步，每步可独立回滚）

> 目标：**钱包表是唯一真相源，`customers.balance` 从"可写副本"降级为"派生展示值"，最后删列。**
> 全程**不动 API 字段名**（`CustomerOut.balance` 保持 `float`），前端零改动。

### Step 0（已完成）巡检基线

上线前在生产库跑一次，把 `--csv` 结果归档。**阻断项 > 0 就不许往下走**，先人工对账修平。

### Step 1 读切换：所有余额读钱包（**已实现**）

改动：

- 新增 `app/services/customer_view.py`，作为客户余额对外的唯一取值口：
  ```python
  def balance_cents_of(db, user_id) -> int:      # 单个；无账号 / 无钱包 → 0
  def wallet_cents_map(db, user_ids) -> dict     # 批量，键为 user_id，避免 N+1
  def customer_view(customer, cents) -> CustomerOut
  def customer_views(db, customers) -> list[CustomerOut]
  ```
- 6 个返回 `CustomerOut` 的端点（`routes.py` 的 `list_customers / create_customer /
  get_customer / customer_me / sales_customers / admin_assign_customer`）改为走上面这层，
  不再由 ORM 的 `customer.balance` 直接填充。
- `customer_admin_routes.py` 两处 `round(customer.balance * 100)` 兜底改为 `0`
  （无钱包即 0，与 `/wallet` 一致）。

验证（`tests/test_customer_balance_read.py`，8 用例）：

- 浮点副本被改坏成 99.99、钱包 100.00 时，列表/详情/自助页都返回 100.0；
- 无钱包客户返回 0.0，管理端 `balance_cents` 也是 0；
- 客户列表的余额与 `/wallet` 的 `balance_cents` 对得上（同一个数）。

回滚：纯代码改动，revert 即可。

### Step 2 双写加校验（**已实现**）

`apply_wallet_delta` 继续写 `customer.balance`，但写后校验往返精度：

```python
customer.balance = after / 100
if int(round(customer.balance * 100)) != after:
    raise ValueError(f"余额副本精度异常：{after} 分写成 {customer.balance}")
```

行为不变，只是让"副本写坏"当场报错而不是攒到月底。观察一段时间无异常再进 Step 3。

### Step 3 停写副本

删掉 `apply_wallet_delta` 里那两行写 `customer.balance` 的代码。此后该列只保留历史值。

注意事项：

- 此步之后巡检的 `customer_float_drift` 会**持续报警**（旧值不再更新）。这是预期的，
  因此 Step 3 上线时同步把该项从"提示"改为"忽略"或直接跳过——具体做法：巡检加 `--ignore customer_float_drift`，
  而不是改判定逻辑（保留能力，迁移完还能用）。

### Step 4 列降级与删除

分两次发布，避免不可逆：

1. **第一次**：迁移 `0024_rename_customer_balance.py` —— `ALTER TABLE customers RENAME COLUMN balance TO balance_deprecated`。
   同时把 ORM 字段改为 `balance_deprecated`（`CustomerOut.balance` 已由 Step 1 从钱包取值，不受影响）。
   观察两周，出问题就 rename 回来。
2. **第二次**：迁移 `0025_drop_customer_balance.py` —— 删除该列。

回滚：第 1 次可 `rename` 回滚；第 2 次不可回滚，所以必须在前一次稳定两周后再做。

### Step 5 补建缺失钱包（**已实现**，必须在 Step 1 之前跑完）

> 顺序不能反：Step 1 把读数切到钱包后，没钱包的客户余额会直接变成 0。
> 所以先补建钱包、让这些客户的钱真正落到钱包里，再切读取口径。

针对巡检里的 `orphan_customer_balance`，脚本已就绪（默认就是预演，不加 `--apply` 不写库）：

```bash
python scripts/migrate_customer_balance_to_wallet.py                 # 预演
python scripts/migrate_customer_balance_to_wallet.py --apply         # 执行
python scripts/migrate_customer_balance_to_wallet.py --customer-id 12 --apply
python scripts/migrate_customer_balance_to_wallet.py --csv plan.csv
```

脚本逻辑（每个客户一个事务，单个失败不影响其他）：

1. 取 `customer.balance`，转分：`round(balance * 100)`；
2. `user_id` 为空 → **跳过**（没有账号无法建钱包，是否补建账号属业务决策）；
3. 余额为负 → **跳过**（期初流水是负数会直接违反余额非负约束，只能人工处理）；
4. 钱包已存在且余额非 0 但与浮点副本不同 → **只报告不覆盖**（谁对说不清）；
5. 钱包不存在或为空 → 建 `WalletAccount(balance_cents=0)`，再用 `apply_wallet_delta`
   记一笔 `transaction_type="opening_balance"`、`idempotency_key=f"opening-balance:{customer.id}"`
   （天然幂等，重跑安全）；
6. 校验 `wallet.balance_cents == 目标值`，不等则抛错回滚该客户。

实测（含一个 123.45 元的孤儿余额）：预演 → 执行 → 重跑，第二次识别为"已迁移"、不产生重复流水；
执行后巡检的 `orphan_customer_balance` 归零，账本仍然自洽。

| 巡检：断链 / 单条不平 | 报 `ledger_chain` 且阻断 |

| 巡检：余额退款缺流水 | 报 `missing_refund_transaction` 且阻断 |
| 巡检：浮点副本分叉 | 报提示、不阻断 |
| 巡检：孤儿余额 | 报提示、计入 stats |
| 巡检：负余额 | 报阻断（用 `PRAGMA ignore_check_constraints` 模拟绕过约束写库） |
| 迁移：孤儿余额 | 计划标记待补建，金额按分取整正确 |
| 迁移：执行 | 钱包余额正确，期初流水期初/期末/金额自洽，执行后巡检仍 ok |
| 迁移：幂等 | 连做两次只产生一条期初流水 |

| 读口径：无钱包客户 | 返回 0，管理端 `balance_cents` 也是 0 |
| 读口径：与 `/wallet` 一致 | 客户列表余额 ×100 == `/wallet` 的 `balance_cents` |
| 副本写入：往返精度 | 写入后 `round(balance*100)` 还原为同一整数分 |

已有 28 个用例（巡检 11 + 迁移 9 + 读口径 8）。

## 8. 明确不做

- **不把 `orders.amount / total_amount / unit_price` 一起迁**。它们是**下单时的价格快照**，
  已由 `pricing_service` 用 Decimal 算好后落库，且收款口径另有 `PaymentOrder.amount_cents`（整数分）。
  单独一轮做，避免和余额迁移混在一起、出问题分不清是哪边。
- **不改 `CustomerOut.balance` 的字段名与类型**。前端在用，改了要连带发版，而收益为零。
- **不引入新的账务表**。现有 `wallet_transactions` 已经是完整的复式记账雏形（期初/期末/幂等键齐全），
  缺的是校验，不是结构。
- **不在迁移里顺手改退款/充值流程**。先把"能发现错"做到位，再谈"少出错"。

## 9. 与其它方案的关系

- 定价收敛（`docs/定价收敛实施方案.md`）解决的是**卖出价**，本文解决的是**收到的钱**，两者独立。
- 定时任务（`docs/定时任务与支付对账设计.md`）里的 `payment_reconcile` 做的是**支付单状态**对账；
  本文的钱包巡检是**金额**对账。两者互补。
- 巡检已接进调度：`wallet_audit` 任务每天跑一次，有阻断项才给管理员发通知（按自然日去重），
  没阻断项只记一条 `scheduled_task_runs`。也就是说上线后不需要有人记得跑 CLI——
  CLI 只在**迁移前后手工验收**时用。
