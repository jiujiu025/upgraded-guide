# 线路健康：客户线路与面板入站（实现说明）

> 原来的「线路健康」页是演示原型（数据来自 `frontend/src/mocks/health.js`，页面自己标着
> "演示数据"）。本文说明改成真实数据后的口径。

## 1. 为什么不能只看 Node

`/health/lines` 返回的是 `Node`（出口），而同一个出口可能卖给多个客户。管理员要看的是
「**哪条线、谁的、哪个销售在跟**」，所以新接口从 `CustomerLine` 出发再 join 回去：

```
CustomerLine
  → Customer（客户名、sales_id）
  → User（销售名）
  → Product（产品名、resource_category → 产品线）
  → Order（订单号、地区快照）
  → Node（入口地址、健康状态、延迟）
  → TransitProvision → TransitVps（入站端口、出站 tag、出口 IP、面板名）
```

## 2. 两个视图

| 视图 | 数据来源 | 能回答什么 |
| --- | --- | --- |
| 客户线路 | 数据库 `CustomerLine` | 这条线是谁的、哪个销售、连哪个入口、出口 IP、走哪台面板、健康状态 |
| 面板入站 | 实时问 3x-ui（`inbounds/list` + `POST /panel/xray/`） | 面板上**所有**入站，包括人工直接建的、系统里没有记录的 |

面板入站会解析 Xray 路由规则，把 `inbound-{port}` 对应的 `outboundTag` 找出来，再从出站里
读出口地址与端口，于是每条入站都能显示「入口 → 出站 → 出口」。系统内的中转记录按
`(transit_vps_id, inbound_id)` 匹配，匹配不到就是「未关联客户」。

## 3. 接口

```
GET  /api/admin/health/overview                 汇总：线路数/正常/离线/待检测/面板数
GET  /api/admin/health/customer-lines           分页 + sales_id/customer_id/line_code/country/health/keyword
POST /api/admin/health/customer-lines/check     {line_ids: []} 或 {all: true}，按节点去重后并发探测
GET  /api/admin/health/transit-inbounds         ?vps_id=，不传则所有启用中的面板
POST /api/admin/health/transit-inbounds/check   {vps_id?, ports?: [], include_outbound?}
```

## 4. 检测口径与边界

- 检测是 **TCP 连通性探测**（连接入口 `connect_host:port`，超时 3 秒），不改任何配置；
- 8 线程并发，避免 100 条线路串行探测卡 5 分钟；SQLAlchemy 会话只在主线程用，
  网络 IO 丢进线程池；
- 同一节点被多条线路引用时只探测一次（客户线路按 `node_id` 去重）；
- 掉线会开故障事件并通知受影响的客户与销售（复用原有 `apply_result`）；
- **出站不一定能测准**：上游是代理网关（`proxy.quanqiudaili.com:5001`）时，裸 TCP 能连上
  不代表代理可用；页面只承诺"入站端口可达"，不把出站 TCP 结果当成业务可用性。

## 5. 前端

`HealthView` 按角色分流：管理员渲染 `AdminHealthPanel`（真实数据），客户与销售仍是原视图
（原型），后续再接。

页面能力：

- 顶部统计按**客户线路**计数，不按节点；
- 客户线路 tab：销售/产品线/国家/状态下拉 + 关键词搜索（客户、订单号、IP、出站 tag、面板名），
  状态 chip 与下拉联动，计数不随状态筛选收缩；
- 列表列：客户(销售) / 产品(订单) / 入口 → 出口 / 中转(面板·端口·出站 tag) / 健康 / 延迟 / 到期；
- 单条检测、检测当页、全量检测三种粒度；
- 面板入站 tab：按面板筛选，展示入站 id/端口/备注、出站 tag/出口、对应客户(销售)，
  支持整台面板的入站端口检测；面板连不上时逐台报错，不阻塞其它面板。
