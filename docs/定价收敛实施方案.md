# 定价收敛实施方案（修订版 · 2026-11-08）

> **口径变更**：定价规则由「长周期打折」改为「**严格线性、无折扣**」。
> 半年 = 月价 × 6，一年 = 月价 × 12，季付 = 月价 × 3。折扣功能不在本期范围，后续独立设计（接入点见 §11）。
>
> 目标：同一个商品、同一个周期，**全站只有一个价格**。
> 工期：2 个工作日｜风险：中（不涉及金额类型迁移，不删列）
> 前置：M0 止血完成（测试 98 绿）、CI 就绪

---

## 0. 一句话方案

**`RetailPriceRule` 的「30 天价」是唯一真相源；90/180/360 天价一律由它按 `月价 × 周期数` 派生，不再查表、不再乘系数、不再有折扣字段。**

```python
unit_price = 月价 × (billing_days / 30)
```

比上一版方案简单得多——因为「没有折扣」这件事，把最大的复杂度（周期价矩阵）直接消掉了。

回滚方式：把商品的 `resource_category` 置空，立刻退回旧的固定价逻辑（商品粒度，秒级生效，不用发版）。

## 1. 更正上一版的错误结论

上一版文档写「官网长周期系统性卖贵 10%」。**这个结论是错的**，原因是我把价目表当成了真相源。实际情况是：

> **官网和价目表各自打了一套不同的折扣，谁贵谁便宜取决于分类。**

以四个分类各取一个代表 SKU（数据来自 `retail_price_seed.py`，可复现）：

| 分类 | 代表 SKU | 月价 | 官网现价 180天 / 360天 | 价目表现值 180天 / 360天 | 谁更高 |
| --- | --- | --- | --- | --- | --- |
| 静态住宅 | `static_residential / HK` | 60 | 330 / 600 | 300 / 540 | 官网高 10% |
| 原生住宅 | `static_residential_native / US` | 60 | 330 / 600 | 300 / 540 | 官网高 10% |
| 静态数据中心 | `static_datacenter / US` | 45 | 247.5 / 450 | 230 / 405 | 官网高 7.6% |
| 运营商 ISP | `static_residential_isp / AE` | 80 | 440 / 800 | **480 / 960** | **价目表高 9.1%/20%** |

所以上一版「客户看到两个价」的判断成立，「官网更贵」的判断不成立。修正后的正确表述是：

**两条链路的分歧不是方向问题，是「两份折扣表」问题——官网用 `{6:5.5, 12:10}`，价目表用各分类自己的一套倍数。**

价目表共 **238 个 SKU × 4 个周期档 = 952 行**。按「月价 × 3 / 6 / 12」校验：

## 3. 这个口径下的价格影响（必须提前通知运营和客户）

规则改成线性，**两个渠道都会涨**，且方向一致（终于一致了）：

| 渠道 | 180 天 | 360 天 | 备注 |
| --- | --- | --- | --- |
| 官网 C 端 | ¥330 → **¥360**（+9.1%） | ¥600 → **¥720**（+20%） | `{6:5.5}`→`×6`、`{12:10}`→`×12` |
| 管理员资源池 | 视分类 **+0% ~ +20%** | 视分类 **+0% ~ +33.3%** | ISP 分类零变化，住宅类涨幅最大 |
| 90 天 | **从"买不到"变成可售** | — | ¥60 → 3 × 60 = **¥180** |

三件必须做的事：

1. **老客户续费按新价**——订单已存快照，历史单不回溯，但续费单会按新价生成。建议 180/360 天档给一个过渡期（例如提前 7 天公告）。
2. **销售话术统一**——以后只有一个价，销售报价 = 官网价，不再有"内部价更便宜"的灰色空间（ISP 分类现在是反过来的，销售报价 480 比官网 440 贵，客户一比价就穿帮）。
3. **涨价不是本方案引入的**——是「取消折扣」这个决策的结果。方案只负责让价格**可解释、可复现、唯一**。

## 4. 目标契约

```
                    ┌──────────────────────────────┐
                    │  RetailPriceRule (30 天档)     │  ← 唯一真相源
                    │  (分类, 国家) → 月价            │     后台「零售价」页写
                    └──────────────┬───────────────┘
                                   │ 只读
                    ┌──────────────▼───────────────┐
                    │  pricing_service               │  ← 唯一取价入口
                    │  monthly_price_of()            │     任何地方要价格都走这里
                    │  unit_price(days) = 月价×n     │
                    │  periods_of() / quote()        │
                    └──┬──────────┬──────────┬──────┘
                       │          │          │
                  官网产品列表   下单/续费   后台商品页
                  (periods)   (quote)    (只读展示)
```

四条铁律：

1. **只有月价能配**——90/180/360 天价不存在"配置"这个概念，一律算出来
2. **任何周期选项必须来自后端**——前端不许出现 `[base, base*6, base*12]` 这类硬编码
3. **不存在折扣字段**——API 不再返回 `discount`，前端不再渲染"折"
4. **`Product.price` 只写不读**——由月价回写，只用于列表页展示"¥60 起"

## 5. 关键设计决策

### 决策 1：加一个连接键 `Product.resource_category`

`Product` 现在只有中文 `product_type`（"独享静态住宅（运营商原生）"），价目表用的是 code（`static_residential_native`）。新增 `Product.resource_category`（`String(50)`，可空，带索引），连接路径：`Product.region_id → Region.country_code` + `resource_category`。

**不拆 `ProductPrice` 子表**：2 天工期不值得动表结构，而且"周期价由月价派生"之后，本来就没有矩阵需要存了。

### 决策 2：`resource_category IS NULL` = 固定价商品，老逻辑零影响

系统里确实有不该走价目表的商品，例如种子数据的「香港直播专线 ¥199/30天」（`seed.py:28`），它是线路套餐，没有国家×周期的矩阵。

| `resource_category` | 定价模式 | 行为 |
| --- | --- | --- |
| 有值 | **线性派生** | 月价 × 周期数；只允许 30 的整数倍 |
| 为空 | **固定价（legacy）** | 保留原 `PERIOD_FACTORS`，完全不变 |

老数据和直播专线**零影响**，且这个字段天然就是回滚开关。

### 决策 3：价目表里的 90/180/360 行**降级为休眠数据**

库里那 453 行非线性的长周期价，改价后不再参与报价。处理原则：

- **不删**（未来折扣功能可能要复用这批"渠道价"，删了要重新录）
- **不读**（`quote()` 只读 30 天档）
- **后台标灰**：零售价页把非 30 天档显示为"由月价自动计算：¥360"，不可编辑，旁边一行小字说明"当前不打折"
- **数据治理脚本**（Step 8）可以 `--dry-run` 出一份"这些行已失效"的清单给运营看，`--apply` 时才把它们刷成线性值（纯清洁，不影响报价）

这是本方案最重要的取舍：**先让机制单一，再让数据干净**。顺序反了会变成一次性大改价，没法灰度。

### 决策 4：可售周期由后端下发

`GET /api/public/products` 每个商品带 `periods: [{billing_days, unit_price}]`。周期档位来自常量 `SELLABLE_PERIODS = (30, 90, 180, 360)`，价格全部算出来。

副作用（正面）：**90 天档立即变成可售**，运营不用再看着"配了价却卖不出去"的零售价页发愁。

### 决策 5：折扣字段直接删掉，不保留

`OrderPreviewOut.discount` 现在返回 `5.5/6 = 0.9167`，前端渲染成 **"0.9167 折"**（差 10 倍）。既然没有折扣功能，**这个字段整体删除**，比"置 None 后再兼容"更干净——留着一个永远为 1 的字段，下次一定有人拿它算错。

替代展示：结算页改成「周期单价 ¥360 / 90 天」「折合 ¥4.00 / 天」。真实、可验证、不用编。

### 决策 6：这一步不动金额类型

`Float` → 整数分的迁移排在 D5 独立做。本方案内部用 `Decimal` 计算、出口转 `float` 保持现有契约，避免把两件事耦在一起。

### Step 2　新建 `app/services/pricing_service.py`（2 小时）

```python
"""价格唯一入口：所有对外报价必须经过这里。

口径：严格线性，无折扣。
    周期单价 = 月价 × (billing_days / 30)
折扣功能不在本期范围，届时在 quote() 里加一层调整，不动本文件结构。
"""
from decimal import Decimal, ROUND_HALF_UP

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models import Product, Region, RetailPriceRule

BASE_PERIOD_DAYS = 30
SELLABLE_PERIODS = (30, 90, 180, 360)          # 可售档位，全部由月价派生
LEGACY_PERIOD_FACTORS = {1: Decimal("1"), 6: Decimal("5.5"), 12: Decimal("10")}
CENT = Decimal("0.01")


class PricingError(ValueError):
    """价格不可用（缺月价、周期不支持）。路由层转 422。"""


def product_country_code(db: Session, product: Product) -> str:
    region = db.get(Region, product.region_id)
    if not region or not region.country_code:
        raise PricingError("商品缺少国家编码，无法按价目表报价")
    return region.country_code.strip().upper()


def monthly_rule(db: Session, product: Product) -> RetailPriceRule | None:
    """只取 30 天档——它是唯一真相源。"""
    if not product.resource_category:
        return None
    return db.scalar(select(RetailPriceRule).where(
        RetailPriceRule.resource_category == product.resource_category,
        RetailPriceRule.country_code == product_country_code(db, product),
        RetailPriceRule.billing_days == BASE_PERIOD_DAYS,
    ))


def monthly_price_of(db: Session, product: Product) -> Decimal:
    rule = monthly_rule(db, product)
    if not rule:
        raise PricingError("该商品尚未配置月价，请联系运营")
    return Decimal(str(rule.unit_price)).quantize(CENT, rounding=ROUND_HALF_UP)


def unit_price_for(base: Decimal, billing_days: int) -> Decimal:
    """线性派生。90天=3×，180天=6×，360天=12×。"""
    if billing_days <= 0 or billing_days % BASE_PERIOD_DAYS:
        raise PricingError("使用周期必须是 30 天的整数倍")
    periods = Decimal(billing_days) / Decimal(BASE_PERIOD_DAYS)
    return (base * periods).quantize(CENT, rounding=ROUND_HALF_UP)


def periods_of(db: Session, product: Product) -> list[dict]:
    """该商品所有可售周期及单价；固定价商品只返回自身周期。"""
    if not product.resource_category:
        return [{
            "billing_days": product.billing_days,
            "unit_price": round(float(product.price), 2),
        }]
    try:
        base = monthly_price_of(db, product)
    except PricingError:
        return []                                  # 缺月价 → 前端置灰
    return [
        {"billing_days": days, "unit_price": round(float(unit_price_for(base, days)), 2)}
        for days in SELLABLE_PERIODS
    ]


def quote(db: Session, product: Product, quantity: int, billing_days: int) -> tuple[Decimal, Decimal]:
    """返回 (周期单价, 合计)。"""
    if quantity < 1:
        raise PricingError("数量必须大于 0")
    if product.resource_category:
        if billing_days not in SELLABLE_PERIODS:
            raise PricingError(f"仅支持 {'/'.join(map(str, SELLABLE_PERIODS))} 天周期")
        unit = unit_price_for(monthly_price_of(db, product), billing_days)
    else:
        if product.billing_days <= 0 or billing_days % product.billing_days:
            raise PricingError("使用周期不合法")
        factor = LEGACY_PERIOD_FACTORS.get(billing_days // product.billing_days)
        if factor is None:
            raise PricingError("仅支持基础周期、6 个周期或 12 个周期")
        unit = (Decimal(str(product.price)) * factor).quantize(CENT, rounding=ROUND_HALF_UP)
    total = (unit * quantity).quantize(CENT, rounding=ROUND_HALF_UP)
    return unit, total


def display_price_of(db: Session, product: Product) -> float:
    """月价，用于 Product.price 展示缓存。"""
    if not product.resource_category:
        return round(float(product.price), 2)
    try:
        return round(float(monthly_price_of(db, product)), 2)
    except PricingError:
        return 0.0


def sync_display_price(db: Session, product: Product) -> bool:
    """把月价回写到 Product.price；返回是否发生变化。"""
    if not product.resource_category:
        return False
    new_price = display_price_of(db, product)
    if not new_price or abs(float(product.price) - new_price) < 0.005:
        return False
    product.price = new_price
    return True
```

**关键点**：`quote()` 返回**该周期的单价**，不是基础周期价。这从根上解决"单价 × 数量 ≠ 合计"的展示 bug。

## 9. 回滚方案

**三层，都不需要回滚代码版本：**

| 层级 | 操作 | 影响面 | 生效时间 |
| --- | --- | --- | --- |
| 单个商品 | `UPDATE products SET resource_category = NULL WHERE id = ?` | 该商品退回固定价 | 立即 |
| 全部商品 | 同上，去掉 `WHERE id` | 全站退回旧逻辑 | 立即 |
| 表结构 | `alembic downgrade -1` | 删列 | 需停机窗口 |

第二层是这个设计最大的安全垫：**两套逻辑在代码里同时存在，只是由数据字段选择走哪条**。出问题改数据即可，不用等发版。

> ⚠️ 回滚**不会**恢复已被新价成交的订单——回滚只影响后续报价。

## 11. 折扣功能后续怎么接（本期不做，只留接口）

你现在说"后面再设计"，那就别提前埋假设。三种常见折扣维度，未来的实现位置各不相同：

| 折扣维度 | 未来的实现位置 | 对本方案的影响 |
| --- | --- | --- |
| **周期折扣**（年付 9 折） | `pricing_service.unit_price_for()` 里乘一个 `Decimal` 系数，系数存配置表 | 零结构变更，只改一行 |
| **活动折扣**（限时特价） | 新建 `promotions` 表，`quote()` 里查生效中的活动 | 零结构变更，加一个查询 |
| **客户等级折扣**（VIP 价） | `quote()` 增加 `customer` 参数，按等级查系数 | 函数签名要变，调用点 2 处 |

所以本方案**故意不做**的事：不加 `discount_rate` 字段、不加 `is_override` 标记、不预留 JSON 配置列。因为折扣的真实维度现在还不知道，提前建模 90% 会建错。

**唯一需要保证的**：`quote()` 是全站唯一取价入口。只要这条守住，未来任何一种折扣都只改一个文件。

> 但库里那 453 行旧的长周期价先别删——如果将来要做"周期折扣"，它们就是现成的候选系数来源（9 倍 = 75 折）。

## 13. 与 D5（金额迁移）的衔接

本方案做完后，D5 会简单很多：

- 所有价格计算收敛到 `pricing_service` 一个文件
- `quote()` 返回的就是 `Decimal`，改整数分只需 `quantize` 后乘 100
- 订单写入点只剩 `build_order` 和 `admin_create_resource_order` 两处
- **线性定价让 D5 的对账变简单**：任意订单都能用「月价 × 周期数 × 数量」独立复算，不需要再查历史折扣表

**D5 第一个用例建议**：`订单金额 == 月价 × 周期数 × 数量 == 钱包扣款金额`——这条在现在的双轨体系下不成立。
