# 通知渠道分发设计（站内信 + 企业微信，预留 Telegram）

> 状态：**已实施（2026-11-09）**。拍板背景（玖夜 2026-11-09）：**站内信/收件箱与微信通知同时保留**，后期可能对接 Telegram 机器人等更多渠道。本文设计的是"渠道分发层"，不是替换站内信。
>
> 落地位置：模型 `models/entities.py`（`NotificationChannel` / `NotificationChannelBinding` / `NotificationDelivery`）、迁移 `alembic/versions/0027_notification_channels.py`、服务 `services/notification_channel_service.py`、任务 `tasks/notifications.py`（`notification_dispatch`，每分钟）、路由 `api/notification_channel_routes.py`、前端 `views/NotificationChannelsView.vue`（管理员）+ 安全中心「消息推送」（用户自己开关）。实施差异见文末 §11。

## 0. 一句话结论

业务代码继续只写站内信（现状一行不改语义）；新增一个**异步分发任务**把已落库的通知按"渠道配置 + 用户绑定"推到企业微信；Telegram、Webhook 等后加的渠道只新增 Adapter，不再动业务代码。渠道发送失败永远不影响业务事务。

## 1. 现状盘点（实施前必须知道的事实）

| 事实 | 位置 | 对设计的影响 |
| --- | --- | --- |
| 通知只有一张 `notifications` 表（user_id/title/content/category/is_read），业务事务内同步写入 | `services/order_service.py:143`、`services/health_service.py:30`、`tasks/notify.py` | 入口已收敛，**不能**在业务事务里同步调外部 API——微信 API 慢或挂会把下单/交付事务一起拖回滚 |
| 收件箱（`inbox_threads`）是人工会话，与通知完全分离 | `api/inbox_routes.py` | **保留不动**。收件箱新消息只发"有新消息"通用通知，本方案的分发层照发这条通知，不碰正文 |
| 通知正文已经脱敏：不含订阅地址、密码、Token、收件箱消息内容 | 主设计文档 §12/§13 | 渠道消息直接复用通知正文，不需要二次脱敏设计 |
| 定时任务框架已有：`app/tasks/registry.py` 注册、`app/scheduler.py` 轮询、`scheduled_task_runs` 流水、任务锁 | `tasks/` | 分发任务直接挂进现有框架，不新建进程 |
| 供应商凭据加密已有 Fernet 设施 | `services/supplier_credentials.py` | 渠道密钥（企微 secret、TG bot token）复用同一加密机制落库，明文不进库不进日志 |

## 2. 总体架构

```
业务事务（下单/交付/到期/收件箱新消息…）
    │  只做一件事：写 Notification（现状不变）
    ▼
notifications 表
    │
    ▼  notification_dispatch 任务（scheduler，每分钟）
    │   1. 扫描"创建后 N 分钟内、尚无投递记录"的通知
    │   2. 按渠道配置生成 notification_deliveries（幂等：唯一约束挡重复）
    │   3. 逐条调 Adapter.send()，写结果
    ▼
Adapter（一个渠道一个类，统一接口）
    ├── WecomAppAdapter      企业微信应用消息 → 精确到人（销售/管理员）
    ├── WecomWebhookAdapter  企业微信群机器人 → 运维群告警兜底
    ├── TelegramAdapter      后期：TG bot + getUpdates 轮询绑定（本文 §7）
    └── （未来）邮件 / 钉钉 / 飞书，同接口新增
```

### 2.1 为什么是"先落库再异步分发"而不是"业务里直接发"

1. **事务安全**：微信 API 平均几百毫秒、失败率不可控，放在业务事务里等于给下单链路加了一个外部依赖。
2. **业务代码零改动**：`notify_order_parties`、`notify_admins` 等现有调用点一行不用改，分发对业务完全透明。
3. **可重试可审计**：投递流水独立成表，失败可看、可重试、可统计到达率。
4. **渠道即插即用**：加 TG 只是加一个 Adapter + 绑定方式，前面四层全部复用。

## 3. 数据模型（1 个 alembic revision，3 张表）

### 3.1 `notification_channels`（渠道配置，管理员管理）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | PK | |
| `channel_type` | String(30) | 枚举：`wecom_app` / `wecom_webhook` / `telegram_bot` |
| `name` | String(60) | 人读名称，如"企微-运营通知" |
| `config_encrypted` | Text | Fernet 加密的 JSON。`wecom_app`: `{corpid, agent_id, secret}`；`wecom_webhook`: `{webhook_url}`；`telegram_bot`: `{bot_token, api_base}` |
| `push_categories` | String(200) | 逗号分隔的 category 白名单，空 = 全部。例：`order,health,expiry` 只推业务类，`system`（任务失败类）只进群机器人 |
| `is_enabled` | Boolean | 停用即不再生成新投递，存量 pending 标记 skipped |
| 时间戳 | | created_at / updated_at |

加密密钥复用 `SUPPLIER_SECRET_ENCRYPTION_KEY` 同款机制；生产校验独立长度（沿用现有 validator 风格）。密钥明文只在发送瞬间解密在内存，不进日志、不进 `notification_deliveries`。

### 3.2 `notification_channel_bindings`（用户 ↔ 渠道目标，谁能收到）

| 字段 | 说明 |
| --- | --- |
| `user_id` → users | 哪个账号要收 |
| `channel_id` → notification_channels | 走哪个渠道 |
| `target` | String(120)。`wecom_app` = 企微 userid；`telegram_bot` = chat_id；`wecom_webhook` 无需绑定（群即目标） |
| `is_enabled` | 用户可暂停自己的推送 |
| 唯一约束 | `(user_id, channel_id)` |

绑定方式分渠道：
- **企微应用消息**：管理员在后台把销售账号和企微 userid 对上（通常两者同名，提供"按用户名预填"）。第一版管理员代绑，不做 OAuth 授权流（明确不做，见 §8）。
- **Telegram**：用户自助绑定，见 §7。

### 3.3 `notification_deliveries`（投递流水）

| 字段 | 说明 |
| --- | --- |
| `notification_id` → notifications | 源通知 |
| `channel_id` / `target` | 冗余存快照，渠道删除后历史仍可读 |
| `status` | `pending` / `sent` / `failed` / `skipped` |
| `attempts` / `last_error`(String(300) 截断) / `sent_at` | |
| 唯一约束 | `(notification_id, channel_id, target)` —— **幂等核心**：任务重跑、锁过期重入都不会重复推送 |

## 4. 分发任务（`app/tasks/notifications.py`，注册进 registry）

- 间隔 1 分钟；任务锁沿用 `tasks/locking.py`。
- 扫描窗口：`created_at` 在最近 24h 内且没有对应 delivery 的通知。超过 24h 的不补发（陈年通知再推是骚扰，不是可靠性）。
- 生成投递的匹配规则：
  1. 渠道启用，且通知 category 命中 `push_categories`（空 = 全部）；
  2. 该通知的 `user_id` 存在启用的 binding，target 即收件人；
  3. `wecom_webhook` 类型的例外：不看 binding，凡命中 category 就推群（告警兜底渠道的定位）。
- 发送：每渠道每轮批量上限 50 条，条间 sleep 100ms（企微应用消息有频率限制）；失败重试 `attempts < 3`，间隔 1/5/15 分钟退避（下轮扫描自然实现）。
- **防风暴环**：分发任务自身产生的通知（如"渠道连续失败"告警）标记 source，不再进入分发，最多推群机器人。
- 连续失败 10 条 → 通知管理员 + 把该渠道置"降频"（只记流水不发送，等管理员处理）——避免 secret 失效后每分钟空转打日志。

## 5. Adapter 契约

```python
class ChannelError(Exception): ...

class NotificationAdapter(Protocol):
    channel_type: str
    def send(self, config: dict, target: str, title: str, content: str) -> None: ...
```

- `WecomAppAdapter`：POST `https://qyapi.weixin.qq.com/cgi-bin/message/gettoken`（缓存 token，2h 内复用）→ `message/send`，msgtype=text。非 0 errcode 抛 `ChannelError(errcode, errmsg)`。
- `WecomWebhookAdapter`：POST webhook_url，markdown 消息（群机器人支持 markdown，比 text 好读）。
- HTTP 客户端复用供应商模块的 timeout/重试参数风格（`SUPPLIER_HTTP_TIMEOUT_SECONDS` 同级别，新增独立配置 `NOTIFICATION_HTTP_TIMEOUT_SECONDS=10`）。

## 7. Telegram 适配（第二期实施，本期只留接口位）

- **绑定流程（不需要公网 webhook）**：用户在站内"我的通知渠道"点"绑定 Telegram" → 生成一次性 `bind_token`（10 分钟有效，存 Redis）→ 用户在 TG 里对该 bot 发 `/start <token>` → 新增轻量任务 `telegram_poll`（getUpdates 长轮询，30s）收到消息 → 匹配 token → 写 binding(chat_id) → TG 回一句"绑定成功，后续通知发到这里"。
- **出网前提（主动挑明）**：`api.telegram.org` 从国内服务器直连不可达，必须走出站代理。你们自己就是做跨境线路的，这不是障碍，但要写进部署清单：`telegram_bot` 渠道的 `api_base` 支持配置代理地址，生产 `.env` 增加 `TELEGRAM_PROXY_URL=`（留空则该渠道不可创建，启动时校验给出明确报错，不静默失败）。
- **合规口径**：TG 作为内部运营触达渠道没问题，但对客户的对外话术和宣传物料里**不要**把它表述为官方客服渠道；客户触达仍然只有站内信/收件箱 + 销售微信，这条边界写死。
- 消息内容沿用站内信正文（已脱敏），不追加任何凭据类字段。

## 8. 明确不做什么

1. **不动收件箱**：人工会话、未读、负责人逻辑一行不改；收件箱新消息只触发通用通知，微信里也只推"您有新的站内消息"，不带正文。
2. 不做用户级"按 category 订阅"（管理员配渠道级 categories 已够用；做细了没人配得明白）。
3. 不做企微 OAuth 授权登录/代绑自动化（管理员手绑userid，量级就几个销售）。
4. 不做邮件渠道（无 SMTP 通道，等有真实需求再说）。
5. 不做"已读回传"（TG/微信里读了不回写站内信已读状态，单向推送）。
6. 不做实时推送（WebSocket / SSE）——1 分钟轮询的异步分发对"到期提醒、新订单"这类场景足够；真需要秒级再议。

## 9. 验收标准

1. 下单 → 30 秒~2 分钟内对应销售的企微收到通知；站内信与收件箱行为与改造前完全一致（回归现有 238 个测试无漂移）。
2. 杀掉分发进程再启动：不漏发、不重复发（唯一约束 + 24h 窗口验证）。
3. 企微 secret 配错：业务下单不受影响；delivery 落 `failed` + last_error；连续失败后渠道降频并有管理员通知。
4. 停用渠道：存量 pending 转 skipped；新通知不再生成投递。
5. 审计包含渠道创建/修改/测试/绑定变更。
6. 新增测试：分发幂等、category 过滤、绑定启停、失败退避、防风暴环（≥8 个用例）。

## 11. 实施记录与差异（2026-11-09）

落地内容与本文设计的差异，如实记在这里：

| 项 | 设计 | 实际 | 原因 |
| --- | --- | --- | --- |
| 加密设施 | 复用供应商凭据加密 | 复用同一 `SUPPLIER_SECRET_ENCRYPTION_KEY`（AES-GCM，独立 associated data 前缀） | 不再引入第二把密钥；代价是**未配置该环境变量时渠道创建直接 400**（本地 `.env` 默认为空，需先生成 32 字节 hex） |
| 重试 | 失败退避重试 | 每个通知×渠道只建一条 delivery，失败后**同一轮不重试**，靠下一轮扫描 `status in (pending, failed) and attempts < 3` 补发 | 避免同轮死循环；24h 窗口外不再补发 |
| 渠道级 categories | 逗号分隔白名单 | 同设计，空 = 全推 | — |
| 防风暴 | 分发自身的告警不进分发 | 用消息正文标记 `DISPATCH_MARKER` 过滤 | 少一张表/一个字段，代价是标记不能出现在业务文案里 |
| 用户侧页面 | 独立"我的通知渠道"页 | 并入 `安全中心` 的「消息推送」面板（只可开关，不可改目标） | 少一个一级入口；改目标必须走管理员，防止把推送地址改成别人的 |
| 渠道删除 | 未设计 | **未实现**（只能停用） | 投递流水有外键引用，硬删会破坏历史；停用语义已足够 |
| Telegram | 二期 Adapter | 未实现，仅保留 `CHANNEL_TYPES` 注册位 | 按计划二期 |

验收实测（本地）：

- `notification_dispatch` 手动触发 → `{"channels":1,"created":6,"delivered":0,"failed":6}`，6 条 delivery 全部落 `failed`，`last_error` 为企微真实返回（`invalid webhook url`），业务侧无异常。
- 幂等：重复触发不再新增 delivery（唯一约束 `uq_notification_delivery_target`）。
- 测试：`tests/test_notification_channels.py` 覆盖渠道 CRUD、绑定、category 过滤、24h 窗口、幂等、失败记录、防风暴环、权限（销售/客户不可见）。
