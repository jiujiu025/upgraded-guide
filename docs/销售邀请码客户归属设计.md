# 销售邀请码客户归属设计

> 状态：**已实施（2026-11-09）**。迁移 `0026_sales_invite_codes`；注册接口带 `invite_code` 绑定归属；销售/管理员 API 与前端（注册页邀请参数、销售工作台邀请码卡片、管理员销售管理"邀请码"页签）已上线；测试 `backend/tests/test_invite_codes.py`（13 个用例）。公海兜底路径（无码注册 → 管理员分配）仍为后续方案，本文只预留了接口位。
> 拍板背景（玖夜 2026-11-09）：客户分配不走轮询/公海抢单，**给销售设置邀请码，走哪个邀请码注册就是谁的客户**。

## 0. 一句话结论

注册接口 `POST /api/public/register` 增加可选 `invite_code` 字段；有效码则注册事务内直接写 `customers.sales_id`，失效码**不拒绝注册**（客户无感知，归公海 + 通知管理员）。销售工作台自助生成/管理自己的码，管理员全量可见、可强制停用、全程审计。

## 1. 现状盘点（实施前必须知道的事实）

| 事实 | 位置 | 对设计的影响 |
| --- | --- | --- |
| 注册写死 `sales_id=None`，`RegisterIn` 是 `extra="forbid"` | `api/routes.py:597`、`schemas/common.py:31` | 加字段必须同步改 schema，且**只**加 `invite_code`，不允许前端传 sales_id 之类的越权字段 |
| 注册按可信代理解析后的 IP 限流（5 次/分钟） | `services/registration_service.py` | 邀请码校验接口沿用同一限流，防止枚举扫描码 |
| 客户与销售归属已按 `sales_id` 做全链路范围过滤（销售只见自己的客户） | 现有权限矩阵 | 绑定即生效：销售立刻能在工作台看到该客户，无需其他改动 |
| 通知写入已收敛（`notify_order_parties` / `notify_admins`） | `services/order_service.py` | 新增"邀请注册"事件复用同一入口；若通知渠道分发方案（另文）已实施，则同步推企微 |
| 审计要求 actor 是 users 外键 | `services/audit_service.py` | 绑定发生在注册事务内，actor 用**新注册用户的 id**（动作的实际发起者就是客户本人） |

## 2. 数据模型（1 个 alembic revision，1 张表）

### `sales_invite_codes`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | PK | |
| `code` | String(12)，unique | 8 位 Crockford Base32（去掉 `0/O/1/I/L` 防误读误输），`secrets` 随机生成，库内唯一冲突重试 |
| `sales_user_id` | FK users | 持有人，必须是 `role='sales'` 且启用的账号 |
| `status` | String(20) | `active` / `disabled` |
| `max_uses` | int, nullable | 累计注册上限，空 = 不限 |
| `used_count` | int, default 0 | 每次成功绑定 +1 |
| `expires_at` | datetime, nullable | 到期自动失效 |
| `note` | String(120) | 人读备注："抖音地推"、"官网轮播图" |
| `disabled_at` / `disabled_by` | nullable | 停用留痕：谁在什么时候停的 |
| `created_at` | | |

设计要点：

1. **一个销售可持多个有效码**（上限 10 个 active）：地推、官网入口、朋友圈不同渠道各一个码，归属同一个销售但统计可分。
2. **码不可自定义字符串**：防钓鱼（仿冒官方码）、防撞车、防含义化（`"VIP888"` 会被客户当折扣码）。只能系统生成。
3. 8 位去混淆 Base32 ≈ 2^40 组合，配合注册限流，枚举不可行。

## 3. 注册绑定流程

```
客户打开 注册页?invite=XXXXXXX
    │  前端先调 GET /api/public/invite-codes/{code} 显示"邀请人：某某"
    ▼
POST /api/public/register {…, invite_code: "XXXXXXX"}
    ▼ 同一事务内：
    ├─ 现有注册逻辑（建 user + customer，不变）
    ├─ 校验邀请码：status=active 且未过期且 used_count<max_uses
    │           且持有人 role='sales' 且 is_active
    ├─ 有效 → customer.sales_id = code.sales_user_id
    │         code.used_count += 1
    │         审计：actor=新用户, action='invite_code_bind'
    │         通知销售："新客户 {name} 通过邀请码注册"
    └─ 无效 → 注册照常成功，sales_id=None（公海）
              审计：action='invite_code_rejected'，detail 记录
              attempted_code 与拒绝原因（不记任何客户敏感信息之外的字段）
              通知管理员："公海新增客户（尝试了失效邀请码 {code}）"
```

### 3.1 失效码不拒绝注册——理由写死

客户填错/旧码过期/销售离职被停码，这些是**商家的内部状态，不是客户的错**。注册被 4xx 拒绝会直接损失一个真实客户。归属纠纷由管理员在后台裁决（现有转派逻辑 + 审计已覆盖），客户侧永远无感知。

### 3.2 归属只绑一次

- 绑定发生在注册事务内，天然一次性；
- 已有 `sales_id` 的客户不存在"再绑"路径（注册只会新建客户）；
- 管理员后续改派/转派走现有逻辑与审计，本方案不新增覆盖手段。

### 3.3 销售离职

管理员停用销售账号时，接口返回该销售仍有 active 码的提示，确认后**级联停用其全部码**（`disabled_by`=操作管理员）。已绑定客户不迁移（客户关系由交接流程处理，系统不自动改归属）。

## 4. API

| 方法与路径 | 请求 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET /api/public/invite-codes/{code}` | — | 公开（限流） | 只回 `{valid, inviter_name}`；失效回 `valid:false` 不回原因细节（不给枚举者探针信息）。inviter_name 用销售 display_name |
| `POST /api/public/register` | `RegisterIn` + `invite_code?: str`（strip 后 4-12 位，大小写不敏感） | 公开（限流） | §3 流程 |
| `GET /api/sales/invite-codes` | — | sales | 我的码列表（code/状态/used_count/max_uses/expires_at/note/注册链接） |
| `POST /api/sales/invite-codes` | `{note?, max_uses?, expires_at?}` | sales | 生成新码；active 数达 10 个则 422 |
| `POST /api/sales/invite-codes/{id}/disable` | — | sales | 只能停自己的码 |
| `GET /api/admin/invite-codes` | `sales_id?/status?` 筛选 | super_admin / admin | 全量视图 |
| `POST /api/admin/invite-codes/{id}/disable` | — | super_admin / admin | 强制停用（审计） |
| `GET /api/sales/invite-customers` | 分页 | sales | 通过我的码注册的客户列表（本质是 `sales_id=me` 客户按注册时间倒序，前端复用客户 360 卡片） |

安全约束：

- 销售接口全部按 `current_user.id` 过滤，IDOR 防御与现有客户范围过滤同一套路（别人的码 ID 直接 404，不回 403 区分存在性）。
- 公开校验接口与注册共用 IP 限流 scope，且对**不存在**和**失效**的码返回同构响应、同耗时路径（防存在性探测）。
- `invite_code` 在注册 schema 里与现有字段同样走 `extra="forbid"`，防止夹带 `sales_id`。

## 5. 前端改动

1. **注册页**：URL 带 `?invite=` → 自动填入隐藏字段，顶部显示"邀请人：{inviter_name}"（调公开校验接口，失效则显示普通注册不带邀请标识）；码支持手动输入框（大小写不敏感，提交前统一大写）。
2. **销售工作台**：新增"我的邀请码"卡片——每个码显示码本身、注册链接（`{FRONTEND_ORIGIN}/register?invite={code}`，前端拼）、一键复制、used_count、备注、停用按钮；"生成新码"表单（备注/上限/有效期）。二维码：第一期只给链接复制（销售贴到微信即可）；真机扫码需求上来再加前端 qrcode 依赖渲染。
3. **管理员后台**：销售管理页内嵌"邀请码"页签：全量表格 + 筛选 + 强制停用 + 该销售的绑定统计。

## 6. 通知联动

| 事件 | 收件人 | 内容 |
| --- | --- | --- |
| 邀请码绑定成功 | 该销售 | "新客户 {name} 通过你的邀请码注册，请在工作台跟进" |
| 失效码注册 | 管理员 | "公海新增客户（尝试邀请码 {code} 已失效）"，marker 去重防刷屏 |
| 码被强制停用 | 该销售 | "你的邀请码 {code} 已被管理员停用" |
| 销售账号停用且级联停码 | 操作管理员 | 确认提示 + 事后审计 |

通知正文不含客户手机号/邮箱（脱敏），沿用现有通知口径。若《通知渠道分发设计》已落地，这些事件自动获得企微推送能力，无需额外改动。

## 7. 测试清单（新增 ≥10 个用例）

1. 有效码注册 → `sales_id` 正确、used_count+1、审计两条（注册 + 绑定）、销售收到通知；
2. 失效/过期/超限/停用码 → 注册仍 201、`sales_id=None`、管理员收到通知、审计记拒绝原因；
3. 持有人被停用/降权后，码视为失效；
4. 码大小写不敏感、前后空格容忍；
5. 销售建码达 10 个 → 422；停用后可再建；
6. 销售 A 不能停用/查看销售 B 的码（IDOR）；
7. customer 角色调用建码接口 → 403；
8. 公开校验接口：存在与不存在响应同构；限流生效；
9. 管理员强制停用写审计且通知销售；
10. 停用销售账号 → active 码级联停用；
11. 回归：不带 `invite_code` 的注册行为与现状完全一致（快照对比）。

## 8. 明确不做什么

1. **不做多级分销/邀请返佣**：码只决定客户归属，与佣金无关（佣金已有"按收款计提"的独立口径，别搅在一起）。
2. 不做码自定义字符串、不做二维码后端生成（前端事）、不做批量导入码。
3. 不做"公海自动分配"（轮询/抢客）：无码注册先进公海由管理员手动分配，是另一个方案的范畴。
4. 不做邀请码维度的成单漏斗统计（注册→下单→回款转化率）：数据都在，等真实运营跑起来再决定口径，先给 used_count 和客户列表。

## 9. 验收标准

1. 销售在工作台 30 秒内拿到可用邀请码，复制注册链接发进微信；
2. 客户点链接注册，销售工作台立刻（刷新后）看到该客户，且能正常走客户 360 / 下单 / 触达全流程；
3. 填错码的客户注册成功且无任何错误提示（内部可见审计与管理员通知）；
4. 全链路范围过滤回归：销售只见自己码带来的客户，管理员全量；
5. `alembic check` 无漂移，迁移可 downgrade。
