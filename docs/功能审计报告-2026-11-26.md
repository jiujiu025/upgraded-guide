## 1. P1

### 1.1 中转抛出的非业务异常没人接，上游已扣款但系统停在"采购中"

- 位置：`app/services/procurement_service.py:321-325`、`app/services/transit_service.py`（异常类型）
- 复现（已跑通）：把 `transit_vps.encrypted_password` 设成无效密文（密钥轮换后的真实场景），
  调 `provision_transit`，抛出的异常是 **`TransitCredentialError`**；
  `auto_procure_order` 只捕获 `(TransitNotConfigured, TransitProvisionError)`，**捕获不到**。
- 链路后果：
  1. `order.status = pending_delivery` 已提交；
  2. `procurements` 记录已提交为 `pending`；
  3. 上游 `buy_static_ip` **已经扣钱**；
  4. `record.external_order_no` / `response_payload` 的赋值在异常前未提交，被后台任务的
     `db.rollback()` 回滚 —— **上游单号丢失**；
  5. 客户没有线路、没有通知；后台采购记录永远显示"采购中"。
- 影响：社媒/直播订单在上游扣款后静默卡死，运营既看不到错误也查不到上游单号，
  只能去上游后台按 remark（订单号）捞。
- 建议：
  1. **先落盘再加工**：拿到 `result.order_number` 后立即 `db.commit()`（采购成功、单号、账号），
     再调 `provision_transit`；这样中转失败时采购结果不会丢。
  2. `provision_transit` 内用 `except Exception` 兜底，统一包成 `TransitProvisionError`
     （保留原始 code），不要漏出裸异常。
  3. `auto_procure_order` 的 except 增加通用分支：记 `failed`/`awaiting_transit` 并通知客户。
- 回归：新增用例"凭据损坏 → 订单 `pending_transit`、采购记录保留上游单号、客户收到通知"。

### 1.2 模拟标签里点「退出登录」，会把管理员自己的后台会话登出

- 位置：`frontend/src/views/WorkspaceView.vue:485`（`logout()` → `endSession()` → `POST /auth/logout`）
- 原因：登录态靠 refresh cookie，**cookie 是浏览器级共享的**。模拟标签虽然用独立 token，
  但 `/auth/logout` 读的是 cookie，撤销的是**管理员的真实会话**。
- 影响：管理员在模拟窗口里顺手点"退出登录"，回到后台标签发现已掉线；
  更糟的是他可能以为只是退出了模拟，实际把自己的会话杀了。
- 建议：
  1. 模拟态下把「退出登录」替换为「退出模拟」（`logoutImpersonation()` + `clearImpersonation()`）；
  2. 后端 `/auth/logout` 识别到 Bearer 是 `imp_` 前缀时直接 400 并提示"请退出模拟"，
     作为第二道防线（防止别处调用）。
- 回归：前端用例断言模拟态点退出只调 `logoutImpersonation`，不调 `logout`。

## 2. P2

### 2.1 中转部分失败后重试，只按已有记录补，可能少交付

- 位置：`transit_service.retry_provision`（只查 `TransitProvision`）+ `provision_transit` 的循环
- 现象：`quantity=2` 的订单，第一条线路就失败时，`provision_transit` 直接抛出，第二条
  `line_index` 根本没有记录。重试只处理已有记录 → 交付 1 条 →
  `claim_delivery_slot` 把订单推到 `partially_delivered`，而重试接口只接受 `pending_transit`，
  **再也无法自动补第 2 条**。
- 建议：重试时按 `order.quantity` 补齐缺失的 `line_index`（账号可从采购记录里的
  `encrypted_exit_credentials` 恢复），缺凭据的标人工。

### 2.2 已存在的中转出站不会更新

- 位置：`transit_service._provision_one` 的 `has_outbound = any(tag == outbound_tag)`
- 现象：只看 tag 是否存在，不比对地址/账密。上游换过 IP 后重试，模板里仍是旧 IP，
  客户出口指向一台可能已失效的机器。
- 建议：比对 `servers[0]` 与当前账号，不一致就替换并重新保存（重启一次）。

### 2.3 健康页的国家筛选用「产品地区」而不是「订单地区」

- 位置：`app/api/health_admin_routes.py:77`（`outerjoin(Region, Region.id == Product.region_id)`）
- 现象：产品在后台被换绑地区后，历史订单按国家筛会错位或漏掉。
- 建议：改 join `Order.region_id`；订单表已有 `region_name` 快照，但没有 `country_code`，
  长期建议下单时把国家码一起快照。

### 2.4 面板批量探测在线程池里共用同一个 SQLAlchemy Session

- 位置：`health_admin_routes._panel_snapshot(panel, db)` 被丢进 `ThreadPoolExecutor`
- 现状：里面只读已加载属性 + 解密，没有查询，所以暂时不炸；但 Session 不是线程安全的，
  以后有人在里面加一句 `db.scalar(...)` 就会随机报错。
- 建议：主线程先解密凭据，线程函数只接收 `base_url / 凭据 / connect_host`，不碰 `db`。

### 2.5 模拟 token 可以被转发

- 位置：`ImpersonationBanner` / 新标签 URL 的 `#imp=<token>`
- 现状：token 有效期 10 分钟，拿到 URL 的任何人都能直接用。
- 建议：首次使用后作废（页面加载换成一个只在本标签有效的短期凭据），或绑定首次请求的 IP/UA。

### 2.6 模拟客户/销售时，健康页仍是演示数据

- 位置：`HealthView.vue` 的 `isAdmin` 分支，非管理员继续读 `mocks/health.js`
- 影响："以客户身份看"时看到的是原型数据，和真实接入后的页面不一致。
- 建议：接只读接口并按名下客户限权，或在页面上明确标注"演示数据"。

## 3. P3

1. **中转面板表单允许填固定 reality 密钥**，一旦填了，该机所有入站共用一对，
   等于回到"一条被墙、整机受影响"。建议表单加警示，或默认隐藏该字段。
2. **资源池页有两个"自动采购"概念**：`supplier.auto_purchase_enabled`（供应商级）与
   `purchase_enabled`（运行时开关）。文案都叫自动采购，运营容易混。
3. **购买页热度**：未知国家默认 40 分，会排在小市场（孟加拉 35 / 巴基斯坦 33）前面。
   建议默认分降到 30 以下。
4. **模拟过期后跳 `/admin/login?imp=ended`**，登录页没有对应提示，管理员不知道发生了什么。
5. **`deliver_pending_transit` 未校验 `created` 为空**：理论上会发"已开通 0 条"并把采购
   标成功；当前有状态闸门挡着，属于防御性缺失。

## 4. 已知取舍（不算 bug，但要知道）

- 中转每次改 Xray 模板都要重启，同机客户瞬断 1–3 秒；已按机器限量并按国家分机。
- 模拟登录按需求给了**全部写权限**，下单/退款/删除都真实生效；审计记在管理员头上，
  但资金动作追不回来。
- 健康检测是 TCP 连通性，不代表代理真实可用；页面已注明。

## 5. 建议修复顺序

1. P1-1（中转异常兜底 + 先落盘上游单号）——发布前必须，否则社媒单可能静默卡死；
2. P1-2（模拟态退出按钮）——发布前必须，一行判断 + 一个后端保护；
3. 一起发布上述两个修复；
4. 下一批：2.1 → 2.2 → 2.3 → 2.4；
5. 2.5 / 2.6 与 P3 随迭代处理。
