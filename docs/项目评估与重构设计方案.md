> 评估时间：2026-11-07　评估基线：分支 `codex/admin-layout-finance-deploy`（HEAD `3e5be94`）+ 当前工作区未提交改动

## 0. 一句话结论

**这是一个真实可运行的 v1，不是玩具项目，不建议推倒重写。** 后端的权限隔离、账务幂等、交付并发控制、密钥加密这几块做得比大多数同规模业务系统要好；真正的债务集中在**分层（单文件 1436 行的路由）、金额类型双轨、前端单文件 2167 行的巨型组件、以及后台任务/可观测性缺失**这四件事上。

推荐路径：**保留领域模型与数据表 → 绞杀式（strangler）增量重构 → 先止血再分层**。预估 6-8 周可到"可长期维护、可多人协作"的状态，期间线上功能不中断。

**但有一件事必须立刻处理**：当前工作区有 9 个测试是红的（详见 2.2）。

## 2. 问题清单（按严重度）

### 2.1 P0：当前正在出血

#### P0-1　工作区 9 个测试红，HEAD 是绿的（新功能引入的回归）

**现象**：`tests/test_supplier_readonly.py` 中 9 个用例失败，HEAD 快照 25/25 全过。

**根因**（已定位到具体行为，不是猜）：

```
sqlite3.IntegrityError: NOT NULL constraint failed: supplier_regions.source_endpoint
raised as a result of Query-invoked autoflush
```

触发点：`app/services/supplier_service.py` 的 `sync_regions()` 中，新代码在给 ORM 对象赋完前几个字段后，就调用了 `_ensure_local_region(db, ...)`（内部执行 `db.scalar(select(...))`）。SQLAlchemy 的 autoflush 在此刻把**尚未赋完**的 `SupplierRegion` 提前 INSERT 出去，而 `source_endpoint` / `last_synced_at` 还没赋值（NOT NULL）。

**修复**（3 行，二选一）：

```python
# 方案 A：调整赋值顺序，先补齐 NOT NULL 字段再查询
record.source_endpoint = source_endpoint
record.last_synced_at = synced_at
record.local_region_id = _ensure_local_region(db, record.country_code, item.country_name).id

# 方案 B：查询段包在 no_autoflush 里（推荐，防同类复发）
with db.no_autoflush:
    local_region = _ensure_local_region(db, record.country_code, item.country_name)
record.local_region_id = local_region.id
```

顺带把 `_ensure_local_region` 里 `db.flush()` 改为 `db.flush([region])`，收窄 flush 范围，避免同类问题在别处复现。

> 这类 bug 的根因不在这一处，而在"服务层直接操作 ORM 且靠 autoflush 隐式落库"这个模式。M2 分层时会顺手解决。

#### P0-2　`/healthz` 是假绿，容器健康检查会骗人

> **已实现**：`/healthz` 保留为纯存活探针；新增 `/readyz`（`app/services/readiness_service.py`）检查数据库 `SELECT 1`、共享限流 Redis `PING`、数据库迁移版本与脚本 head 一致，任何 fail 回 503；镜像 `HEALTHCHECK` 与 compose api healthcheck 已改指 `/readyz`；部署手册补了排障对照。测试见 `tests/test_readiness.py`。

```python
# app/main.py:36-38
@app.get("/healthz")
def healthz():
    return {"status": "ok", "service": "ops-platform"}
```

数据库挂了、Redis 挂了、迁移没跑，它照样返回 200。而 `docker-compose.prod.yml` 里 api 和 web 的 healthcheck 都依赖它 —— **编排层会认为服务健康，故障期间不重启、不报警**。

**修复**：三级探针（业界标准）：

| 端点 | 语义 | 检查内容 | 失败后果 |
| --- | --- | --- | --- |
| `/healthz` | liveness | 进程活着，什么都不查 | 失败 → 重启容器 |
| `/readyz` | readiness | `SELECT 1` + Redis PING + Alembic 版本 == head | 失败 → 摘流量，不重启 |
| `/metrics` | 观测 | 请求量/延迟/错误率/DB 连接池 | — |

compose 的 healthcheck 改指 `/readyz`。

#### P0-3　金额双轨：Float 与「分」并存，且客户余额有两份真相

三套金额表示同时存在：

| 位置 | 类型 | 示例 |
| --- | --- | --- |
| `Order.amount` / `.total_amount` / `.unit_price` | `Float` | `app/models/entities.py:133,139,140` |
| `Product.price` / `Customer.balance` | `Float` | `entities.py:81,66` |
| `WalletAccount.balance_cents` / `WalletTransaction.*` | `BigInteger`（分）| `entities.py:373-434` ✅ |
| `RetailPriceRule.unit_price` / `Order.supplier_cost` | `Numeric(18,2)` / `Numeric(18,4)` | ✅ |

问题不在"能不能跑"，在于**三个致命场景**：

1. **对不上账**：`wallet_service.py:73-76` 每次余额变动都执行 `customer.balance = after / 100`——float 除法把整数分转回浮点，客户余额有了两个真相源，长期必然漂移。
2. **舍入漏洞**：`money_to_cents(order.total_amount)` 每次都要从 float 反推分，`0.1+0.2` 类问题会在边界金额上产生 1 分钱差异，而财务对账是对到分的。
3. **改价不可比**：`order_service.calculate_order_price` 用 `Decimal(str(product.price))` 兜底，但入库仍是 float，属于"算得准、存不准"。

**修复方向**（M2 执行，需迁移）：
- `Order` 增加 `total_cents / unit_price_cents`（`BigInteger`），金额计算全链路整数分，展示层再除。
- `Customer.balance` 直接**删除**，一律读 `WalletAccount.balance_cents`（这是一处历史冗余，没有存在价值）。
- float 列保留 1-2 个版本只读兼容，前端切换完成后删列（走 expand → migrate → contract）。

### 2.2 P1：结构性债务（决定未来 6 个月的开发速度）

#### P1-1　路由层是巨石：`routes.py` 1,436 行 / 70 个端点 / 5 种角色

一个文件里同时装着：登录注册、密码找回、客户 CRUD、产品地区、线路、订单、交付、续费、健康、通知、公开接口、销售工作台、管理员订单、资源池下单。每位开发者的修改都要抢同一个文件，Git 冲突必然频繁。

更麻烦的是**认证细节在每个端点重复**：`_cookie()` / `_clear_cookie()` / `_csrf()` / `_origin()` 这些辅助函数要在端点里手动调用（例如 `change_password`、`logout`），任何一处漏调就是安全缺口。

另外 `routes.py:840` 和 `routes.py:959` 有函数体内的 `from ... import ...`——这是典型的循环依赖信号，说明服务边界已经不清晰了。

#### P1-2　两套价格体系并行，同一商品可能两个价

| 路径 | 定价逻辑 | 位置 |
| --- | --- | --- |
| 官网 C 端下单 | `Product.price`（Float）× 硬编码周期系数 `{1:1, 6:5.5, 12:10}` | `order_service.py:11,14-25` |
| 资源池下单 | `RetailPriceRule`（Decimal）按 `分类+国家+周期` 查表 | `routes.py:1006-1009` |
| 后台改价 | 改 `RetailPriceRule` | `catalog_admin_routes.py:193` |

**后果**：同一个"美国静态住宅 30 天"，官网走 Product.price，资源池走 RetailPriceRule，两个值可以不同。运营在后台改零售价，官网价格不会跟着动。这是**收入侧的一致性风险**，比代码风格重要得多。

同时 `PERIOD_FACTORS` 把 6 个月打 5.5 折、12 个月打 10 折写死在代码里，运营无法配置；而 `RetailPriceRule` 恰恰是为可配置价格建的——能力有了但没接上。

**修复**：确立**单一价格真相源**= `RetailPriceRule`（Decimal + 版本），`Product.price` 降级为"展示缓存"由同步/发布流程回写，`calculate_order_price` 改为查表 + 只保留"数量 × 单价"的乘法，周期折扣表进数据库。

#### P1-3　列表接口无分页，全表返回

```python
# routes.py:474-480
def list_orders(db, user):
    ...
    return list(db.scalars(query.order_by(Order.created_at.desc())).all())   # 无限
# routes.py:830-831
def admin_orders(db, user):
    return list(db.scalars(select(Order).order_by(Order.created_at.desc())).all())  # 全表
```

`/customers` 有 `limit(200)`（硬编码），`/orders`、`/admin/orders`、`/lines` 完全无上限。订单量到万级后，后台首屏就会超时。收件箱接口已经做对了（`page/page_size/total`），**照着那个模式统一即可**，有现成范本。

#### P1-4　没有后台任务/调度器，该异步的全在请求里同步跑

`config.py` 定义了 `supplier_catalog_ttl_minutes`（1440）、`supplier_inventory_ttl_minutes`（30）、`supplier_quote_ttl_minutes`（1440）——**定义了 TTL 却没有任何任务在刷新**（全仓 `grep APScheduler|celery|cron` 无结果）。

由此产生三个具体问题：

1. 管理后台点"同步国家"→ 后端串行发上游 HTTP（超时 10s × 重试 3 次），HTTP 请求可能挂 30s+，nginx/浏览器超时。`SupplierSyncRun` 表已经建模了"运行记录"，说明设计上本来就该是异步的，只是没落地。
2. 线路健康只有手动触发（`routes.py:538`），没有周期探测；到期提醒、支付超时未支付关单、渠道对账，全都没有。
3. 无定时任务 = 无补偿机制。`pending` 状态支付单永久悬挂，只能人工看。

**修复**：引入轻量任务队列（建议 **arq**，原生 asyncio + Redis，与现有 Redis 复用，比 Celery 轻）。首批 5 个任务：供应商目录/库存/报价刷新、线路健康探测、到期提醒、支付单超时关闭、渠道对账。

#### P1-5　前端：`WorkspaceView.vue` 2,167 行承担 3 种角色

```
1-639      脚本（24 个函数）
641-1988   模板（1,347 行，内含多层 v-if 分支）
1990+      样式
```

客户中心、销售工作台、管理员首页三种完全不同的界面塞在一个组件里，靠 `v-if="workspace === 'client'"` 切换。后果：任何人改客户中心都可能弄坏销售工作台；组件无法单独测试；首屏加载三种角色的全部逻辑。

其他前端债务：
- `src/api/index.js`：171 行里塞了 **110 个接口函数** + 拦截器 + 刷新逻辑 + mock 兜底，无领域划分、无类型、无自动生成。
- `src/styles.css`：52KB **压缩成单行**的 CSS，变量与组件类混在一起，改样式靠全文搜索。
- 11 个视图各自带 `<style scoped>`，重复定义同类卡片/表格/按钮。
- `main.js` 引入 Pinia 但**全仓没有一处使用**（状态靠 `session.js` 的 reactive 模块），是纯粹的冗余依赖。

#### P1-6　没有 CI 在跑测试

`.github/workflows/` 只有一个 `production-infrastructure-acceptance.yml`（基础设施验收），**没有 `push` 触发跑 pytest / build 的工作流**。所以 9 个红灯能在工作区躺着——没有门禁。

## 3. 重构设计方案

### 3.1 总体策略：绞杀式增量重构，不推倒重来

**为什么不做重写**：领域模型（40 张表、21 个迁移、0 漂移）是这个项目最贵的资产，重写等于把它扔掉；而且现有安全/账务逻辑的质量高于平均水平，重写大概率退化。

**怎么做**：在旧结构旁边长出新的模块边界，逐个端点搬迁，每次搬迁都有测试保护，线上不收工。

```
原则：
1. 数据表先不动，只做「加列」，不轻易删列（expand → migrate → contract 三步走）
2. 每搬一个模块，旧端点保留 1 个版本做 302/代理转发，前端可灰度
3. 任何重构 PR 必须测试数不减、通过率 100%
4. 一次只动一个维度（不并行改「分层 + 金额类型 + 前端拆分」）
```

### 3.2 目标架构

```
┌──────────────────────────── Frontend (Vue 3 + Vite) ────────────────────────────┐
│  packages/                                                                      │
│  ├─ ui/          设计系统：Button/Card/Table/Drawer/Form/Toast/Empty（无业务）    │
│  ├─ api/         按领域拆分的客户端 + 类型（由 OpenAPI 自动生成）                  │
│  ├─ web/         官网（营销，SSG 友好）                                           │
│  ├─ console/     客户中心 + 销售工作台（按角色路由懒加载）                          │
│  └─ admin/       管理员后台（独立 layout + 权限指令）                              │
└───────────────────────────────────┬─────────────────────────────────────────────┘
                                    │  /api/v1  (统一版本前缀 + OpenAPI 契约)
┌───────────────────────────────────▼─────────────────────────────────────────────┐
│ Backend (FastAPI)                                                               │
│  api/v1/          路由层：只做「解析 → 调 service → 序列化」，不含业务判断          │
│   auth.py  catalog.py  order.py  delivery.py  finance.py                        │
│   inbox.py  supplier.py  admin.py  public.py  health.py                         │
│  services/        领域服务：事务边界在此，可被接口/任务/CLI 复用（无 HTTP 依赖）      │
│  domain/          纯逻辑：金额(cents)、订单状态机、交付策略、定价规则（无 ORM）      │
│  repositories/    查询封装：统一分页/过滤/权限范围注入                             │
│  workers/         arq 任务：sync / probe / remind / reconcile / close_expired    │
│  infra/           db(pool) / redis / crypto / logging(request_id) / metrics      │
└───────────────────────────────────┬─────────────────────────────────────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
   PostgreSQL 17               Redis 7.4                 上游供应商 API
   (主库 + 只读副本)        (限流/队列/缓存)              (只读适配器)
```

**关键变化点**：

| 维度 | 现在 | 目标 | 收益 |
| --- | --- | --- | --- |
| 路由 | 1436 行 / 70 端点 / 1 文件 | 9 个领域文件，单文件 ≤ 250 行 | 并行开发、冲突消失 |
| 业务逻辑 | 在端点里（事务、校验、审计混写） | 在 service，端点只做 IO | 可测试、可被任务复用 |
| 金额 | Float + cents + Decimal 三套 | **全链路整数分** + Decimal 计算 | 对账可闭合 |
| 定价 | 两套并行 | 单一真相源 `RetailPriceRule` | 价格不会打架 |
| 列表 | 全表返回 | 统一 `{items,total,page,page_size}` | 万级数据不卡 |
| 同步类操作 | 请求内串行 HTTP | 入队 → 返回 run_id → 前端轮询 | 不再超时 |
| 前端页面 | 1 个 2167 行组件 | 30+ 个组件，单文件 ≤ 300 行 | 可维护、可测试 |
| 观测 | 无 | request_id + 结构化日志 + /metrics | 故障 5 分钟内定位 |

### 3.3 分阶段实施计划

#### M0　止血（0.5-1 天）——必须最先做

| 任务 | 具体动作 | 验收 |
| --- | --- | --- |
| 修 9 个红测试 | `sync_regions` 加 `no_autoflush`（见 2.1） | `pytest` → 98 passed, 0 failed |
| 提交半成品 | 决定 `sync_supplier_catalog` 是完成还是回退，不要留在工作区 | `git status` 干净 |
| 分级探针 | 新增 `/readyz`（DB+Redis+迁移版本），compose 改指它 | 停 postgres 后 `/readyz` 返回 503，容器被标记不健康 |

> 为什么最先做：现在仓库处于"红灯 + 半提交"状态，任何后续工作在脏基线上都会放大风险。

#### M1　工程基线（1 周）

- CI：`push`/`PR` 触发 `pytest`（含 postgres service）+ `npm run build` + `npm run test`；红灯阻断合并
- 后端：引入 `ruff`（lint + format）+ `mypy --ignore-missing-imports`（先只查 `services/`、`domain/`）
- 前端：`eslint-plugin-vue` + `prettier`；`package.json` 全部锁死为 `^x.y.z`（删掉所有 `latest`）；删除未使用的 Pinia（或真正用起来）
- 日志：`structlog` 式 JSON 日志 + 中间件注入 `request_id`；`db.py` 加 `pool_pre_ping=True, pool_size=10, max_overflow=20`
- **产出**：任何 PR 都必须绿；任何人本地一条命令可复现 CI

#### M2　后端分层 + 金额统一（2-3 周，风险最高，单独排期）

按这个顺序，每步独立可上线：

1. **抽 service 边界**（无迁移，纯挪代码）
   `routes.py` 按领域拆成 `api/v1/{auth,catalog,order,delivery,finance,inbox,supplier,admin,public}.py`；
   端点内的事务/审计/校验下沉到 `services/`。认证、CSRF、Cookie 逻辑收敛到 `api/deps.py` 的依赖，端点不再手写。
2. **统一分页**（无迁移）
   抽 `repositories/pagination.py`，`/orders`、`/admin/orders`、`/lines`、`/customers` 全部改为 `page/page_size/total`；前端表格接分页参数（`InboxView` 已有实现可抄）。
3. **金额迁移**（有迁移，需灰度）
   - 迁移 `0022`：新增 `orders.total_cents / unit_price_cents`，回填 `round(total_amount*100)`，双写 1 个版本
   - `Customer.balance` 停写 → 读 `WalletAccount`；确认无调用方后迁移 `0023` 删列
   - 定价统一：`calculate_order_price` 改为查 `RetailPriceRule`，`PERIOD_FACTORS` 进表
4. **引入 worker**（新增组件）
   `arq` + Redis；先把 `/admin/suppliers/sync/*` 改为 `202 + run_id`，前端轮询 `SupplierSyncRun`；再补健康探测、到期提醒、超时关单、对账

> **风险控制**：M2 第 3 步金额迁移必须"双写 + 对账脚本 + 可回滚"。上线后跑 1 周对账（`sum(wallet delta)` vs `sum(order total)`），确认 0 差异再删旧列。

#### M3　前端重构（2-3 周）

1. **先拆 `WorkspaceView.vue`**（收益最大）：
   ```
   views/
   ├─ client/{Dashboard,Orders,OrderDetail,Lines,LineDetail,Renewals,Notifications,Profile,Security}.vue
   ├─ sales/{Workbench,Customers,CustomerDetail}.vue
   └─ admin/Dashboard.vue
   components/
   ├─ ui/        AppButton AppCard AppTable AppDrawer AppFormField AppToast AppEmpty StateBadge
   └─ business/  OrderStatusTag  LineHealthDot  MoneyText  Pagination  ConfirmDialog
   ```
2. **抽设计系统**：`styles.css` 按 token / base / component 三层拆分（拆完先不改视觉，纯结构），11 个视图的 `<style scoped>` 里的重复卡片/表格样式上移
3. **API 客户端分域**：`api/{auth,catalog,order,wallet,inbox,supplier,admin}.js`；用 `openapi-typescript` 从后端 schema 生成类型，避免前后端字段漂移
4. **测试补位**：现在只有 2 个前端测试（Checkout、SupplierPool）。给 3 个最关键的页面加组件测试 + 一份 Playwright 冒烟（登录 → 下单 → 交付 → 查线路）

#### M4　能力补齐（按业务价值排序，可与 M2/M3 并行）

| 优先级 | 能力 | 理由 |
| --- | --- | --- |
| 高 | 支付对账 + 悬挂单自动关闭 | 现在 `pending` 支付单永久挂着，全靠人工 |
| 高 | 线路健康真实探测（协议握手/出口 IP） | 当前仅 TCP 连通，不代表代理可用（文档已自认） |
| 中 | 到期提醒 + 自动续费通知 | 直接减少客户流失 |
| 中 | 审计检索/导出、数据保留策略 | 已有数据，缺出口 |
| 低 | 收件箱附件、i18n、暗色主题 | 体验增强 |

### 3.4 里程碑与验收标准（DoD）

| 里程碑 | 周期 | DoD |
| --- | --- | --- |
| M0 止血 | 1 天 | 测试 0 红；工作区干净；`/readyz` 故障时返 503 |
| M1 基线 | 1 周 | CI 强制绿；lint 0 error；依赖全部锁定；日志带 request_id |
| M2 后端 | 2-3 周 | `routes.py` ≤ 250 行；全部列表分页；金额全整数分且对账 0 差异；同步接口异步化 |
| M3 前端 | 2-3 周 | 无 >400 行组件；设计系统覆盖 80% 页面；前端测试 ≥ 15 个；OpenAPI 类型生成接入 |
| M4 能力 | 持续 | 对账日清、健康探测真实、告警可触达 |

### 3.5 不做什么（明确排除，避免范围膨胀）

- ❌ **不拆微服务**：单体 + 清晰模块边界足够，现在拆只会把复杂度乘以 5
- ❌ **不全量迁 TypeScript**：先给 `api/` 和 `domain` 类型，页面逐步
- ❌ **不改技术栈**：FastAPI + Vue 3 没问题，问题在组织方式不在选型
- ❌ **不动安全与账务核心逻辑**：那部分质量高于平均线，重构只搬位置不改语义
- ❌ **不做多租户**：当前单品牌运营，过早抽象是负债

### 3.6 风险登记

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 金额迁移导致对账偏差 | 中 | 高 | 双写 + 对账脚本 + 可回滚迁移 + 灰度一周 |
| 路由拆分引入权限回归 | 中 | 高 | 现有 98 个测试就是安全网；拆分 PR 强制全绿 + 补 IDOR 用例 |
| 前后端同时改导致联调地狱 | 中 | 中 | 后端先出 OpenAPI 契约，前端按契约并行 |
| 异步化改造破坏现有前端 | 低 | 中 | 保留同步端点 1 个版本，用 feature flag 切换 |
| 人力不足导致重构停滞 | 高 | 中 | M0/M1 必须完成（成本极低收益极高）；M2 起按模块切片，随时可停 |
