# 资源池 1（全球代理）原生静态住宅 API 接入

> 文档来源：<https://develop.quanqiudaili.com/>（Apifox，项目 5275065；`llms.txt` 可机器读取）
> 接入范围：**只接「静态住宅（原生）」，上游 `product_type_id=3`**；产品 2（普通非原生）只用于比价/历史数据。
> 状态：适配器读写能力已实现并有单测；**尚未接入采购状态机**（需要 `procurements` 表与支付触发）。

## 1. 基础约定

| 项 | 值 |
| --- | --- |
| 网关 | `https://admin.quanqiudaili.com` |
| 鉴权 | Header `token: <API Key>`（不是 Bearer） |
| Body | `application/x-www-form-urlencoded`（**不是 JSON**） |
| 成功判定 | `code=1`；`code=0` 为业务错误，`msg` 是原因 |
| 响应外层 | `{code, msg, time, data}` |

代码位置：`backend/app/suppliers/global_proxy.py`（类 `GlobalProxyAdapter`，旧名 `GlobalProxyReadOnlyAdapter` 保留别名）。

### 3.1 购买参数

| 参数 | 必填 | 说明 |
| --- | --- | --- |

## 4. 与 985 的关键差异

| | 资源池 1（全球代理） | 资源池 2（985） |
| --- | --- | --- |
| 购买返回 | **同步**，下单响应直接带 IP/账密/端口/到期 | 异步：先拿 `order_no`，再轮询 `order_result` |
| 时长 | 30/90/180/**360**（还有 7 天，不卖） | 30/60/90/180（无 360） |
| 指定段 | `appoint_ip[i][ip_str]`（前两段） | `spec_ip_segment_list` + `spec_ip_segment` |
| 退单 | 提交申请，**上游人工审核** | 按设计走退款流程 |
| 余额/钱包 | 无（账户余额在后台，无查询接口） | `/wallet/balance` |
| 幂等 | 无幂等键；重试有重复下单风险 | 预订单 + `order_no` 查询可复用 |

### 4.1 Key 录入与「立即同步」（已实现）

后台「资源池管理」页每张池卡片上都能单独录入该池的 Key（超级管理员）：

```
PUT  /api/admin/suppliers/{supplier_id}/credential   {"api_key": "..."}
GET  /api/admin/suppliers/{supplier_id}/credential   → {configured, source, encryption_ready}
DELETE /api/admin/suppliers/{supplier_id}/credential
```

- 密文按供应商隔离（AAD 带 supplier code），A 家的密文贴到 B 家解不开；
- 旧入口 `PUT /admin/suppliers/credential` 仍指向资源池 1，兼容现有页面；
- Key 只存密文，页面不回显、审计不落原文。

保存后点卡片上的「立即同步」，会按顺序即时执行（全部是同步 HTTP，不需要等定时任务）：

```
POST /admin/suppliers/sync/products
POST /admin/suppliers/sync/countries?product_type_id=3
POST /admin/suppliers/sync/cities?product_type_id=3
POST /admin/suppliers/sync/city-segments?product_type_id=3
```

完成后池卡片上的「商品/国家/城市/最近同步」立即刷新，客户选购页也能马上选到真实城市与号段。
资源池 2（985）暂不显示「立即同步」按钮——适配器与 Key/zone 还没接。

### 4.2 城市与号段怎么进客户目录（已实现）

资源池 1 的 `ipStrList` 是**按城市**给段的（前两段，如 `149.52`），而客户选购页的城市/号段
来自 `catalog_city_options`。中间用一次同步把它们接起来：

```
POST /api/admin/suppliers/sync/city-segments?product_type_id=3[&country_code=US]
→ countryList → cityList → ipStrList（每城市最多 40 段/页，默认 1 页）
→ 合并写入 catalog_city_options（data_source=supplier_global_proxy）
```

规则：

- **能匹配到已有城市码就合并**：`CITY_ALIASES` 把上游英文名（`Los Angeles`）映射到我们的
  城市码（`LAX`），已有 51 个城市都有别名；号段取并集、去重、按 500 字符上限截断；
- **匹配不上先停用**：上游城市（如 `Washington`）落库为 `is_enabled=False` + 备注「待归属」，
  不直接进客户下拉——城市命名归规范表，避免同一城市出现两个名字；
- **不覆盖手工配置**：只合并号段，不改手工维护的启停、展示名、排序；
- **幂等**：重复执行不会产生重复城市或重复段；
- 后台「商品与价格 → 城市与号段」有「从资源池1同步城市/号段」按钮，同步后可立即在选购页选到真实段。

注意：池 1 的段是**前两段**，比 985 的 /24 粗；同一个 `149.52` 下可能包含多个 /24。客户选段时
我们按"段"交付，不承诺具体 /24；若要更细，只能等 985 的 `spec_ip_segment_list`。

### 4.3 同步购买带来的幂等要求（重要）

上游没有幂等键，网络超时后**不能直接重试购买**——可能买两遍。落地时采购状态机必须：

1. 先落 `procurements`（状态 `pending`、记录订单号、数量、金额、请求体哈希）；
2. 调用购买前把 `remark` 写成我们的 `order_no`；
3. 超时/异常时**不重试购买**，先查 `accountList?remark=<order_no>`：
   - 查到子账号 → 视为成功，回写交付；
   - 查不到 → 标记 `unknown`，转人工确认后再决定重试或退款；
4. 同一客户订单永远只有一条采购单（`order_id + line_index` 唯一）。

## 5. 与我们模型的映射

| 上游 | 我们 |
| --- | --- |
| `country.code` | `regions.country_code` / `catalog_city_options.country_code` |
| `city.name` / `city_code` | 城市别名：池 2 是命名源，池 1 的 `Los Angeles` 通过 `catalog_city_aliases` 映射到规范城市码 |
| `ipStr`（前两段） | 客户可选号段（`requested_ip_segment`），比 985 的 /24 略粗，展示时需注明 |
| `sub_accounts[].id` | `customer_lines` 的上游子账号 id（续费/退单都靠它） |
| `order_product_buy_id` | 采购单/退单关联字段 |
| `timelen` | 我们的 `billing_days`：1→30、2→90、3→180、4→360 |
