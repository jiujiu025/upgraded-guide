# 线路自助升级（客户 / 销售端「更多选项」）

> 2026-11-26 玖夜提出：客户买完静态住宅 IP 后，线路行尾要有「更多选项」，
> 里面能升级成视频专线或直播专线，补差价，**到期日与静态住宅 IP 一致**。
>
> 本文是这次落地的口径与实现记录。管理员后台早就有升级入口
> （`docs/商品上下架与销售端升级设计.md` 之后的 `LineUpgradeDialog`），
> 这次补的是**客户自助**和**销售代客**两个入口，并把三处的算价口径收成一份。

---

## 1. 口径

| 项 | 规则 |
| --- | --- |
| 可升目标 | 同国家、同周期、单价高于当前的产品线（视频/社媒、直播手机/电脑） |
| 差价 | （目标单价 − 当前单价）× 原订单周期倍数，**按整周期，不按剩余天数** |
| 到期时间 | **完全不变**，升级不重新计时 |
| 交付 | 原住宅 IP 保留，视频/直播只加一层中转 |
| 生效时点 | 升级单收款后才切线路；先切再收，退款就回不去了 |
| 降级 | 不支持（差价 ≤ 0 直接拒绝） |
| 过期线路 | 不能升级，必须先续费（否则会出现「使用中但已过期」的矛盾数据） |

### 1.1 「视频专线」= 社媒运营专线

系统里没有独立的 `video` 分类，客户口中的「视频专线」就是 `social_media`
（社媒运营专线）。处理方式：

- 数据层不动，仍是 `social_media`；
- 客户/销售侧的升级弹窗把 label 显示为 **视频专线**，小字注明「社媒运营专线 · 商品全名」；
- 管理员后台保持原名，避免和商品管理对不上。

**已知不一致**：升级后订单的 `product_name` 是商品原名（如「美国 社媒运营专线 30天（升级）」），
客户在订单列表看到的是「社媒运营专线」。如果希望全站统一叫「视频专线」，
要改的是商品命名与官网文案，不是这次的功能改动。

### 1.2 为什么差价不按剩余天数

按剩余天数折算会出现「用了 25 天再升级只补 5 天差价」，等于让老客户免费换档；
而且每次升级金额都不同，对账与退款都算不清。按整周期差价，规则简单、可复算，
退款时也能原路退回。玖夜 2026-11-13 已确认这个口径，本次沿用。

## 2. 入口与交互

### 2.1 线路列表行尾「更多选项」

```
线路 / IP        地区 / 产品      开通 / 到期        状态    备注        ⋯
美国-LA01        美国             11-01 / 12-01     正常    添加备注    ⋯ ← 点这里
23.94.5.10       静态住宅IP
```

点开后是三个动作：

| 动作 | 行为 |
| --- | --- |
| 查看线路详情 | 跳 `/client/lines/:id`（销售端 `/sales/lines/:id`） |
| 续费这条线路 | 带上线路进续费页 |
| 升级线路 | 打开升级弹窗，副标题写明「视频专线 / 直播专线」 |

弹层用 `Teleport` + `position: fixed`，按点击位置实时算坐标，下方空间不够就向上翻。
**不用原生 `<select>` 或行内绝对定位**：`.data-table` 是 `overflow: hidden`，
行内弹层会被裁掉（与 `docs/商品上下架与销售端升级设计.md` 第 3 节同一个坑）。

### 2.2 线路详情页

底部操作区变成：`返回线路` ｜ `发起续费` `升级线路`。
返回和续费原来硬编码 `/client/...`，销售端点会把销售带去客户路由，这次一并改成按 workspace 取路径。

### 2.3 升级弹窗

- 当前产品与单价、到期日
- 可升级选项，**按差价从低到高**（先看到「视频专线 补 ¥35」，而不是直接看到直播的 ¥1040）
- 补差价金额由后端算，前端只展示
- 付款方式：客户三选一；销售只有「联系经理确认」
- 明确写「升级后到期日与当前线路完全一致」

## 3. 权限

| 入口 | 读选项 | 建单 | 付款方式 |
| --- | --- | --- | --- |
| 客户 `/customer/lines/{id}/upgrade` | 只看自己的线路 | 可以 | 余额 / 在线 / 联系经理 |
| 销售 `/sales/lines/{id}/upgrade` | 只看名下客户 | 可以 | **只能**联系经理 |
| 管理员 `/admin/lines/{id}/upgrade` | 全部 | 可以 | 三种 |

越界统一返回 404（与「线路不存在」同一文案，避免探测）。
销售不能替客户动余额——与代客续费同一原则，防止销售拿客户的钱做业绩。

## 4. 接口

```
GET  /api/customer/lines/{id}/upgrade-options
POST /api/customer/lines/{id}/upgrade
GET  /api/sales/lines/{id}/upgrade-options
POST /api/sales/lines/{id}/upgrade
GET  /api/admin/lines/{id}/upgrade-options     ← 原有
POST /api/admin/lines/{id}/upgrade             ← 原有
```

三个入口共用两个内部函数：

- `_line_upgrade_options_payload(db, line)`：候选产品线 + 差价
- `_create_upgrade_order(db, actor, customer, line, payload, created_via)`：校验 + 建单 + 审计

`created_via` 分别写 `self_service` / `sales_assisted` / `admin`，业绩仍按
`assigned_sales_id` 归客户所属销售。

建单返回的订单 `order_type = "upgrade"`，`renewal_line_id` 指向原线路，
`previous_product_id` 记住升级前产品（退款时按它切回）。

## 5. 支付与生效

```
建单（contact_manager） → status = pending_confirm → 管理员确认收款 → 切线路
建单（balance / online）→ status = pending_payment → 客户付清差价 → 自动切线路
```

- 余额支付：`POST /api/wallet/orders/{id}/pay-balance` → `settle_upgrade`
- 在线支付：回调成功后同样走 `settle_upgrade`
- 客户在弹窗里选了余额/在线，前端建单后直接跳账户余额页付差价
- 未付款不会改动现有线路
- 退款：`rollback_upgrade` 把线路切回 `previous_product_id`，到期时间不动

`settle_upgrade` 只在收款后执行，且以 `renewal_completed_at` 做幂等；
目标产品需要中转（社媒/直播）时线路状态置 `pending_transit`，不假装已开通。

## 6. 两个容易踩的坑（已处理）

1. **同一分类有多条重复商品行**
   候选列表按 `resource_category` 去重，只保留 id 最小的一条——下单时 `order_by(Product.id).limit(1)`
   取的也是这条。否则弹窗显示补 ¥35，建单却按另一条算出 ¥50。

2. **同一线路堆多张待处理升级单**
   除幂等键外，额外拦「该线路已有待处理升级单」；并发双击落到 `IntegrityError` 时
   按幂等键返回同一张单，不报 500。

## 8. 没做的

- 不做降级（业务未提，且涉及退款口径）
- 不做「升级到其他周期」（只换产品线，周期跟原单）
- 不做批量升级（单条线路操作，批量容易误伤）
- 不自动配置中转：升级后 `pending_transit` 仍由现有中转流程处理
