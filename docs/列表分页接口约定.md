# 列表分页接口约定

> 状态：订单类接口（`/customer/orders`、`/sales/orders`、`/admin/orders`、`/orders`）已按本约定改造。
> 线路列表（`/customer/lines`、`/lines`）仍是全量返回，原因见文末。

## 1. 为什么改

订单列表原来一律 `.all()`。客户只有几十单看不出问题，**管理员的 `/admin/orders` 是全站订单**：
上万单之后单次查询要扫全表，前端一次渲染几千个卡片，后台首屏直接超时。收件箱早就分了页
（`page/page_size/total`），订单只是没跟上。

## 2. 请求参数

四个接口参数一致：

| 参数 | 默认 | 约束 | 说明 |
| --- | --- | --- | --- |
| `page` | 1 | ≥ 1 | 页码从 1 开始，超界返回空 `items` 但 `total` 仍是真实总数 |
| `page_size` | 25 | 1–100 | 超过 100 直接 422，不静默截断 |
| `status` | — | ≤ 32 字符 | 精确匹配订单状态 |
| `keyword` | — | ≤ 64 字符 | 按订单号模糊匹配，`%` `_` 按字面量处理 |
| `customer_id` | — | ≥ 1 | 仅 `/admin/orders`，便于从客户 360 跳过来 |

排序固定为 `created_at DESC, id DESC`：同一秒创建的订单也要有稳定顺序，否则翻页会重复或漏行。

## 3. 响应结构

```json
{
  "items": [ { "order_no": "ORD000123", "status": "pending_confirm", "...": "同 OrderOut" } ],
  "total": 3120,
  "page": 2,
  "page_size": 25,
  "status_counts": { "pending_confirm": 12, "delivered": 3080, "completed": 28 }
}
```

`total` 与 `page_size` 一起决定页数；`items` 是当页记录。

## 4. `status_counts` 是"全量"，不是"当页"

这是最容易写错的一点：`status_counts` 在**加状态筛选之前**计算，覆盖当前角色能看到的所有订单。

原因在前端：状态下拉框的选项由它生成。若按当页统计，用户选了"已完成"之后下拉框里就只剩
"已完成"，再也切不回"待确认"——看起来像数据丢了。同理，客户工作台的"待处理订单"徽标也用它
计算；若按当页算，待处理订单跑到第 2 页就会从看板上消失。

## 5. 前端用法（`WorkspaceView.vue`）

- `orderStatus` 变化 → 页码重置为 1 → 只重拉订单，不重拉线路/通知（`loadOrders()`）；
- 列表渲染 `orders`（服务端已筛选），不再做客户端 `filter`；
- 翻页用 `.order-pager`（上一页/下一页 + `共 N 笔 · 第 x / y 页`）；
- 销售工作台每页 20 条，客户与管理员每页 25 条。

## 6. 为什么不顺手把线路也分了

线路列表撑着三个前端徽标：当前线路数、异常线路数、7 天内到期数，全部在客户端 `lines` 上算。
分页后这些数字会变成"当页统计"，跟订单的 `status_counts` 一样需要服务端补计数接口。
订单是量最大、最先出事的那张表，先做它；线路等真的有客户超过一页再改，届时把三个计数一起
放进接口响应，避免出现"看板数字随翻页变化"的中间状态。

## 7. 迁移影响

- 这五个接口的返回从**数组变成对象**，属于破坏性变更。仓内调用点已全部改完
  （`WorkspaceView.vue`、`InboxView.vue`、`tests/WorkspaceOutreach.test.js`）；
  若有外部脚本直接消费 `/api/customer/orders`，需同步改成读 `items`。
- 后端测试 `tests/test_order_pagination.py` 覆盖：总数、页大小上限、状态分布不塌陷、
  关键词字面量匹配、超界空页、销售/客户的角色隔离、管理员按客户过滤。
