# 数据库定时备份与恢复演练

- 状态：**脚本与单元已就绪，服务器尚未安装**（安装后需跑一次真备份 + 一次恢复演练才算闭环）
- 实现：`scripts/backup_postgres.py`、`deploy/systemd/99ipxin-pgbackup.*`
- 单测：`backend/tests/test_backup_postgres_script.py`
- 关联：`docs/99ipxin独立生产部署.md` 的「备份与恢复」

## 1. 为什么单独做这一项

全站只有一件事**做完就回不去**：数据库没了。代码可以回滚、镜像可以重建、Redis 里的限流窗口丢了也无所谓，
PostgreSQL 里的订单、收款、客户线路和审计日志丢了就是彻底没了。所以备份不能靠"升级前记得手动敲一次"。

原来的状态：`docs/99ipxin独立生产部署.md` 里只有一段手工 `pg_dump` 命令，没有人每天执行，也没有校验和保留策略。
等于**事实上没有备份**。

## 2. 目标与边界

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| 备份对象 | PostgreSQL `ops_platform` | Redis 只存限流窗口，可重建，不备份 |
| 频率 | 每天 03:30（Asia/Shanghai） | 停机错过会开机补跑（`Persistent=true`） |
| RPO | 24 小时 | 最坏丢一天数据；要更低必须上 WAL 归档，见 §12 |
| RTO | 1–2 小时 | 视备份体积与宿主机 IO，按演练实测修正 |
| 保留 | 近 14 天每天一份 + 更早的按周 8 份 | 约 22 份，压缩后通常几十 MB/份 |
| 存放 | `/secure/99ipxin-backups`（0700） | 与代码、容器卷分离；异机另算 |

## 3. 脚本做了什么

```
pg_dump -Fc  →  .part 临时文件  →  原子改名  →  pg_restore --list 校验核心表  →  sha256  →  按策略裁剪旧文件
```

几个刻意的设计：

- **先写 `.part` 再 `os.replace`**：半截文件永远不会被当成可用备份。
- **导出后立刻校验**：`pg_restore --list` 必须列出 `users / customers / orders / customer_lines / payment_orders / wallet_accounts / audit_logs / alembic_version`，
  缺任何一张即判失败。"文件在、但打不开或没数据"是最常见的备份事故。
- **体积下限 16 KB**：空库 dump 也有几十 KB，小于这个数说明导出没跑起来。
- **失败不裁剪**：只有本次备份 + 校验都通过，才按策略删旧文件。备份失败时历史一份不动。
- **保留按日期 + ISO 周分桶**，不是"删最旧 N 个"；未来时间戳的文件永不删除；最新一份永远保留。
- **并发锁**：`/secure/99ipxin-backups/.99ipxin-backup.lock`，崩溃残留超过 180 分钟可被接管。
- **不接触凭据**：密码由 compose 从 `.env.production` 注入容器，脚本只调 `docker compose exec`，从不读取或打印密钥。

退出码：

| 码 | 含义 | 处置 |
| --- | --- | --- |
| 0 | 成功 | — |
| 1 | 参数/环境错误（缺 `.env.production`、目录权限过宽） | 按提示修 |
| 2 | `pg_dump` 失败 | 看 journal 里 stderr 尾行；容器是否在跑、磁盘是否满 |
| 3 | 校验失败（dump 不可恢复） | **当作没备份**，立刻人工重跑并排查 |
| 4 | 异地转储失败（`--offsite-command`） | 本地备份有效，修异地通道 |
| 5 | 已有备份进程在跑 | 等它结束；频繁出现说明调度重复 |
| 6 | 最近备份已过期（`--check-only`） | 备份链路断了，当天必须处理 |

## 4. 服务器安装（一次性）

前提：仓库在 `/opt/99ipxin`，`.env.production` 已就位，`python3` ≥ 3.9（脚本只用标准库）。

```sh
# 1) 备份目录：只有 root 能读写
sudo install -d -m 0700 -o root -g root /secure/99ipxin-backups

# 2) 先空跑，确认命令拼得对，不碰数据库
sudo python3 /opt/99ipxin/scripts/backup_postgres.py --dry-run

# 3) 真跑一次，看 JSON 报告里的 size_bytes / verified_entries / sha256
sudo python3 /opt/99ipxin/scripts/backup_postgres.py

# 4) 装定时器
sudo cp /opt/99ipxin/deploy/systemd/99ipxin-pgbackup.service /etc/systemd/system/
sudo cp /opt/99ipxin/deploy/systemd/99ipxin-pgbackup.timer /etc/systemd/system/
sudo cp /opt/99ipxin/deploy/systemd/99ipxin-pgbackup-check.service /etc/systemd/system/
sudo cp /opt/99ipxin/deploy/systemd/99ipxin-pgbackup-check.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now 99ipxin-pgbackup.timer 99ipxin-pgbackup-check.timer
systemctl list-timers | grep 99ipxin
```

第 3 步必须亲自看到 `"status": "ok"` 且 `verified_entries` 大于 50，否则不要往下走。

## 5. 每天自动发生什么

- 03:30（±5 分钟随机抖动）执行 `99ipxin-pgbackup.service`：导出、校验、写 `.dump` + `.dump.sha256` + `.dump.json`、裁剪。
- 09:00 执行 `99ipxin-pgbackup-check.service`：只检查最近一份是否在 30 小时内，过期就以退出码 6 失败。

巡检回看：

```sh
systemctl status 99ipxin-pgbackup.service
journalctl -u 99ipxin-pgbackup.service -n 50 --no-pager
ls -l /secure/99ipxin-backups | tail -5
cat /secure/99ipxin-backups/ops_platform_YYYYMMDDTHHMMSSZ.dump.json
```

`systemctl --failed` 里出现这两个单元就是备份链路出事，按 §8 处置。

## 6. 异地与加密

本机备份挡不住"整台机器没了"。两种做法，任选其一并落实：

```sh
# A. 用脚本内置钩子（成功且校验通过后才执行）
python3 scripts/backup_postgres.py \
  --offsite-command 'rclone copy "$BACKUP_FILE" remote:99ipxin-backups/ && rclone copy "${BACKUP_FILE}.sha256" remote:99ipxin-backups/'

# B. 定时器里加 Environment + 同一参数，例如让 BACKUP_FILE 走 age 加密后上传
#    age -r <公钥> -o "$BACKUP_FILE.age" "$BACKUP_FILE"
```

要求：异机位置**不是**同一台宿主机、不是同一块云盘；密钥与备份分开保管；每月至少拉回一份验证可解密、可 `pg_restore --list`。

## 7. 恢复演练（每季度一次，必做）

**硬规则：演练用独立项目名、独立空卷、独立网络，绝不指向生产库。** 生产上直接 `pg_restore --clean` 是事故，不是演练。

```sh
# 0) 准备一个只放数据库的受限环境文件（不同项目名 + 不同子网）
#    .env.restore 里 DATABASE_URL / POSTGRES_PASSWORD 与生产完全不同
export P=99ipxin-restore

# 1) 起一个空库（只起 postgres，不起 api/worker/web）
docker compose -p $P --env-file .env.restore -f docker-compose.prod.yml up -d postgres

# 2) 恢复
docker compose -p $P --env-file .env.restore -f docker-compose.prod.yml exec -T postgres \
  pg_restore -U ops_platform -d ops_platform --clean --if-exists --no-owner \
  < /secure/99ipxin-backups/ops_platform_YYYYMMDDTHHMMSSZ.dump

# 3) 验收（缺一条就算演练失败）
docker compose -p $P --env-file .env.restore -f docker-compose.prod.yml exec -T postgres \
  psql -U ops_platform -d ops_platform -c "select version_num from alembic_version;"
docker compose -p $P --env-file .env.restore -f docker-compose.prod.yml exec -T postgres \
  psql -U ops_platform -d ops_platform -c "select (select count(*) from orders) orders, (select count(*) from customer_lines) lines, (select count(*) from audit_logs) audits;"
```

验收清单：

1. `alembic_version` 与生产当前版本一致；
2. `orders / customer_lines / payment_orders / audit_logs` 行数落在生产同量级（差异需能解释）；
3. 用只读账号跑一次应用读接口（例如 `GET /api/public/catalog`）能返回数据；
4. 记录本次耗时，更新 §2 的 RTO。

演练结束只清理**该项目**的资源：`docker compose -p 99ipxin-restore down -v`。

## 8. 故障处置

| 现象 | 先看 | 处置 |
| --- | --- | --- |
| 定时器没跑 | `systemctl list-timers` | `systemctl enable --now 99ipxin-pgbackup.timer` |
| 退出码 2 | `journalctl -u ...` 尾行 | 容器在跑吗？`/secure` 满了吗？`docker compose ps` |
| 退出码 3 | `.dump.json` | 立刻人工重跑一次；连续失败按"当前无可用备份"上报，禁止升级 |
| 退出码 4 | 异地通道 | 本地备份有效，当天修好异地 |
| 退出码 5 | 进程列表 | 检查是否配了两套调度（cron + systemd 重复） |
| 09:00 巡检失败 | 03:30 那次日志 | 按上面对应退出码处理，当天闭环 |

## 9. 与升级流程的衔接

升级（`alembic upgrade head`）前固定三步：

```sh
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T api alembic current
python3 scripts/backup_postgres.py --check-only        # 必须有新鲜备份
python3 scripts/backup_postgres.py                     # 再手动补一份"升级前"备份
```

升级前这份会自然进入保留策略，不会被提前裁掉（最近 14 天全留）。

## 10. 已知限制

- **RPO 24 小时**：没有 WAL 归档，做不到按时间点恢复。若业务要求 RPO < 1 小时，应改用 pgBackRest / wal-g 做增量 + 归档，这套脚本可作为日全量兜底。
- **备份在宿主机本地**：磁盘损坏或误删 `/secure` 会一起丢，必须做 §6 的异地转储。
- **未做自动恢复演练**：演练仍是人工季度动作。自动化恢复有"误连生产"的风险，暂不脚本化。
- **未接告警通道**：目前靠 `systemctl --failed` + 每日巡检退出码。接入通知渠道时，把巡检单元的 `OnFailure=` 指到告警脚本即可。
