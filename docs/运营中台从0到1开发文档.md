# 玖玖云运营中台从 0 到 1 开发文档

> 当前版本：第二阶段后端闭环版（2026-10-23）。本文严格区分已完成、部分完成和后续规划，所有客户、销售和管理员查询都必须经过后端权限过滤。

## 1. 产品目标

运营中台把官网获客、客户自主购买、销售跟进、订单确认、线路手动交付、健康检测和到期续费放进同一条可审计链路。客户可自助查看产品、订单和线路；销售只处理自己的客户；管理员处理全量业务；超级管理员管理权限、价格、财务和安全策略。

## 2. 系统边界

已纳入：客户自主注册、认证、角色、客户与销售归属、产品与地区、节点和客户线路、订单快照、单订单多线路手动交付、人工确认续费、健康摘要、通知和审计模型。当前不伪装实现在线支付、余额扣款、退款、自动上游采购、完整代理握手、附件会话和财务结算。

## 3. 用户角色和权限矩阵

| 角色 | 页面 | 数据范围 | 写操作 | 二次确认/审计 |
| --- | --- | --- | --- | --- |
| 超级管理员 | 全部后台 | 全量 | 用户、价格、线路、订单、权限 | 删除、停用、交付、价格变更；必须审计 |
| 管理员 | 客户、订单、线路、健康、通知 | 全量 | 客户、确认、手动交付、健康处理 | 交付、停用；必须审计 |
| 销售 | 工作台、客户 360、收件箱 | 仅自己负责客户 | 创建客户、跟进、确认订单 | 转派和敏感操作；必须审计 |
| 客户 | 客户中心、我的订单、我的线路 | 仅本人 | 下单、续费申请、消息 | 支付和续费需确认；记录业务日志 |

后端以 JWT 中的用户身份为唯一来源，销售通过 `sales_id` 作用域过滤，客户通过当前用户绑定范围过滤，禁止使用前端隐藏按钮作为权限控制。

## 4. 站点和工作台结构

官网展示产品与地区；客户中心提供购买、订单、我的线路、订阅地址和通知；销售工作台展示待跟进、到期、异常线路、待回复和提成；管理员后台提供客户、订单、交付、线路、健康和通知；超级管理员增加账号、价格、支付、财务、系统设置和审计。

## 5. 客户自主购买流程

客户通过公开注册接口创建账号和绑定客户档案，销售归属默认留空。随后浏览产品 → 选择地区、数量与周期 → 创建订单 → 管理员人工确认 → 运营逐条手动交付 → 订单经过待交付、部分交付、全部交付状态 → 客户在我的线路查看真实交付数据。没有真实订阅数据时接口返回空值，不生成假链接。

## 6. 订单、支付与交付

订单状态包括 `pending_confirm`、`pending_delivery`、`partially_delivered`、`delivered`、`renewal`、`processing`、`completed` 和 `cancelled`。普通订单按数量逐条交付，每条线路通过 `customer_lines.order_id` 关联订单；原子交付计数禁止重复或并发超量，全部数量交齐后才进入 `delivered`。`pending_payment`、`paid`、退款类状态仅为后续支付流程保留，当前没有在线支付、余额扣款或退款实现。敏感凭据不写入日志或通知正文。

## 7. 续费管理

客户发起续费时只创建 `renewal` 订单，不修改线路。管理员调用人工完成接口并显式确认续费条件后，系统从 `max(原到期时间, 当前时间)` 起延长周期，同时提交订单完成状态、线路到期时间、审计和客户通知。重复完成同一订单不会再次延长。自动扣款和在线支付未实现。

## 8. 线路健康架构

探测链路：DNS 解析 → TCP 连接 → TLS 握手 → 协议/Reality 完整探测 → 代理出口 IP 和国家 → 静态住宅 IP 可用性。健康采样写入节点状态和事件；连续失败/恢复阈值、并发、超时、维护窗口、告警静默、确认、转派和受影响客户计算由健康服务扩展。

第一阶段已实现手动 TCP 基础检测、healthy/offline/unknown 状态、开放故障事件、恢复关闭事件、健康摘要及销售/客户可见范围过滤。协议握手、出口检测、维护窗口、静默和告警渠道是部分完成/后续能力。

## 9. 健康大屏

页面展示总线路、正常、离线、平均延迟、故障列表和线路状态矩阵；管理员可刷新采样。销售只能看到自己客户的线路，客户只能看到本人线路，不展示探测堆栈、内部凭证和其他客户信息。区域矩阵、产品统计、事件抽屉和一键维护将在第四阶段补齐。

## 10. 客户 360

资料、负责人、标签、等级、生命周期、订单、线路、续费、余额支付、收件箱、跟进任务、联系记录、健康异常和审计记录统一以客户为主索引。当前实现基础资料和归属字段，其他页签留有模型/API 扩展位置。

## 11. 销售管理

支持自己客户、客户创建和订单确认的基础闭环。客户分配、按地区/权重轮询、转派历史、跟进任务、到期提醒、异常线路、待回复、销售额和提成统计为第二阶段和第六阶段。

## 12. 收件箱

系统通知与人工会话分离。人工收件箱已实现文字会话、分页列表、消息分页、双侧未读、状态处理、负责人和订单/线路关联；附件仍未实现。

API 路径：

| 方法与路径 | 请求 | 响应 | 权限 |
| --- | --- | --- | --- |
| `POST /api/inbox/threads` | `subject`、可选 `related_order_id`、`related_line_id` | 会话对象 | 仅客户；客户身份和负责人由后端确定 |
| `GET /api/inbox/threads` | `status`、`customer_id`、`assigned_sales_id`、`order_id`、`line_id`、`keyword`、`page`、`page_size` | `{items,total,page,page_size}` | 客户仅本人，销售仅负责客户，管理员全量 |
| `GET /api/inbox/threads/{id}` | 无 | 会话对象 | 按角色数据范围校验 |
| `GET /api/inbox/unread-count` | 无 | `{unread_count}` | 客户统计客户侧未读；销售和管理员统计各自权限范围内的员工侧未读 |
| `GET /api/inbox/threads/{id}/sales-options` | 无 | `[{id,display_name}]` | 仅管理员；返回该会话客户当前可用的有效销售候选 |
| `GET /api/inbox/threads/{id}/messages` | `page`、`page_size` | `{items,total,page,page_size}` | 按角色数据范围校验 |
| `POST /api/inbox/threads/{id}/messages` | `content`，最多 4000 字 | 消息对象 | 客户本人、负责销售、管理员 |
| `POST /api/inbox/threads/{id}/read` | 无 | `{ok,updated}` | 按当前角色标记客户侧或员工侧已读 |
| `PATCH /api/inbox/threads/{id}` | 可选 `status`、`assigned_sales_id` | 更新后的会话对象 | 销售可改自己范围内状态；负责人仅管理员可改 |

会话对象包含 `customer_id`、`customer_name`、`assigned_sales_id`、`assigned_sales_name`、主题、`open/pending/closed` 状态、关联订单/线路、最后消息时间和客户侧/员工侧未读数。名称由后端随列表和详情一次返回，前端无需读取全量客户或用户数据。消息对象包含发送者角色和显示名、正文、双方已读时间及创建时间，不允许前端指定发送者。关闭的会话不能继续发送，销售可在自己的客户范围内重开；管理员设置负责人时，目标必须是该客户当前的有效销售。销售候选接口只允许管理员访问，客户和销售均返回 403。

消息正文入库前拒绝密码或 Token 赋值、代理协议链接、HTTP 链接和节点地址格式。通知只发送“有新消息”等通用内容，不复制消息正文；发送消息、标记已读和状态/负责人变化都写入审计。

## 13. 通知事件

订单创建、线路开通、线路异常/恢复、即将到期、续费完成和收件箱新消息均采用事件名驱动。通知只写必要业务内容，敏感字段和收件箱正文不进入通知。付款成功、余额变动等事件等待真实支付能力接入后实现。

## 14. 数据库模型

当前模型包含 `users`、`customers`、`regions`、`products`、`nodes`、`customer_lines`、`orders`、`notifications`、`health_incidents`、`audit_logs`。订单保存价格、数量、周期、产品和地区快照、负责人、状态时间、已交付数量及续费完成时间；客户线路可关联来源订单。支付、独立续费流水、收件箱和财务表留到后续阶段。

## 15. API 设计

第二阶段新增并已实现：`POST /api/public/register`、公开产品/地区/价格预览、客户订单和线路接口、客户续费申请、销售工作台接口、管理员订单确认/取消/逐条交付，以及 `POST /api/admin/orders/{id}/complete-renewal`。收件箱接口统一位于 `/api/inbox/threads`，覆盖会话、消息、已读、筛选和处理状态。公开注册固定创建 `customer` 角色，用户和客户档案在同一事务绑定。

## 16. 安全设计

JWT 会话、bcrypt 密码、密码强度校验、登录失败锁定、CORS 白名单、后端 RBAC、资源范围过滤、审计写入和敏感数据不入日志均已实现。公开注册和登录按可信代理解析后的客户端 IP 使用 Redis 共享限流；生产环境 Redis 不可用时拒绝启动或关闭认证入口，不回退到单进程内存。种子脚本不再创建演示销售或客户，管理员密码必须通过环境变量显式配置。

## 17. 审计日志

高风险动作记录操作者、动作、资源类型、资源 ID、时间和脱敏详情。当前已覆盖客户创建、线路交付和订单确认；审计检索页面与导出在第六阶段。

## 18. 部署架构

开发环境 SQLite + FastAPI + Vite；生产环境 PostgreSQL + FastAPI + Nginx + Docker Compose。配置只从 `.env` 读取，数据库目录和日志目录挂载卷。Windows 使用 PowerShell，Linux 使用 bash，命令保持一致。

## 19. 开发里程碑

已完成阶段包括基础结构、认证、角色、客户/销售范围、产品地区、订单、按数量交付、人工续费确认、基础健康、通知、审计及人工文字收件箱。后续阶段包括完整健康探针、附件上传、财务、提成、安全策略和生产运维。

## 20. 测试方案

后端运行 `python -m pytest -q`，覆盖注册绑定、IDOR、销售范围、价格篡改、人工续费幂等、多数量并发交付，以及收件箱两名销售与两个客户的跨归属越权、管理员全量读取、负责人调整权限、筛选分页、状态和权限范围未读统计。前端继续运行 `npm run build`。

## 21. 验收标准

可迁移数据库、可登录、四角色权限边界可验证、客户可下单、管理员可确认并手动交付、线路可查询、健康摘要可见、销售/客户看不到越权数据、通知和审计可追溯、Windows/Linux 启动命令清晰。

## 22. 风险和暂不实现

完整代理探测依赖 sing-box 或同类内核；在线支付需供应商密钥与回调验签；IP 凭证加密需生产密钥托管；自动采购依赖上游 API；人工会话附件会增加存储和安全面。上述能力未在第一阶段伪装完成。

## 23. 当前已知问题

开发和单元测试允许使用进程内限流，生产固定使用 Redis 共享限流；健康检测目前为 TCP 基础检测，不代表代理实际可用；金额仍为 `Float`，将在财务阶段统一迁移为精确金额类型。

## 24. 启动与默认账号

```powershell
cd D:\99IPxin\backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
New-Item -ItemType Directory -Force data | Out-Null
alembic upgrade head
python -m app.seed
uvicorn app.main:app --reload --port 8000
```

执行种子脚本前必须在 `.env` 中显式配置 `ADMIN_PASSWORD`，系统不提供默认密码，也不会创建演示销售或演示客户。客户账号通过 `POST /api/public/register` 自主注册。前端另开终端运行 `cd D:\99IPxin\frontend; npm install; npm run dev`。
