# 订单体系归并方案

> 状态：**待拍板**。本文只定方向与迁移步骤，不改代码、不改表结构。
> 关联：`docs/自动采购与自动交付实现.md`、`docs/销售代客下单设计.md`、`docs/定价收敛实施方案.md`。

---

## 1. 现在有两套「订单」，但只有一套能走完

同一个 `orders` 表，靠 `source_type` 分成两条互不相通的生命周期：

| | `owned`（官网/代客下单） | `resource_pool`（后台资源池下单） |
| --- | --- | --- |
| 谁创建 | 客户自助 / 销售代客 / 管理员代开 | 仅管理员，`/admin/order-center` |
| 价格 | `pricing_service.quote()`，月价 × 周期 | 同一套定价函数（已统一） |
| 货源 | 采购时按分类 + 国家现选（实际固定池 1） | 创建时锁定供应商商品 / 国家 / 网段 / 报价快照 |
| 能付款吗 | 能（余额 / 在线 / 线下登记） | **不能**，三个支付入口全部 409 |
| 能采购吗 | 能，付款后自动触发 | **不能**，`auto_procure_order` 第一行就跳过 |
| 能退款吗 | 能 | **不能**，退款登记 404 |
| 能续费吗 | 能 | 不能 |
| 实际用途 | 真实收入 | 一张「打算这么买」的记录 |

结论：这不是两套订单体系，是**一条真实链路 + 一个停在半路的原型**。`resource_pool` 订单现在既不能收钱也不能交付，留在后台只会让人误以为功能已经存在。

---

## 2. 三个方向

| 方案 | 做法 | 成本 | 代价 |
| --- | --- | --- | --- |
| **A. 归并成一条生命周期** | `source_type` 降级为「货源来源」标记；资源池订单和普通订单一样可付款、可退款、可交付；采购按订单上的货源快照路由，没有快照就按供给规则现选 | 中（支付 5 处判断 + 采购 1 处 + 权限回归 + 测试） | 需要明确「快照锁定后，上游缺货怎么办」——不能静默换源 |
| **B. 降级为线下工单** | 明确它不是订单：改名「资源池报价单」，不进入支付/交付/财务统计，只做内部选源记录；真正的交付走代客下单 | 小（文案 + 列表过滤 + 状态机收口） | 管理员仍然不能为客户锁定特定网段下单；特殊需求只能线下处理 |
| **C. 直接删掉** | 移除后台资源池下单入口与 `resource_pool` 分支 | 最小 | 丢掉「按供应商快照下单」的能力；将来要做特殊选源得重写 |

**推荐：A。** 理由：

1. 业务上确实存在「客户要某个城市的某个段」的场景，普通下单只到城市级；资源池快照是唯一能锁定到段的结构，删掉可惜。
2. 归并的成本主要是**删判断**，不是加逻辑：支付/退款/采购里现在各有 3-5 处 `if source_type == "resource_pool"`，归并就是把这些分支删掉，再补一条「按快照路由」。
3. B 会让后台继续存在一个「看起来能下单、其实不能」的入口，和现在的毛病一样，只是换了名字。

---

## 3. A 方案的边界（先定这四条，否则不要动）

1. **快照是承诺，不是建议**：订单带了 `supplier_segment_snapshot_id`，采购就必须按这个段买；买不到 → 失败转人工 + 通知客户改选，**不允许**静默换城市/换段。
2. **资源池订单仍然只能管理员创建**：客户不能自助选供应商，供应商是实现细节。
3. **价格仍走 `pricing_service`**：快照里的 `supplier_cost` 只用于毛利，不参与售价。
4. **续费不继承货源快照**：续费按当时的城市/段重新采购；原段没了就转人工，不承诺「永久同段」。

## 4. 迁移步骤（每步独立可上线）

### 第 1 步：让资源池订单能收钱（不改表）

- 删除 `finance_routes.py` 中 5 处 `source_type == "resource_pool"` 的拒绝：
  `_record_paid_order`、`pay_order_with_balance`、`pay_order_online`、回调入账、线下收款登记、退款登记。
- `is_payable_order()` 对 `pending_payment` 已返回真，不需要改。
- 回归：`tests/test_payment_and_resource_order.py` 里「资源池订单不能支付」的用例改为「可以支付」，并补一条「支付后进入 `paid`」。

### 第 2 步：采购按快照路由

- `auto_procure_order` 去掉 `source_type == "resource_pool"` 的提前返回。
- 请求参数优先取订单快照：
  - `country` ← `supplier_region.country_code`（没有则 `region.country_code`）
  - `city` ← `supplier_region.city_name`
  - `segment` ← `supplier_segment_snapshot.cidr`
  - `timelen` ← `billing_days`
- 快照过期不阻塞采购（快照是下单时的承诺，不是库存预留）；但采购失败要在 `procurements.error_message` 里写清「快照段已不可用」。
- 回归：新增「资源池订单支付后按快照段采购」用例，断言 `buy_static_ip` 收到的 `segments` 与快照一致。

### 第 3 步：统一列表与状态口径

- 后台订单列表已包含两种来源，保持；补一个 `source_type` 筛选与列展示（现在只有线路列表有）。
- 财务导出按 `source_type` 分组统计，避免资源池订单混入官网收入时口径不清。
- 客户中心现在就能看到自己名下的资源池订单（`_require_scoped_order` 按 customer 限权，不按来源过滤）。归并后应明确展示「待付款」并给支付入口；若拍板选 B（内部报价单），则要在客户订单列表里过滤掉 `resource_pool`。

### 第 4 步（可选）：统一创建入口

- `admin_create_resource_order` 改为调用 `order_service` 的建单函数，只多传货源快照；删除重复的价格计算与通知代码。
- 这一步纯重构，放在 1-3 步稳定之后。

## 5. 验收标准

- [ ] 资源池订单可以用余额、在线、线下三种方式收款，收款后订单进入 `paid` / `pending_delivery`
- [ ] 付款后自动采购按快照段下单；快照段不可用时转人工，不换段
- [ ] 资源池订单可登记退款，退款后状态与普通订单一致
- [ ] 财务导出能区分 `owned` / `resource_pool`，合计口径写清楚
- [ ] 客户中心能看到自己要付款的资源池订单（若产品决定展示）
- [ ] 全量后端测试绿；新增至少 4 条回归（支付、采购路由、退款、快照失效）

## 6. 需要拍板的一件事

**资源池订单要不要对客户可见并可付款？**

- 要（推荐）：按 A 执行，它就是「管理员替客户锁定了货源的订单」，客户正常付款。
- 不要：走 B，把它降级为内部报价单，不要让它出现在客户的订单列表里，也不要给它支付按钮。

在这个问题确认前，不改代码——否则做出来的东西仍然是一个半成品。
