## 3. 池级上架：官网到底卖谁的东西（决策 1）

### 3.1 为什么需要这一层

现在官网的可见性是「产品线 × 国家」（`catalog_listings`），没有"这批货来自哪个池"的概念。
两个池同时用之后会出现三种情况：

1. 同一个国家两个池都有货 → 需要决定官网展示哪一个（或都展示、按价格/库存排序）；
2. 只有池 2 有货 → 池 1 下架，官网仍应能买到（由池 2 供）；
3. 池 1 的某国要停（成本涨了/上游限流）→ 只下架池 1，不能把整个国家下架。

所以可见性必须带池维度：**「池 × 产品线 × 国家」三键**。

### 3.2 模型（已实现）

`catalog_listings` 增加 `pool_id`（空 = 平台级，对所有池生效），唯一性用两个部分索引表达：
全局格子 `(line_code, region_id) WHERE pool_id IS NULL`、池级格子
`(pool_id, line_code, region_id) WHERE pool_id IS NOT NULL`。

**默认规则：没有记录 = 下架。** 管理员不点，官网就不出现——包括新国家、新商品、新同步来的池货。

```
官网某个（产品线, 国家）可见 =
    ∃ 记录：status=listed 且（pool_id 为空 或 属于某个已启用池）
  且 该格子有在售商品（商品被停用时跟随隐藏，不展示"暂无报价"假入口）

池视图（后台）：
   池 P 的格子状态 = P 自己的记录 → 没有则回退平台级记录 → 都没有 = 未上架

路由候选（后续阶段）= 可见池 ∩ 客户选择 ∩ 库存新鲜 ∩ 毛利达标
```

两种"没有报价"要区分开：

| 情况 | 上架后表现 |
| --- | --- |
| 该国从来没配过商品 | 展示「暂无报价」，不可下单（管理员有意为之） |
| 配过商品但被停用 | 跟随商品一起隐藏，不给客户一个假入口 |

后台「商品与价格 → 官网可见性」从一张二维表升级为**按池切换的三维表**：
顶部选池（池 1 / 池 2 / 全部），表格仍是「国家 × 产品线」，格子状态：在售 / 已下架 / 无报价 / 无覆盖。
“全部”视图只读，用于对比两个池的覆盖差异；改动必须在具体池上进行，避免"改了一个以为改了两个"。

### 3.3 客户看到什么

- 客户只看到「国家 + 城市 + 价格」，看不到池；
- 同一个国家两个池都在售时，**价格仍按国家+周期一份**（不因池而变），差异体现在路由成本；
- 订单落 `pool_id` 与 `supplier_id` 快照，用于排障与对账，不展示给客户。

## 4. 城市命名归资源池 2（决策 3）

### 4.1 规则

1. **规范城市码 = 资源池 2（985）的城市码**。`catalog_city_options.city_code` 以池 2 为准；
2. 池 1 同步城市时，先按别名表匹配到规范码；匹配不上 → 进「待归属城市」队列，**不直接对客户开放**；
3. 管理员在待归属里绑定一次，系统记住 `(supplier_id, upstream_city_ref) → canonical_city_code`；
4. 池 2 改名（上游把 `Los Angeles` 改成 `LA`）时，只改别名，不改客户看到的城市码；
5. 池 2 没有、池 1 有的城市：允许存在，但需要管理员点「确认上架」才进客户目录，
   并在后台标注「仅池 1 覆盖」。

### 4.2 为什么要指定一个源

两家命名一定对不齐（`Los Angeles` / `LA` / `Los Angeles, CA`）。如果两边各自维护，
客户会在同一国家看到两个"洛杉矶"，订单、报表、续费全对不上。指定池 2 为源，
池 1 做映射，是成本最低且不会漂移的做法。

## 5. 路由算法（v2）

```
输入：product, region(country), quantity, 客户选择(city_code?, segment?), 池级上架状态

1. 候选 =
     池成员(enabled, status=active)
   ∩ 该池在 (line, region) 上架
   ∩ supply_rules(product, region).enabled
   ∩ 客户选了城市 → supplier_city_offers(city, active, fresh)
   ∩ 客户选了段   → supplier_segment_offers(segment, available)
   ∩ 成本 ≤ 客户价 × (1 - 最低毛利率)   ← 决策 5

2. 排序：池内 priority → 成本升序 → 供应商 id（稳定排序，便于复现）

3. 结果：
   - 有候选 → 写路由快照（pool_id / supplier_id / 城市 / 段 / 成本），支付成功进采购
   - 无候选但存在"覆盖该城市/段、仅因毛利不达标"的供应商 → 转人工审批（不静默亏钱）
   - 完全无覆盖 → 下单阶段 422，提示改选
```

### 5.1 客户选择与路由（不变）

| 客户选择 | 允许 | 不允许 |
| --- | --- | --- |
| 未选城市/段 | 换城市、换池、换供应商 | — |
| 只选城市 | 换池、换供应商，必须同城 | 换城市 |
| 城市 + 号段 | 只有能精确交付该段的供应商 | 换段、换城市 |
| 只选段 | 先反查唯一城市，再按上一行 | 多城时自动挑一个 |

**换供应商/换池 = 内部决策，客户不感知；换城市/换段 = 违约。**

## 6. 一单多线允许拆单（决策 4）

### 6.1 拆单规则

`quantity > 1` 时按以下顺序装箱：

1. **优先整单同池同城**：一个候选能吃下全部数量 → 不拆；
2. 吃不下时按候选依次装箱（同池优先、成本低的优先），同一单可产生多条采购单；
3. 客户选了号段时，**不能拆到不同号段**：只能在同一段内找多个供应商/多份库存；
   做不到就整单失败，不做"一半给你一半换段"；
4. 客户只选城市时，可拆给同城不同供应商，但每条线路的城市必须一致；
5. 每条线路独立交付、独立到期、独立续费；退款按线路粒度（未交付的那几条退）。

### 6.2 数据结构影响

- `procurements` 从「一单一条」改为「一单多条」，唯一键改为 `(order_id, line_index)`；
- `customer_lines` 增加 `procurement_id` / `supplier_id`，交付时按线路回写；
- 订单增加 `delivered_quantity`（已有）与 `delivery_summary`（如 "2 条已交付 / 1 条采购中"）；
- 通知文案必须能说清"部分交付"：不能笼统说"已开通"，否则客户以为三条都好了。

### 6.3 不建议的做法

- 不做跨城市凑数（客户选洛杉矶，不能拿纽约的补）；
- 不对客户展示"这批来自不同上游"（内部成本信息）；
- 不在支付前锁多家库存（预下单锁库存会占坑，只对"库存个位数"的国家按需开启）。

## 7. 毛利护栏（决策 5）

- 阈值：**最低毛利率 20%**，默认值来自配置，管理员可在后台改（运行时设置，不用重启）；
- 判定：`供应商成本 ≤ 客户价 × (1 - 20%)` 才允许自动采购；
- 不达标：订单照常付款成功，但采购单进「待人工审批」，同时通知管理员与销售；
- 审批页显示：客户价、成本、毛利率、两家对比、建议动作（换池 / 改价 / 取消退款）；
- 改价入口仍走「国家周期售价」，不要在采购单上直接改客户价（会造成两套价格）。

实现方式：新增 `system_settings`（key/value/updated_by）或在现有配置表上加一列；
优先级低于路由本身，和阶段 2 一起做。当前配置项 `MIN_ORDER_MARGIN_PERCENT=20` 先兜底。

## 12. 还需要你提供 / 确认的

1. **旧上游的下单 API 文档**：路径、鉴权（header/签名）、下单返回（是否直接给 IP）、
   订单查询、取消/退款、回调方式。没有这些只能先按"未知能力"处理，适配器写不出来。
2. **旧上游是否支持指定城市/号段**：决定它能不能进"选段"路由，还是只能接自动分配的单。
3. **池级上架的默认策略**：新国家/新城市默认"两池都上架"还是"只在池 2 上架、池 1 手动开"？
   建议默认只在主力池（池 2）上架，池 1 由管理员按需开，避免客户被路由到不熟悉的池。
4. **拆单的客户感知**：部分交付时是否允许"先交付已拿到的线路、剩余继续采购"？
   建议允许，但订单状态显示"部分交付"，并给客户明确的预计时间。
