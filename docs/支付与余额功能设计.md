# 支付与余额功能设计

## 1. 范围与资料

本设计依据裕汇通公开 [V1 旧版 API 文档](https://pay.suisuizhifu.com/doc/v1_legacy_api.html) 和商户 [API 信息页](https://pay.suisuizhifu.com/user/#/account/api-info) 的字段说明，并结合玖玖云现有用户、订单和余额模型。当前实现和验收状态见文末；在线支付仍处于关闭状态。

文档确认 V1 使用 `application/x-www-form-urlencoded`、JSON 返回和 MD5 签名；支付请求为 `POST https://pay.suisuizhifu.com/mapi.php`，成功响应可返回 `payurl`、`qrcode` 或 `urlscheme` 其中之一。异步通知使用 GET 参数，只有 `trade_status=TRADE_SUCCESS` 表示支付成功；接收方必须验签，且应以 `success` 响应确认收到通知。单笔订单查询使用 `act=order`，可按商户订单号或平台订单号查询。退款接口要求商户后台开启“订单退款 API”。

商户 API 信息页可见 V1 的商户 ID、MD5 密钥，以及 V2 RSA 签名设置。由于本轮实际打开的 API 信息页将密钥显示在页面上，该密钥应视为已暴露；建议商户本人在该页面重置 MD5 密钥后再接入，重置动作由商户本人完成。不要把密钥粘贴到聊天、工单、Git 或文档中。

## 2. 管理员支付管理

在超级管理员后台新增“支付管理”，分为“支付通道”和“充值订单”两个视图。普通管理员、销售、客户不得读取或修改商户密钥。

### 首期需要填写

| 配置项 | 来源与用途 |
| --- | --- |
| 启用状态 | 默认关闭；完成回调部署及商户联调后由超级管理员启用 |
| 接口版本 | 首期按用户提供的 V1 文档接入；若服务商提供 V2 文档，优先评估 RSA 方案 |
| 商户 ID（`pid`） | 裕汇通 API 信息页提供 |
| V1 MD5 密钥 | 裕汇通 API 信息页提供；只写入后端加密存储，保存后不回显 |
| 可用支付方式 | 仅从商户实际开通的通道中勾选，使用文档代码，如 `alipay`、`wxpay`；不得假设示例通道均已开通 |
| 充值限额与预设金额 | 玖玖云业务设置；服务端校验最小、最大单笔金额和每日限额 |

支付域名固定为官方 HTTPS 地址，不允许后台配置任意请求 URL，避免凭据被导向其他主机。`notify_url` 和 `return_url` 由玖玖云后端根据正式 HTTPS 域名生成，页面不让管理员手工填写。当前生产域名为 `https://1.ipip99.com`，上线时回调路径应由实现固定，例如 `/api/payments/suisui/notify` 与 `/payment/result`。

### 服务商需补充确认

- 商户实际开通的支付方式及对应 `type` 值、手续费、单笔限额和到账时效。
- 是否提供沙箱、测试商户和测试支付方式；提供的 V1 文档没有确认沙箱能力。
- 回调重试策略、来源 IP 范围、回调 URL 白名单要求，以及订单金额/币种字段的精度规则。
- V2 RSA API 的完整文档、签名/验签流程及 V1 是否仍推荐用于新接入。商户页显示 V2 RSA 选项，但不能仅凭页面切换签名模式；必须先取得并实现匹配的 V2 契约。
- 退款 API 启用流程、部分退款规则、重复退款处理和退款结果查询能力。V1 文档注明需先在商户后台开启退款 API。

## 3. 充值与支付流程

### 在线充值

1. 已登录客户或销售选择充值金额和支付方式；客户端只提交金额档位/金额及支付方式，不提交 `pid`、密钥、订单金额快照或“已支付”状态。
2. 后端校验身份、金额、限额、通道状态，创建唯一的本地充值订单 `pending`，金额以整数分保存，生成不可预测且唯一的 `out_trade_no`。
3. 后端以表单方式请求 `/mapi.php`，按 V1 规则签名；只把支付 URL/二维码结果返回给前端。支付密钥、签名串和完整供应商响应不写日志。
4. 前端展示跳转或二维码。浏览器 `return_url` 只展示“正在确认/成功/失败”等状态，绝不直接给余额加款。
5. 后端通知地址校验签名、商户 ID、商户订单号、币种/金额、`trade_status`，再锁定充值订单。仅从 `pending` 转成 `paid` 时，在同一数据库事务内新增一笔唯一的钱包充值流水并增加余额；重复通知只返回 `success`，不会重复入账。
6. 通知缺失或状态不确定时，由后台订单详情触发服务端查询 `act=order` 对账。V1 查询会把密钥放在查询参数中，实现必须对支付域名、代理和应用日志配置脱敏，不能记录完整 URL。

签名按官方说明处理：参数名 ASCII 排序，忽略 `sign`、`sign_type` 和空值，按键值对拼接后附加商户密钥再计算小写 MD5；验签使用常量时间比较。金额、订单号、`pid` 和成功状态需与本地待支付订单逐项比对。只验签而不比对金额与本地订单仍可能错账。

## 4. 余额账本

当前 `Customer.balance` 是浮点数，不能继续作为唯一账务依据。建议引入以下表并逐步停止直接改写旧字段：

- `wallet_accounts`：按 `user_id` 唯一，为客户和销售分别建独立钱包；余额使用整数分，禁止负余额。
- `wallet_transactions`：不可变流水，记录钱包、类型（充值/订单扣款/退款/人工调整）、金额分、变动前后余额、关联本地订单/支付单、幂等键、操作者和时间。
- `payment_orders`：充值单本地订单号、用户、金额分、通道、支付状态、平台交易号、过期时间、最近对账时间；商户 ID 只需在配置中保存，流水仅记录通道版本和必要的脱敏信息。

钱包余额列作为并发访问的快速汇总值，账本流水是审计凭据。每次更改必须在事务中锁定钱包行、检查余额、写流水并更新汇总余额；唯一幂等键阻止重复回调、双击和重试重复入账。账务金额统一用整数分，禁止 Python/JavaScript 浮点数参与加减。

从旧 `Customer.balance` 迁移时先只读盘点非零余额、负数和超过两位小数的记录，备份后按确定的舍入规则生成期初流水，再进行双重核对。迁移脚本不能静默丢弃精度；本设计阶段不修改数据库。

## 5. 余额支付与销售代付

- 客户下单使用客户自己的钱包；服务端在一个事务中锁定钱包，验证余额充足，新增扣款流水并将订单设为已支付。并发扣款不得产生负余额，重复请求须通过幂等键返回原结果。
- 销售可为自己充值到独立的销售钱包。销售为客户订单代付时，订单的客户归属仍是客户，钱包流水记录销售 `payer_user_id` 和关联订单；需要限定销售只能为其负责客户付款，并完整审计。
- 销售不能直接增加客户余额或调整任意钱包。若要销售为客户“充值代充”，应另设有审批与账务凭证的操作，不应伪装成客户在线充值。
- 超级管理员人工调账应要求正/负方向、原因、关联凭证、二次确认和审计；禁止直接编辑余额数值。
- 支付成功与供应商采购/线路交付分开。余额扣款只改变本地订单付款状态；自动采购必须等待资源池采购契约、审批门槛、沙箱、超时对账与失败补偿完成。

## 6. 状态与 API 规划

充值单状态：`pending -> paid | failed | expired | manual_review`。通知金额不符、签名错误、订单不存在或相互矛盾时转人工核查，不自动入账。退款状态另建流程，不把“退款请求已提交”记为“余额已退”。

首期内部接口建议：

- 客户/销售：`GET /wallet`、`GET /wallet/transactions`、`POST /wallet/recharges`。
- 支付回调：`GET /payments/suisui/notify`，仅接受平台定义的通知字段并执行严格验签与幂等处理。
- 返回页：`GET /payment/result`，只查询本地充值单展示状态。
- 客户订单：增加明确的余额支付命令；重复支付安全返回，不允许客户端指定扣款用户或金额。
- 超级管理员：读取/更新支付配置状态、管理充值订单、发起单笔对账和查看脱敏审计；配置密钥写入接口不可回读密钥。

所有钱包接口仅允许客户或销售读取自己的钱包；管理员后台可以按授权查看对账所需信息，但密钥、签名原文和完整支付 URL 不向任何页面返回。

## 7. 分阶段实施

### 当前实现状态（2026-10-29）

- 已实现：整数分钱包账本、旧客户余额迁移、客户/销售钱包读取、管理员线下充值、客户订单余额付款、15% 销售佣金计提及整单退款冲销、超级管理员支付配置密文保存、支付域名连通性检查。
- 在线支付创建和通知验签代码已实现，但在线收款开关由后端固定关闭；当前未完成服务商沙箱或受控小额支付验收，不能当作可用收款能力。
- 外部渠道退款入口只登记已在支付平台或银行实际完成的退款，不调用退款 API。余额订单退款会返还原付款钱包。
- 资源池订单继续禁止余额/在线付款和自动采购；已收款不代表线路已交付。
- 本轮未部署、未连接生产环境、未使用真实支付凭据，也未创建真实充值、收款或退款。

1. 已实现账本与余额支付的基础代码；上线前仍须在隔离 PostgreSQL 验证并发扣款、重复请求、事务回滚和历史余额迁移；在线支付开关保持关闭。
2. 实现超级管理员支付管理与 V1 充值单，但先使用服务商沙箱/测试账号验证签名、金额校验、通知验签、重复通知、异步延迟、订单查询和日志脱敏。
3. 用户本人在生产超级管理员后台录入新商户 ID 和轮换后的密钥；完成正式 HTTPS 回调可达性、通道小额实测与对账后，再由超级管理员启用在线充值。
4. 退款 API 和自动供应商采购单独评估、单独开关，不随充值功能自动开放。

### 上线门禁

- 真实 `notify_url` 只能走 HTTPS；支付回调必须验签并校验本地订单、金额、币种、商户和支付状态。
- 支付密钥只存后端加密配置，禁止进入前端构建、数据库明文、Git、日志、异常和监控标签。
- 余额修改必须有不可变流水和数据库事务；禁止浮点记账、重复入账、负余额和无审计调账。
- 未完成服务商沙箱/小额支付、回调重试与对账验证前，在线充值开关保持关闭；支付成功不代表供应商采购成功或线路已交付。
