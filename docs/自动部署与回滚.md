# 自动部署与回滚

> 状态：流水线与服务器脚本已落地，**尚未在真实服务器执行**（缺部署密钥与服务器登录方式）。
> 关联：`docs/99ipxin独立生产部署.md`（首次部署与隔离网络）、`docs/数据库定时备份与恢复演练.md`（备份与恢复）。

---

## 1. 它做了什么

`.github/workflows/deploy.yml` → SSH → 服务器上的 `deploy/auto-deploy.sh`：

```
拉取目标版本 → 检查工作区干净 → 发布前备份 → build api/web
→ run --rm migrate → up -d api worker web → 轮询 /readyz
   ├─ 成功：记录 last-success-ref，结束
   └─ 失败：checkout 上一个版本 → 重建 → 再验一次 → 仍失败则保留现场并退出 1
```

设计取舍：

- **在服务器构建**，不推镜像仓库。现有 `docker-compose.prod.yml` 本来就是 `build:` 模式，改成 GHCR 要同时改编排、拉取凭据和回滚方式，收益不值这个复杂度。
- **发布前必须备份**。迁移一旦执行，代码回滚救不了 DDL；备份是唯一可靠的退路。
- **健康检查分三层**：api 容器 healthcheck 为 `healthy`、容器内 `127.0.0.1:8000/readyz` 返回 200、web `127.0.0.1:18081/healthz` 返回 200。宿主机 `18081/readyz` 会落到 SPA 的 `index.html`（假 200），不能当探针用。
- **构建走 `docker build --network=host`**：这台服务器的容器 DNS 访问不了公网，`docker compose build` 会 `EAI_AGAIN`。换到网络正常的环境可设 `BUILD_NETWORK_HOST=0`。
- **同一时间只允许一个发布**（`flock`），避免两个人同时点。

## 2. 一次性准备

### 2.1 服务器

- 项目目录固定为 `/opt/99ipxin`（或通过 `DEPLOY_PATH` 指定），必须是 **git clone 的仓库**，不是手工上传的目录。
- 部署账号对项目目录有读写权限，能执行 `docker compose`（加入 `docker` 组），**不需要 sudo**。
- `.env.production` 已在目录内，权限 `0600`；首次部署已完成（见 `99ipxin独立生产部署.md`）。
- 服务器能访问 GitHub（`git fetch`），且 `python3`、`curl`、`flock` 可用。
- 备份脚本已就位：`scripts/backup_postgres.py` 与 systemd timer（见备份文档）。

### 2.2 GitHub Secrets

在仓库 **Settings → Secrets and variables → Actions** 添加：

| Secret | 必填 | 说明 |
| --- | --- | --- |
| `DEPLOY_HOST` | 是 | 服务器 IP 或域名 |
| `DEPLOY_USER` | 是 | 部署账号（非 root 亦可，需 docker 权限） |
| `DEPLOY_SSH_KEY` | 是 | 部署账号的私钥（ed25519，无 passphrase） |
| `DEPLOY_PORT` | 否 | SSH 端口，默认 22 |
| `DEPLOY_PATH` | 否 | 项目目录，默认 `/opt/99ipxin` |
| `DEPLOY_HOST_KEY` | 否 | 服务器 host key（`ssh-keyscan -H host` 的输出）。不填则每次 `ssh-keyscan`，首次连接仍有被中间人的窗口 |

建议在 GitHub 里创建 `production` Environment，把 Secrets 放在 Environment 下，并加 required reviewers——这样"自动部署"仍然有人把关。

### 2.3 分支

当前生产分支是 `codex/admin-layout-finance-deploy`。工作流在 **push 到 `main` 或该分支** 时自动触发；也可以用 Actions 页面的 **Run workflow** 手动指定 branch/tag/commit。以后统一走 `main` 时，把 codex 分支从 triggers 里删掉。

## 3. 日常发布

### 自动

合并到 `main` → Actions 自动执行 → 看 job 日志。成功标志：

```
[deploy ..] 健康检查通过（第 N 次）
[deploy ..] 发布完成：<sha>
```

### 手动（推荐先这样验证一次）

Actions → **Deploy production** → Run workflow → `ref` 填分支名或 commit sha → Run。

### 服务器上直接执行

```bash
cd /opt/99ipxin
./deploy/auto-deploy.sh <commit-or-tag>
```

日志同时输出到终端和 `deploy/logs/`（脚本未重定向文件，建议手工 `| tee`）。

---

## 4. 回滚

```bash
cd /opt/99ipxin
./deploy/auto-deploy.sh --rollback
```

它会回到 `deploy/logs/last-success-ref` 记录的版本（只记录**部署成功**的版本，失败的不会覆盖）。

手工回到指定版本：

```bash
./deploy/auto-deploy.sh <上一个成功的 sha>
```

**迁移的前向兼容是前提**：如果新版本执行了 `DROP COLUMN` / 改类型 / 加 NOT NULL 且无默认值，旧代码回滚后会直接报错。本项目的约定是 expand → migrate → contract，删列至少隔一个版本；发布前 review 迁移时请守住这条。

如果代码回滚也救不回来（例如迁移把数据写坏），按 `docs/数据库定时备份与恢复演练.md` 用发布前备份恢复，不要在生产库上手工 `alembic downgrade`。

## 5. 验收清单（首次接入时执行一次）

- [ ] 服务器 `git status` 干净，`git log -1` 是预期版本
- [ ] `python3 scripts/backup_postgres.py --check-only` 退出码 0
- [ ] 手动触发一次发布，日志出现「健康检查通过」「发布完成」
- [ ] `curl -fsS http://127.0.0.1:18081/healthz` 返回 200；`docker inspect` 中 api 为 healthy
- [ ] `docker compose ... ps` 中 api / worker / web 均为 healthy（worker 无 healthcheck，状态 running）
- [ ] 故意发布一个坏版本（例如临时让前端构建失败），确认自动回滚生效且 `last-success-ref` 未被覆盖
- [ ] 回滚后 `alembic current` 与代码期望一致

## 6. 已知限制

- **不是零停机**：`up -d` 会重建 api/web 容器，期间有数秒 502。当前单机单实例，接受这个窗口；要零停机需要多副本 + 负载均衡，不在本次范围。
- **构建在服务器上**：首次构建几分钟，且占用服务器 CPU/内存。服务器规格较小时建议加 swap 或在低峰发布。
- **不在 CI 里跑测试**：本工作流只负责发布，测试门禁由 `ci.yml` 负责。建议在 GitHub 分支保护里要求 CI 通过后才能合并到 `main`，否则自动部署会把红灯发上去。
- **密钥轮换**：`DEPLOY_SSH_KEY` 轮换后要同步更新服务器 `authorized_keys`；`DEPLOY_HOST_KEY` 在服务器重装后必须更新，否则发布会因 host key 不匹配失败（这是有意的）。
