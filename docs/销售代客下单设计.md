# 销售代客下单设计

> 状态：**已实施（2026-11-09）**。背景（2026-11-09）：客户自助下单已通，销售没有下单入口——销售在微信接完单，只能让管理员去后台开，或者逼客户自己注册。实测：销售调 `/api/customer/orders` → 403，调 `/api/orders` → 400「客户订单必须以客户身份创建」，`/api/admin/order-center/orders` 是资源池采购单（要 supplier 六件套），不是客户销售单。
>
> 拍板结论（玖夜 2026-11-09）：**折扣上限 7 折（30%），且只有管理员能设**；管理员同样有这个入口。落地位置：`api/routes.py` 的 `create_order_on_behalf`、`schemas/common.py` 的 `OnBehalfOrderIn`、迁移 `0028_order_created_via`、前端 `components/OrderOnBehalfDialog.vue`（销售「负责客户」与管理员客户详情页共用）。实施差异见文末 §13。

## 0. 一句话方案

新增**一个**代客下单接口 `POST /api/orders/on-behalf`：销售只能给名下客户开单，管理员可给任意客户开单，复用现有 `build_order` 与算价逻辑；订单落 `created_via='sales_assisted'` 留痕。前端在销售「负责客户」列表每行加「代客下单」按钮，弹窗选产品/周期/数量/支付方式，实时算价。

## 1. 现状事实（决定设计边界的几条）

| 事实 | 位置 | 对设计的影响 |
| --- | --- | --- |
| `build_order` 已经写 `assigned_sales_id=customer.sales_id` | `api/routes.py:210` | 代客下单后业绩**自动归销售**，不需要额外的归属逻辑 |
| 算价只在 `pricing_service`，`/public/orders/preview` 免登录可用 | `api/routes.py:708` | 弹窗实时算价直接复用，不用新写价格接口 |
| 支付方式只有三种：`balance` / `online` / `contact_manager`，决定初始状态 | `order_service.py:11,31` | 代客下单不改状态机，只选支付方式 |
| 订单表**没有** `created_by` / `created_via` | `models/entities.py:122` | 需要一个小迁移，否则列表页无法区分自助单与代客单 |
| `orders.idempotency_key` 唯一约束已存在，但客户下单没传 | `models/entities.py:128` | 代客下单**必须传**（双击、网络重试都会重复建单） |
| 已有 `scoped_customer_ids(db, user)` | `services/customer_scope.py:16` | 销售/管理员的数据范围直接复用，不另写判断 |
| 客户可能**没有登录账号**（`customers.user_id` 为空，管理员手建客户） | `models/entities.py` Customer | 没账号的客户不能用余额/在线支付，也不能自助看单 |
| 订单通知 `notify_order_parties` 会同时通知客户与该单销售 | `order_service.py:166` | 代客下单时销售会收到自己操作的通知，属于噪音，要跳过 |

## 2. 接口设计

```
POST /api/orders/on-behalf
权限：sales / admin / super_admin
```

请求体 `OnBehalfOrderIn`：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| customer_id | int | >0 | 必填，代谁下单 |
| product_id | int | >0 | 必填，仅在售产品 |
| region_id | int \| null | — | 不传则取产品所属地区 |
| quantity | int | 1–100 | 默认 1 |
| billing_days | int \| null | >0 | 不传取产品默认周期 |
| payment_method | str | 三选一 | 默认 `contact_manager` |
| discount_percent | float \| null | 0 ≤ x ≤ 上限 | 默认不传 = 不打折 |
| remark | str \| null | ≤1000 | 写进订单备注 |
| idempotency_key | str | 36–64 | **必填**，前端 `crypto.randomUUID()` |

响应：`OrderOut`（与客户下单同一结构）。

错误语义：

| 场景 | 状态码 | 提示 |
| --- | --- | --- |
| 客户不存在 / 不在自己名下 / 已删除 | 404 | 「客户不存在或无权操作」——不区分两种情况，避免探测他人客户 |
| 产品停用或无货 | 404 | 沿用现有文案 |
| 产品与地区不匹配 | 422 | 沿用现有文案 |
| 折扣超上限 | 422 | 「折扣超过你的权限（上限 X%），请联系管理员」 |
| 客户无登录账号却选余额/在线支付 | 422 | 「该客户还没有登录账号，只能用『联系经理』方式下单」 |
| 同幂等键但 customer_id 不同 | 409 | 「请求重复但客户不一致，请刷新后重试」 |

幂等语义：同一 `idempotency_key` + 同一 `customer_id` → 直接返回原订单（200，不新建）；不同客户 → 409。这样双击、超时重试、客户端重放都安全，又不会被跨客户撞键串单。

## 3. 权限与数据范围

| 角色 | 可下单的客户 |
| --- | --- |
| sales | 仅 `customer.sales_id == 自己` 且未删除；否则 404 |
| admin / super_admin | 任意未删除客户 |
| customer | 无权限（403），继续走 `/api/customer/orders` |

判断全部走 `scoped_customer_ids`，不手写 `if`，避免以后新增角色时漏改。

## 4. 价格与折扣

- **默认价格与客户自助下单完全一致**：同一个 `calculate_order_price`，不存在「销售价 / 客户价」两套价。
- 折扣由配置 `MAX_ORDER_DISCOUNT_PERCENT` 控制，**默认 30（即 7 折）**；设为 0 就完全禁止折扣。
- **折扣只有 admin / super_admin 能设**：销售传 `discount_percent` 一律 403「折扣只能由管理员设置」。销售按标价开单，要优惠找管理员——这样价格口径只有一个人在动。
- 折扣内不超过上限时：`unit_price`、`total_amount` 按折扣重算并落库，订单备注自动追加「销售折扣 X%」，审计记录原价、折后价、折扣比例。
- **不做审批流**。让价审批要状态机 + 待办 + 通知 + 超时，成本是现在这个方案的 3 倍；先用「上限 + 管理员兜底」顶住，等真出现频繁超额让价再说。
- 折扣会自然降低收款额，提成按收款计提，所以提成也自动降低，不需要额外规则。

## 5. 落库变更（migration 0028）

`orders` 加两列：

| 列 | 类型 | 默认 | 用途 |
| --- | --- | --- | --- |
| created_via | String(20) | `self_service` | `self_service` / `sales_assisted` / `admin` |
| created_by_user_id | FK users.id, nullable | null | 谁操作创建的（销售或管理员） |

索引：`ix_orders_created_by_user_id`（按销售统计代客单量、排查异常单）。
存量数据回填 `self_service`（客户自助下的单，语义正确，不需要按审计反推）。

这两列是**可选增强**：如果不想动表，也可以只靠审计日志区分；但列表页要显示「代客」标记就得 join 审计表，不划算，建议加。

## 6. 通知文案

| 收件人 | 是否通知 | 文案 |
| --- | --- | --- |
| 客户（有账号） | 是 | 「销售 XXX 为你创建了订单 ORD-…，金额 ¥N，请在订单中心确认并支付」 |
| 客户（无账号） | 否 | 前端提示「该客户没有登录账号，请线下告知」 |
| 操作该单的销售本人 | **否** | 是他自己点的，发通知纯噪音 |
| 其他管理员 | 否 | 订单在订单中心可见 |

实现上给 `notify_order_parties` 加一个 `skip_sales: bool = False` 参数，代客下单传 `True`，现有调用点行为不变。

## 7. 状态与后续流转（不改状态机）

| 支付方式 | 初始状态 | 谁来推进 |
| --- | --- | --- |
| contact_manager | `pending_confirm` | 管理员确认收款（现有逻辑） |
| online | `pending_payment` | 客户自己在线支付（现有支付闸门全部生效） |
| balance | `pending_payment` | 客户余额支付；余额不足会失败，前端如实提示 |

代客下单**不代付、不代交付**：钱必须客户自己出或走管理员线下充值，交付仍归管理员（避免销售自交自验）。

## 8. 前端

**入口**：销售工作台「负责客户」列表，每行末尾加次要按钮「代客下单」（`.outline-action` 级别，不抢主视觉）。

**弹窗 `OrderOnBehalfDialog`**：

| 区域 | 内容 |
| --- | --- |
| 头部 | 客户名 + 联系方式（只读，防止选错人） |
| 表单 | 产品下拉（`getPublicProducts`，只列在售）→ 地区（随产品带出，只读）→ 数量 → 周期（产品 `periods`）→ 支付方式（默认联系经理；客户无账号时禁用在线/余额并说明）→ 备注 |
| 价格 | 右下角实时显示「单价 × 数量 = 合计」，调 `previewOrder`，300ms 防抖；请求失败显示「价格获取失败，请重试」，不允许提交 |
| 提交 | 按钮 loading + 禁用；`idempotency_key` 在弹窗打开时生成一次，提交成功后才重置 |
| 成功 | toast 显示订单号 + 「去订单中心」，同时刷新右侧客户订单列表 |

**管理员侧**：客户详情页复用同一弹窗（`customer_id` 固定，不可改），放在资料区主操作位。

**移动端**：弹窗改为全屏 sheet，字段单列，价格固定在底部。

## 9. 测试清单（≥12 条）

1. 销售给自己名下客户下单 → 201，`assigned_sales_id`、`created_by_user_id`、`created_via` 正确。
2. 销售给别人的客户下单 → 404。
3. 管理员给任意客户下单 → 201。
4. 客户身份调该接口 → 403。
5. 幂等：同 key 重复提交 → 只建一单，第二次返回同一 `id`。
6. 同 key 不同客户 → 409。
7. 无账号客户 + `online` → 422；无账号客户 + `contact_manager` → 201。
8. 折扣超上限 → 422；上限内 → `unit_price`/`total_amount` 按折扣正确。
9. 折扣配置为 0 时任何折扣 → 422。
10. 停用产品 / 已删除客户 → 404。
11. 通知：客户收到 1 条，销售不额外收到。
12. 审计：`create` 记录含原价、折后价、折扣；`created_via` 落在订单上。
13. 回归：客户自助下单路径与订单列表、订单中心显示不受影响。

## 10. 明确不做

1. **不代客支付、不代客充值**——钱必须客户自己出，否则资金链与对账口径全乱。
2. **不代客交付**——交付仍归管理员，销售不能自交自验。
3. **不允许销售自建客户**——客户只能来自邀请码注册或管理员分配，否则归属可被绕过。
4. **不做批量下单 / 购物车**——单条 30 秒能开完，批量是给运营用的，不是销售。
5. **不做改价审批流**——见 §4，用上限 + 管理员兜底。
6. **不做「销售价」体系**——一套零售价，避免两套价对不上账。

## 12. 风险与前置确认

| 风险 | 处理 |
| --- | --- |
| 折扣一开就乱价 | 折扣只有管理员能设、上限 30%（7 折），销售无权改价；超限 422 |
| 无账号客户占比高，代客下单价值打折 | 上线前先查 `select count(*) from customers where user_id is null`；占比高就先补「给客户开账号」 |
| 同客户同产品连开两单（不同幂等键） | 不拦，前端提交前二次确认：「该客户 5 分钟内已有一笔同产品订单，仍要创建？」 |
| 销售把单开错客户 | 弹窗头部固定显示客户名 + 手机号，提交前二次确认 |

需要玖夜拍板两件事：**折扣上限给多少（还是先关着）**、**管理员是否也需要这个入口**（我默认给，因为现在管理员同样开不了客户单，只能开资源池采购单）。

## 13. 实施记录与差异（2026-11-09）

| 项 | 设计 | 实际 | 原因 |
| --- | --- | --- | --- |
| 折扣配置名 | `SALES_MAX_DISCOUNT_PERCENT` | `MAX_ORDER_DISCOUNT_PERCENT`，默认 **30**（7 折） | 折扣不只销售场景用，命名去掉 SALES 前缀更准确 |
| 折扣权限 | 销售可用、上限内 | **仅 admin / super_admin 可设**，销售传了直接 403 | 玖夜拍板：价格口径只留一个出口，销售按标价开单 |
| `created_by_user_id` 外键 | 外键指向 users | **普通列 + 索引，不加外键** | SQLite 不支持 ALTER 加外键，批量重建又要给历史匿名约束先行命名；这是审计字段，用户不会被硬删除 |
| 客户是否有账号 | 前端自行判断 | `CustomerOut` 新增 `has_account`，由 `customer_view` 按 `user_id` 计算 | 前端拿不到 `user_id`，加个布尔最省事，也避免前端猜 |
| 提醒销售 | 设计里未提 | `notify_order_parties(skip_sales=True)`，代客下单不给自己发站内信 | 销售是操作者，再推一条纯噪音 |
| 管理员入口 | 待定 | 已加：客户详情页「代客下单」，`customer_id` 固定 | 管理员同样需要给客户开单，之前只能开资源池采购单 |
